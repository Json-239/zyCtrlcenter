# 链数据（data/chains）

> 链数据是**可选资产**：中控不内置任何链数据，文件由使用方准备；中控只做**加载 + 原样透传**。
> 实现：`internal/chainlib/`（`chainlib.go` 加载与列表、`passthrough.go` 未知字段透传）。
> 目录里的 README 与模板：`data/chains/README.md`、`data/chains/_example.json`。

## 1. 为什么是「文件驱动 + 原样透传」

- **文件驱动**：加链不改代码——把 JSON 丢进目录，`/api/chains` 立刻能看到，面板即可启动；
- **原样透传**：真实链数据里同一字段有不同形状（例：`npcs` 既可能是 `[[map,x,y],…]` 也可能是 `[map,x,y]`；
  `dijkstra` 既可能是对象也可能是数组），还带大量中控不认识的字段（`ghost_map_pos`、`item_meta`、`catcher_name`…）。
  用强类型结构体会**丢字段或解析失败**，因此中控只搬运不改写。

## 2. 文件约定

| 项 | 规则 |
|---|---|
| 位置 | `<数据目录>/chains/`（默认 `data/chains/`；随 `--data-dir` 联动） |
| 命名 | `<文件名>.json`，**文件名（去掉 .json）= 列表 id = 面板查询用的 `?id=`**（保证「列表里看到的 id 一定能查到」） |
| 下发用的链 ID | 文件内 `chain_id` **优先**（没有才用文件名）；`/api/chains` 会同时给出 `id` 与 `chain_id` |
| 模板 | 以 `_` 开头（如 `_example.json`）不参与 `/api/chains` 列表 |
| 损坏 | 出现在列表里并带 `error` 字段，不影响其它链 |
| 缺失 | 启动链只下发 `chain_id`（不带 `chain`），由机器人端决定怎么跑 |

  手选它启动会被接口层直接拒绝（`ok:false, nav_only:true`）——但**仍然可以选中查看**（抓鬼排障要看 `ghost_maps`/`ghost_map_pos`）。

## 2.1 抓鬼导航数据怎么给（2026-09-21，口径对齐参考实现）

抓鬼（`ghost_start`）与任务链不同：机器人端只认命令里的 `chain` —— 没有它，机器人不知道**钟馗在哪**、**该去哪些刷鬼图**、**怎么寻路**，表现就是"原地不动 / 空点钟馗"。

**中控不让你准备一份 2MB 的大文件**：载荷是**组装**出来的（口径照参考实现 `services/chain.py: ghost_nav_payload()`）：

| 来源 | 提供什么 | 说明 |
|---|---|---|
| 基座链 `<GhostBaseChainID>.json`（默认 `newbie_full`） | `npcs`（含钟馗 10146 等所有 NPC 坐标）/ `map_grids`（寻路网格）/ `dijkstra`（跨图路由）/ `grid_cell` / `item_meta` | 与新手链**同一份数据**，链数据更新后抓鬼自动跟随（不会"新手链换了、抓鬼还用老网格"） |
| 抓鬼专属 `<GhostNavChainID>.json`（默认 `zhongkui_nav`） | `ghost_maps`（刷鬼图列表）/ `ghost_map_pos`（每张刷鬼图的筋斗云落点）/ `maps`（地图名，可选） | **只需放这三项（约 1.7KB）**；也兼容直接放完整导出（向后兼容） |

参考实现里这三项的来历（本中控只消费、不生产）：`ghost_maps` 从 `20195.xml` 的「捉鬼npc」`npc_map_index_str` 解析；`ghost_map_pos` 取该刷鬼图里第一个 NPC 的坐标；`maps` 来自 `map.csv`。导出命令见 [§4 方式 B](#4-怎么准备链数据)（`services.chain.ghost_nav_payload()` 直接产出完整版，可直接用）。

**发命令时的硬校验与硬失败**（宁可报错，也不发一份"导航不了"的载荷）：

| 场景 | 行为 |
|---|---|
| 基座链或专属文件缺失/解析失败 | `ok:false` + 明确 msg，**一条命令都不发**（含不与新手链分组混发） |
| 刷鬼图在 `map_grids` 里没有网格 | 报错点明是哪张图（否则机器人到图后只能直线走 = 穿墙/到不了鬼） |
| 刷鬼图缺 `ghost_map_pos` 落点 | 报错（筋斗云传送要用） |
| `npcs` / `dijkstra` 为空 | 报错（基座链选错了） |

命令形状（与参考实现一致）：`ghost_start{accounts, chain_id, chain, role:"solo", daily_limit:50, done:{账号:已抓次数}}`。
`daily_limit` 见配置 `GhostDailyLimit`（默认 50）；`done` 取运行时状态里机器人上报的 `ghost.done`（有才带，重新下发不丢进度）。
掉线恢复补发同样带 `chain` + `daily_limit`（取不到就不补发，连续 3 次熔断等人工）。

> 载荷 2.2MB 在机器人端 8MB 单行上限内；补发时**同命令 + 同链合并成一条**（`/api/intents/restore` 的 `commands`），避免 N×2MB。
> **想省 2.2MB**：把 `data/chains/zhongkui_nav.json` 换成只含 `ghost_maps`/`ghost_map_pos`/`maps` 的精简版即可（基座自动补坐标与网格），两份文件不会重复占空间。


## 2.2 分享日常（大唐神捕）载荷怎么给（2026-09-23）

与抓鬼**同一口径**（组装、硬校验、硬失败）：

| 来源 | 提供什么 | 说明 |
|---|---|---|
| 基座链 `<GhostBaseChainID>.json`（默认 `newbie_full`） | `npcs`（含张忍慎 13297 等）/ `map_grids`（寻路网格）/ `dijkstra`（跨图路由）/ `grid_cell` / `item_meta` | 与新手链同一份数据；`shenbu_nav.json` 不重复放坐标 |
| 声明文件 `<ShareDailyChainID>.json`（默认 `shenbu_nav`，配置 `CTRL_SHARE_DAILY_CHAIN`） | `task_order`（**必须列全该玩法全部分支任务号**：大唐神捕 `2028301/2028302/2028311/2028399`；少列会让后续环节被机器人当「链外任务」**静默忽略**）+ 可选 `name`/`start_task`/`end_task` | 只放玩法声明，不放坐标/网格 |

**发命令时的硬校验与硬失败**（`internal/api/chainpayload.go:ShareDaily`）：声明文件缺失/解析失败、`task_order` 为空或有条目缺 `task_index`、基座 `npcs`/`dijkstra` 为空 → `ok:false` + 明确 msg，**一条命令都不发**。

命令形状：`share_daily_start{accounts, share_key:"share_daily_大唐神捕", chain_id, chain, daily_limit:10, done?:{账号:已做次数}}`；
`share_daily_stop{accounts}` 对称。`share_key`/`daily_limit` 见配置 `CTRL_SHARE_DAILY_KEY` / `CTRL_SHARE_DAILY_LIMIT`。


## 3. 字段（中控解析用到的最小集合）

| 字段 | 用途 |
|---|---|
| `chain_id` / `name` | 列表与详情展示 |
| `start_task` / `end_task` | 面板展示起止任务号 |
| `task_order` | 数组；面板按「任务号/名称/接取 NPC/后续任务」渲染（**形状任意**，容错展示） |
| `task_hints` / `npcs` / `maps` / `map_grids` / `dijkstra` | 面板统计 + 下发 |
| 其它任意字段 | 原样透传（不会丢） |

缺省补齐（文件没写时）：`grid_cell` → 16；`npcs`/`task_hints`/`map_grids`/`dijkstra` → 空对象；
`task_order` → 空数组（保证机器人端拿到的是对象/数组而不是 null）。

## 4. 三条来源与优先级（`POST /api/start`）

| 优先级 | 来源 | 响应里的 `chain_source` |
|---|---|---|
| 1 | 请求体带 `chain` | `request` |
| 2 | `data/chains/<chain_id>.json` | `file` |
| 3 | 都没有 | `none`（只下发 `chain_id`） |

## 5.1 客观闸门与落点修正（2026-09-19 新增）

- **客观闸门**：`go test ./test/chaindata/` —— 只用游戏服本机 `map_file/blockfile`（0=可走 1=阻挡，格子=坐标/16）
  校验链数据，不引用任何一方（含参考实现）的结论：任务 NPC 坐标可走、所在图有网格且在 `map_grids`、
  抓鬼落点可走、dijkstra 两端有网格、真实链不能有组装错误。本机没有游戏服配置目录会自动跳过
  （可用 `ZY_GAME_CONFIG` 指定）。
- **落点修正工具**：`go run ./tools/fixlanding`（默认 dry-run，`-write` 写回）——把 `ghost_map_pos`
  的阻挡落点换成"同图可走 NPC 坐标"，都不行就 BFS 找最近可走格。已修：图9 `(481,604)`（阻挡）→ `(787,780)`。
- 基线（`dynamicNpcBaseline` / `knownBlockedNpcCounts` / `knownBlockedLandings`）是**故意**的：
  把"已知可接受"固定下来，链数据一变就报警，逼人复核一次。

## 6. 校验与排障

```powershell
go test ./test/chainlib/ -v            # 加载/缺省/透传/目录扫描（含真实形状夹具）
curl "http://127.0.0.1:28082/api/chains"          # 列表（含 error 字段）
curl "http://127.0.0.1:28082/api/chains?id=<id>"  # 详情 + chain_found
```

| 现象 | 原因 | 处理 |
|---|---|---|
| 面板链列表为空 | 目录里没有 `.json` 或全是 `_` 开头 | 放进 `<chain_id>.json`；确认 `chain_dir` 路径（系统信息页可见） |
| 列表条目带 `error` | 文件不是合法 JSON | 按提示修文件；其它链不受影响 |
| 启动成功但机器人拿不到链数据 | `chain_source=none`（没有文件） | 放好文件或用请求体带 `chain` |
| 机器人收到链数据缺字段 | 不应该发生（透传） | 检查是否有人手工改了链文件；跑 `go test ./test/chainlib/` |
