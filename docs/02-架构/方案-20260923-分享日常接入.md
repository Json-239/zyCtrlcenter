## 1. 背景与目标

- **目标**：让机器人自动跑"大唐神捕""烽火大唐"两条日常（当前只有"捉鬼"）。
- **现状**：捉鬼是**特化状态机** `daily_ghost.py`（4000+ 行、几十次现场迭代：钟馗卡对话、task_limited 计数、放弃扣金币……）。
- **关键发现**：分享日常在客户端**不是特化实现**——玩法差异全部收敛在 `config/auto_task.csv` 一行配置（接取 NPC / 杀怪名单 / 采购 / 巡逻 / 收尾任务号），执行逻辑由通用状态机驱动。**这决定了本次的技术路线。**

### 2.3 客户端通用机制（我们要照抄的行为口径）

1. **无专属协议**：点 NPC → `C2S_CLICK_DIALOG(80139)` → 服务端 ticket `action_pick_task`（组内加权随机）→ `S2C_ADD_TASK(90365)`。
2. **日限口径（关键）**：按 `share_daily_key` 共用一份 `task_limited`（`90152` 登录全量 / `90300` 增量），**只在主任务（episode_root）完成时 +1**；收尾环节 `daily_limit=-1` 不重复计数。
3. **"次数满 ≠ 立刻收工"**（`auto_task_manager.py:1061-1110`）：主任务完成瞬间计数 +1，但收尾任务还在身上 → **本轮有未完成在身任务就绝不停止，先跑完**（大唐神捕第 10/10 轮的 `2028399` 必须照跑）。
4. **归属判定三级**：`chain`（后续有自己的 share_key）→ `chain_task`（按 task_index 点名）→ `keywords`（任务名子串）；`__keep_playthrough_key` 在切到无 key 的后续任务时保留原 key。
5. **接取三段判定**（防把冷却误判成失败）：走不到 NPC 20s → 首次实际点击后 3s 无判决 → 票据仍可接则进最多 900s 冷却等待。
6. **`submit_npc` 不要照搬覆盖**：链式任务各环节交付 NPC 不同时该列留空；用任务自带 `finish_npc_index`（大唐神捕 B 分支 catcher 是 `13597`）。
7. **包满通知码 5 个**（360/415/418/528/1295，窗口 15s）、**停止条件 9 类**（`auto_task_design.md:§9`）。
8. **字段消费对照表**：15 列逐列落位（`auto_task_config.py` 解析行号 + manager/state 消费行号），见 gp-2 报告。

### 2.4 机器人端现状（复用面）

**可直接复用**：`fight_tester.py`（定制战斗同协议，协议层零改动）、`msghandle→quest_engine.dynamic_npcs`（动态 NPC 跟踪）、`daily_ghost.__parse_task_attr`（12053/12054 解析，需从私有实现泛化）、`quest_engine` 寻路/点击/对话/事件、中控 `autotask.LaunchTask`/池/在途/水位/恢复框架。

**需新开发**（合并 gp-2/gp-3 结论，最硬的六条）：
1. **无服务端 `task/*.xml`** → 票据条件（等级/同类任务/buff 冷却/broker）本地求值不了 → **条件配置化**（等级=配置）+ 靠服务端推送（`task_limited` 计数、buff 状态）与"静默拒绝→冷却等待"兜底；
2. **三段式接取 + 随机任务识别**（烽火大唐：点秦琼→选"烽火大唐"→选"接受"；票据项/交付项/催促对话混排，`quest_engine.py:1071-1090` 的"点第一个非关闭项"会点错）；
3. `attr 12055 TASK_ITEM_INDEX_LIST` 全仓无消费（押送"银两"与 24 选 1 军需品的物品索引都靠它）；
4. 走路遇怪（暗雷）与"多目标点遍历"目前只有捉鬼专用实现，需泛化（巡逻需"先到 `12053` 指定图 + 打到计数达标"）；
5. `shop` 列（前缀→4 家店路由、储备金/金币两段式、关键词选型）机器人端不存在（`shop_errand.py` 走储备金单通道、无前缀路由）；
6. 链数据 `task_order` 必须**全列任务号**（大唐神捕 4 个 + 烽火大唐 7 个），否则后续环被 `chain_task_set` 静默忽略、链停在收尾前。

## 3. 路线选择（关键决策）

| | 路线 A：通用日常驱动（推荐） | 路线 B：每条链特化 ×2 |
|---|---|---|
| 形态 | 机器人端新增"通用驱动"（配置表 + demand 分型状态机 + 通用闸）；两条链=两行配置 | 仿 `daily_ghost.py` 各写一条专用状态机 |
| 一次性成本 | 中（~2000 行新代码，但**一次覆盖多条玩法**） | 高（每条 ~1500-3000 行，且各带一套现场坑） |
| 后续玩法（伏魔/护卫/打听） | 近乎零代码（加配置行） | 每条再来一轮 |
| 维护 | 一套口径（照抄客户端），修一处全线受益 | N 套并行，口径漂移风险大（项目已有 daily_ghost/quest_engine 双状态机教训） |
| 风险 | 通用抽象初期要覆盖 A/B 分支与采购/巡逻差异 | 上线快但长期成本高；客户端有现成权威实现却不用 |

**推荐路线 A**，但**分期落地**（§5）：P0 只覆盖"大唐神捕"所需能力（点击型杀怪/多点轮换/掉任务恢复），P1 扩烽火大唐（采购/巡逻/五子任务），P2 灰度池化。抽象不做过度设计——只照抄客户端已验证的行为。

## 6. 成本与风险

**成本量级**：P0 ≈ 机器人端 1200±400 行 + 中控 400±150 行 + 链数据 1 份 + 单号验证；P1 追加 ~800/+200 行；P2 主要是观察与调参。相对照：`daily_ghost.py` 单条链已累计 ~4000 行/数十次迭代。

**风险清单**：
1. **掉任务**：大唐神捕 A 分支定制战斗失败/逃跑即掉任务 → 战斗策略必须保守（普攻闸）；掉任务后要能自动重接（还有日限时）。
2. **未实测项**（先测再排期）：需求判定链（击杀"匪首老大"是否确由编队内死亡触发）、烽火大唐暗雷坐标是否进 `12054`。
3. **数据源不一致**：两份 `auto_task.csv`（客户端 15 列权威 / 服务端 12 列截断）→ 实施前统一（勿整体覆盖，按双副本纪律）。
4. **条件求值**：机器人端无 task XML；"已持有同类任务"这类拒绝只能靠服务端行为兜底（接取静默拒绝→冷却等待）。
5. **资源占用**：40+ 号（203/231）同时挂新日常与抓鬼的登录/包量压力 → P2 灰度验证。
6. **传送费**：大唐神捕满轮 ≈1000 开元通宝/天，需确认号上余额充足（否则需自己走回，时长不可控）。
7. **烽火大唐·采购货币**：金币兜底对绝大多数号必失败（现金中位 275 vs 金币价 500~10000）→ 采购须以**储备金**为主；`210xxx` 武器在金币货架**无标价（价格 0，疑配置缺失，需实测）**。
8. **烽火大唐·筋斗云三级降级**：免费→道具筋斗云→100 开元通宝→**全无则不传送**（须自己走回 610，时长不可控）。
9. **烽火大唐·地图与背包**：动态军需官/将军可能刷进 26/27 地狱图；背包需 ≥1 格；放弃冷却 buff `20021999` 文案冲突（XML 十分钟 vs buff.xml 3 分钟/180s）。

## 7. 决策点（需拍板）

1. **路线**：通用日常驱动（推荐）还是每条链特化？
2. **普攻闸**：两条新日常（全部定制战斗）是否**显式切普攻**（不走"非剧情用技能"的现口径）？
3. **数据源**：`auto_task.csv` 以**客户端 15 列版**为权威并同步进机器人端？
