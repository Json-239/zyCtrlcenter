# 任务链路模块化设计（新手链 / 抓鬼）

> 目的：把"账号该跑哪条链、跑的时候怎么推进、出问题怎么恢复"讲清楚，并明确**哪些逻辑留在机器人端、哪些留在中控**。
> 依据：参考实现 `robot/deploy/single_robot/script/{quest_engine,quest_state,daily_ghost,msghandle}.py` 与
> `robot/ctrlcenter/{chainlib,routers/auto_onboard,services/intent_restore}.py` 的实际做法（本节所有引用均为事实核对过的位置）。
> 状态：**P0 已实现**（意图表/判据/单链互斥）；P1（恢复引擎）、P2（进度契约）待做。

## 1. 先说一条硬事实：**没有"主动查询任务"的协议**

- 任务表只有两条来路：
  1. **登录期**服务端推 `S2C_LOAD_TASK(90037)`（+ `S2C_LOAD_TASK_EPISODE(90038)`）——**唯一的一次全量**；
  2. **运行期**服务端推增量：`S2C_ADD_TASK(90365)` / `S2C_UPDATE_TASK(90396)` / `S2C_FINISH_TASK(90072)` / `S2C_DROP_TASK(90413)`。
- 参考实现里**没有任何主动查询任务列表/进度的 C2S 消息**；主动手段只有 GM 指令 `@addtask/@deltask/@cleartask`（`quest_engine.__admin:133`）。
- 中控的 `/api/start` 下发的链数据（`task_order` / `task_hints`）是**提示表，不是指令序列**（`quest_engine.py:4-10` 头注释原文）。

**推论**：设计不能建立在"调用任务获取协议实时刷新"上；正确形态是
**服务端推送 = 权威 + 本地任务表镜像 + 心跳对账 + 重登兜底**。

### 1.1 任务做完会不会刷新？——会，但刷新来自推送

| 时机 | 消息 | 本地动作 |
|---|---|---|
| 登录（唯一全量） | `S2C_LOAD_TASK(90037)` | 覆盖式重建本地任务表 |
| 新接/服务端追加 | `S2C_ADD_TASK(90365)` | 插入进行中；若正是当前链的下一环 → 从 `WAIT_NEXT` 前进 |
| 进度变化/可交付 | `S2C_UPDATE_TASK(90396)` | 更新 `can_finish`/计数 → 触发"去交付" |
| **完成** | `S2C_FINISH_TASK(90072)` | 从进行中移除 + `done_tasks` 追加；若是链尾 `end_task` → `chain_done` |
| 丢失/被放弃 | `S2C_DROP_TASK(90413)` | 移除；若属于当前链 → 判定"任务丢失"，走恢复阶梯（§3.3） |
| 限次任务（抓鬼每日数） | `S2C_LOAD_TASK_LIMITED(90152)` / `S2C_UPDATE_TASK_LIMITED(90300)` | **覆盖**当日权威计数（别用本地累加） |
| 对话 | `S2C_SHOW_DIALOG(90075)` | 选项里带 `task_index`，用于决定"点哪个选项" |
| 心跳（中控 3s `status`） | `task_index` / `done` / `chain_done` | 只做**对账告警**，不当权威值 |

对应本地字段（`quest_state.py:44/45/59/60/62/63`）：`active_task_index` / `tasks{}` / `done_tasks` / `done_base` / `chain_done` / `chain_task_set`。
解析入口：`msghandle.task_{load,add,update,finish,drop}_handle` → `quest_engine.on_event(:1017)`。

**所以映射表（`task_order` + `task_hints`）只负责"翻译"**：`task_index → 名字 / 接取 NPC / 交付 NPC / 下一步 / 特殊执行器（商店/加点/打怪）`。
它**不参与**"这个任务是否完成"的判定——判定永远是服务端报文（+ `end_task` 比对，`quest_engine.py:1144-1149`）。

**什么时候必须主动对齐**：只有重登（拿新全量）与"心跳对账"两处。丢事件时靠 §3.3 的恢复阶梯兜底。

### 1.2 声明：链路不是固定脚本，拆模块是为了**卡壳定位**

- **任务链 ≠ 固定步骤序列**：链数据（`task_order`/`task_hints`/`npcs`）是**提示表**；真正推进由服务端推送驱动（`ADD/UPDATE/FINISH/DROP_TASK`）。同一段链每次跑的路径、顺序都可能不同。
- **抓鬼/捉鬼这类是"主动接取 + 动态目标"**，不是走固定点位：
  - 要**自己寻路去找任务给予者 NPC 对话接取**（参考实现按链 id 特判：`quest_engine.__start_accept` 只对 `zhuaogui` 生效）；
  - 接取后**鬼/怪/目的地由服务端动态给**：刷鬼图 `ghost_maps`、落点 `ghost_map_pos`（每张图挑一个 NPC 坐标当筋斗云落点）、动态 NPC `S2C_ADD_TASK_DYNAMIC_NPC(90351)`（可增/移/删）、任务怪坐标来自任务属性 `12053/12054`；
  - 抓鬼日常（`daily_ghost`）是一个**循环状态机**（READY→ACCEPT→WAIT_GHOST→NAV→FIGHT→SUBMIT→计数→READY/DONE），**没有 `task_order`**：组装器对这类只给"导航数据"（如 `zhuaogui_nav.json` → 0 任务 + 提示），不给步骤序列。
- **所以模块序列的定位是"骨架 + 排障地图"**：把链路拆成 寻路/移动/跨图/对话/购买/战斗/加点/状态补充/等待，目的是**卡住时能一眼说出卡在哪个模块**、该看哪个数据字段，而不是"这条链没跑"。每步都标了 `source`：`data`（链数据里有）/ `derived`（从 npcs/dijkstra 推导）/ `policy`（机器人端策略，链数据无此字段）——**`policy` 与 `derived` 不代表真实时序**。

**卡壳定位对照表（状态 ↔ 模块 ↔ 先查什么）**

| 机器人状态(`ST_*`) | 对应模块 | 卡住时先看 |
|---|---|---|
| 寻路阶段（NAV 前） | `pathfind` / `move` / `cross_map` | 同图有没有 `map_grids`（A* 网格）；跨图 `dijkstra` 有没有路由；坐标是否落在可走格 |
| `CLICK` / `DIALOG` | `talk` | NPC 有无坐标（`npcs`）还是等动态 NPC(90351)；对话选项是否匹配（指引项/关闭项/跳转目的地） |
| `FIGHT` | `fight` | 目标怪坐标（attr 12054 / 动态 NPC）；回合指令超时（约 30s 重发） |
| `SHOP` | `buy` | `task_hints.shop{npc,item_index,count}` 是否齐；背包/钱够不够 |
| `ALLOC` | `alloc` | 加点标记（`alloc_point`）与服务端是否要求 |
| `WAIT_NEXT` / `WAIT_TASK` | `wait` | 在等服务端 `ADD_TASK`；`next` 是否悬空（本侧组装时会提前报 `plan_error`） |
| `ERROR` / `STUCK_<state>` | 跨模块 | `err_code` / `err_repeat`（同错 ≥3 触发熔断）、日志里最后一条动作 |

## 2. 分层与模块化（谁在哪一侧）

| 层 | 职责 | 落点（本项目 / 参考实现） |
|---|---|---|
| 动作原语 | 走一格、点击 NPC、选对话项、战斗回合、等待、买药、加点 | 机器人端 Python：`robot_path.py`(A*)、`__do_action(walk/click/dialog_click)`、`__teleport_click`、`fight_tester.py`、`__handle_dialog`、`bag_ops.py`、`__schedule/__human_delay` |
| 步骤/提示（数据） | `task_order[]`、`task_hints{executor,…}`、`npcs`、`map_grids/dijkstra` | **本项目 `internal/chainlib`（只搬运、RawMessage 透传）**；执行器注册表在机器人端 `STEP_EXECUTOR_REGISTRY:27` / `__run_executor:984`。⚠️ 抓鬼**不走 task_order**：其导航载荷在发送时**组装**（基座链的 `npcs`/`map_grids`/`dijkstra` + 抓鬼专属的 `ghost_maps`/`ghost_map_pos`，口径同参考实现 `services/chain.py:ghost_nav_payload()`，见 [链数据](../05-运维/链数据.md) §2.1） |
| 编排（中控） | 该跑哪条链（意图）、调度/名额、恢复、可见性 | 本项目新增 `internal/services/intent`（P0）；参考实现 `state.INTENTS` + `intent_restore.py` + `auto_onboard.py` + `ghost_fit.py` |

### 2.1 模块清单（`internal/chainplan`，与参考实现一一对应）

| 模块 | 干什么 | 数据来源 | 参考实现 |
|---|---|---|---|
| `pathfind` | 同图网格 A* | `npcs` 坐标 + `map_grids` | `robot_path.GridPathFinder` |
| `move` | 沿路径移动（分段/拟人化） | 同上 | `quest_engine.__tick_walk` |
| `cross_map` | 跨图跳转 | `dijkstra` 路由 | `__start_next_hop` / `C2S_DIJKSTRA_DESTINATION(80330)` |
| `talk` | 点 NPC 对话（接取/交付） | `catcher_npc` / `thrower_npc` | `__teleport_click` + `__handle_dialog` |
| `buy` | 商店购买 | `task_hints[].shop{npc,item_index,count}` | `shop_purchase` 执行器 |
| `fight` | 战斗（含前置战斗） | `task_hints[].fight_npc{npc_index,npc_name}` | `fight_npc` 执行器 + `fight_tester` |
| `alloc` | 属性加点 | `task_hints[].executor=alloc_point` | `alloc_point` 执行器 |
| `restore` | 状态补充（回血回蓝/补给） | **policy**（机器人端策略，链数据无字段） | `__fight_end_heal` / `__use_heal_item` / `__start_shop` |
| `wait` | 等下一环推送 | `next[]` | 等 `S2C_ADD_TASK(90365)` |

### 2.2 组装顺序与校验规则

每个任务节点展开成：

```
[前置战斗] pathfind → move → fight → restore          （参考实现：先打完再点 catcher，否则剧情不推进）
          pathfind →(cross_map)→ move → talk(accept)   （catcher；无 catcher 且该链允许时改为找 thrower）
          buy / alloc                                  （按 task_hints.executor）
          pathfind →(cross_map)→ move → talk(submit)    （thrower 与 catcher 不同才走）
          wait(next)                                   （等 ADD_TASK）
```

**硬错误（`plan_error`，必须修）**：区间内 `next` 悬空（会卡 `WAIT_NEXT`）、`task_index` 重复、未知 `executor`、`shop_purchase` 缺 `shop.npc`。
**提示（`warnings`）**：`task_order` 为空（只下发 chain_id）、`next` 指向区间外（下一段链）、NPC 无坐标（等动态 NPC 推送 90351）、缺 `item_index`、节点无 catcher/thrower。
**兼容**：`npcs` 坐标同时吃扁平 `[map,x,y]`（真实导出）与嵌套 `[[map,x,y],…]`（模板）；`catcher_npc`/`thrower_npc` 同时吃字符串与数字。

**接口约定（动作模块统一契约）**
- 输入：只读任务上下文（账号/区/链/`task_index`/提示/NPC 坐标）+ 参数；
- 输出：状态迁移（`ST_NAV/ST_CLICK/ST_DIALOG/ST_FIGHT/ST_SHOP/...`）+ 事件（`robot_state`/`task_progress`/`error`）；
- 三条硬性要求：**幂等**（重复执行无副作用）、**可中断**（`stop`/换链时立刻退出）、**超时自检**（不许无限等）。
- 动作模块之间**不互相调用**；组合只发生在执行器/链层。依赖注册表名（`executor`），便于裁剪与热更（参考实现有 `reload_scripts` 命令）。

## 3. 关键点

### 3.1 模块依赖管理
- 依赖单向：动作 → 「协议客户端 + 只读上下文 + 时钟 + 日志」。**写操作只能通过状态机迁移 + 事件**。
- 链数据是外部产物（由游戏任务 XML 生成），字段会漂移 → 继续 `RawMessage` 透传，别做强类型解析（已列入"扩展指南·容易踩的坑"）。
- 契约用测试固定：链数据形状用夹具（`test/fixtures/chains/*.json`）保住"未知字段不丢"。

### 3.2 异常处理（三级 + 超时表）
- **可重试**：网络抖动、走路卡、对话不推进 → 退避重试（本轮不重登）。
- **可恢复**：本地任务表与服务端不一致 → 状态重同步（§3.3）。
- **致命**：接取被拒（通知码 70/71）、账号不可用、连不上 → 上报 + 换号/下线。
- 超时**按状态**设（参考实现 `quest_state.STATE_TIMEOUT_MS:22`）：NAV 10s / CLICK 8s / DIALOG 20s / FIGHT 90s / SHOP 25s / WAIT_TASK 30s；重试上限 `quest_max_retry=3`，超限上报 `STUCK_<state>`。
  一个"总超时"会把"慢"误判成"卡"。
- 中控侧要补的：`error` 事件同码重复（现有 `err_repeat`）→ **熔断/退避**（参考实现：连续 3 次封 600s，最长 1800s）。

### 3.3 恢复阶梯（从最便宜的自愈到最贵的人工/重登）
1. **推送自愈**：等 `ADD_TASK/UPDATE_TASK` 到达即回正常态（`quest_engine.py:1066/1072-1076`）。
2. **重发动作**：`__recover:1919` —— 跨图重发 `C2S_DIJKSTRA_DESTINATION(80330)`、候选 NPC 轮换、位置校准 `force_walk`、`WAIT_NEXT` 无任务 → `__ensure_next_chain_task`。
3. **任务缓存**：抓鬼 `_TASK_CACHE`（30min）优先"原地恢复"，其次才点"放弃捉鬼任务"（`daily_ghost.py:623-679/1507-1533`）。
4. **指令兜底**：`@addtask start_task` 补起点（`__maybe_addtask_start:1495`）、`reset` = `@cleartask + @addtask`（`:3392-3417`）。
5. **重登/换号**：`__need_relogin` → 中控 `_relogin_stuck_account` + `_reghost_later`（冷却 900s、每日 ≤5 次）。
- "任务丢失"的判定要窄（参考实现只在"在线 + `task_index==0` + 非抓鬼"时补拉，且带冷却）。
- **默认不要自动 `@deltask` 跳任务**（参考实现注释明确"默认停链等服务端修"）；跳任务只在明确的坏任务白名单下用，否则会污染服务端任务态。

### 3.4 优先级调度
- 判据（本项目 P0 已实现，`internal/services/intent`）：`等级 ≥ NewbieMaxLevel(默认 31)` 或 `chain_done` → **抓鬼**；`等级 < 31` → **新手链优先**；**等级未知 → 不登记（等上线报一次）**。
- **一个账号同一时刻只有一条链**：机器人端一帧只跑一条（`main_tester.tester` 固定优先级），切链先停另一条（`start_chain` 先 `ghost_stop`、`ghost_start` 先 `stop`）；中控侧上线/选号前再校验一次（`Plan.Conflict`）——**两侧双保险**。
- 抢占语义：抓鬼条件不满足 → 下线换号（不回新手链）；新手链完成 → 立刻补位；**抓鬼名额只由抓鬼侧补**（混补会踩坑）。
- 四个旋钮别混成一个"并发"：`max_online`（并发上限）/ `ghost_limit`（每日次数）/ 登录流水线（batch=5、间隔 1s、防登录风暴）/ `interval_min`（分批节奏）。

## 5. 风险清单

1. **不要把设计建在"主动查询任务"上**（协议不存在）；丢事件只能靠心跳对账/重登发现。
2. **不要在 Go 侧重写链执行**（会与机器人端形成第二/第三套口径）；中控只做意图/调度/恢复/可见性。
3. 阈值口径必须单点配置（本项目 `newbie_max_level` ↔ 机器人端 `start_chain_done_level`），漂移会导致"两边都以为对方该跑"。
4. "任务丢失"判定放宽会引发重复接取/重复打怪 → 判定要窄 + 恢复动作幂等 + 冷却。
5. 自动跳任务（`@deltask`）默认禁用。
6. 重登是核武器：冷却 + 每日上限 + 先存意图（否则恢复时不知道原来在跑什么）。
