# 分层与模块

## 1. 三层部署结构

```
┌─ 浏览器面板 web/ (Vue3 + Vite, dev :5273) ─────────────────────────┐
│  监控大屏 / 任务链 / 运行日志 / 系统信息（多区配置 + 协议映射）      │
└──────────────┬─────────────────────────────────────────────────────┘
               │ HTTP API + WS（vite proxy /api、/ws → :28082）
┌──────────────▼──── 中控 zyctrlcenter（Go 单二进制）────────────────┐
│ main.go            装配 + 启动 + 优雅退出                          │
│ internal/api       HTTP 路由（含 /api/config*）+ WS 广播 + 鉴权     │
│ internal/services/zones   多区配置注册表（服→区）+ 写机器人 config.py│
│ internal/services/event   事件处理（表驱动，带当前区标记）+ 状态轮询 │
│ internal/services/process 机器人进程管理（单进程）                  │
│ internal/state     全局状态容器（机器人行带 zone）                  │
│ internal/store     运行历史（日期级）      internal/logging 应用日志│
│ internal/ctrl      控制通道（TCP :27200，单连接）                   │
└──────────────┬─────────────────────────────────────────────────────┘
               │ 命令下行 / 事件上行（事件带 _zone = 当前区）
┌──────────────▼──── robot_single_robot.exe（唯一一个进程，默认不接管）┐
│  连接中控 :27200；登录哪个区由它的 config.py 决定（切区=改配置+重启）  │
└──────────────┬─────────────────────────────────────────────────────┘
               │ TCP <游戏服 IP>:<区端口，如 47.96.8.240:2400>
               ▼
        游戏服务端（1 服多区）
```

**解耦点**：中控不碰游戏协议。对机器人是 TCP JSON-lines，对前端是 HTTP/WS，两层各自可独立演进。
多区是**配置层能力**（服/区候选 + 切换 + 应用到机器人），运行时保持单进程单通道。

## 2. 包职责与依赖方向

| 层 | 包 | 职责 | 依赖 |
|---|---|---|---|
| 基础 | `internal/config` | 集中配置（端口/路径/开关/鉴权） | 标准库 |
| 基础 | `internal/logging` | 应用日志按日切分 + 历史清理 | 标准库 |
| 基础 | `internal/store` | 运行历史按日切分 + 尾部回读 + 清理 + 熔断归档 | 标准库 |
| 基础 | `internal/state` | 全局状态容器（机器人表/已移除/当前游戏服） | 标准库 |
| 基础 | `internal/wsutil` | 最小 WebSocket 服务端 | 标准库 |
| 通道 | `internal/ctrl` | 控制通道：TCP 单连接、接管、入队、命令下发（事件带当前区标记） | 标准库 |
| 数据 | `internal/chainlib` | 链数据文件加载 + 原样透传 | 标准库 |
| 协议 | `internal/gameproto` | **游戏服协议帧编解码**（[type][pblen][body]、整数/字符串字段、角色列表）；只内置 UTF-8，GBK 明确报错 | 标准库 |
| 服务 | `internal/accountcreate` | **建号**：注册协议 106→104→700；密码随机生成（写回库，无统一密码） | gameproto |
| 服务 | `internal/accountverify` | **账号可用性验证**：直连游戏服跑 100/101/102/300（可选 1000/90132），每账号一条独立连接、批量并发 | gameproto |
| 配置 | `internal/services/zones` | 服/区注册表（增删改/切换/落盘/校验）+ 写机器人 config.py | 标准库 |
| 服务 | `internal/services/event` | 事件表驱动处理、区标记归属、状态轮询、位置合并 | config/store/state/ctrl/logging |
| 服务 | `internal/services/process` | 机器人进程管理（单进程：拉起/停止/重启/探测） | 标准库 |
| 接口 | `internal/api` | 路由、CORS、可选鉴权、WS 广播、协议映射 | 上述全部 |
| 入口 | `main.go` | 装配 + 生命周期 | 上述全部 |

**硬约束**：
1. 基础层不依赖业务层；`services` 不依赖 `api`；禁止循环依赖。
2. 跨模块共享状态一律进 `state`（方法级加锁），不在业务包里建可变全局。
3. 中控只做搬运与记账：链数据原样透传（`chainlib/passthrough.go`），命令原样下发。

## 3. 状态容器边界

`state.Robot` 只放**机器人上报的字段**（协议字段的原样映射 + 中控记账字段 `err_*`/`last_seen`）。
业务状态（定时编排、游荡池、**任务意图**、账号库）**不进 state**——使用方自己在模块里维护
（任务意图已落在 `internal/services/intent`：判据 + 单链互斥，见 [任务链路模块化设计](任务链路模块化设计.md)），
需要展示时由自己的 API 透出（见 [扩展指南](扩展指南.md)）。

## 4. 并发模型

| 组件 | 并发方式 |
|---|---|
| 控制通道 | 一个 accept 循环 + 每连接一个读协程；事件进有缓冲 channel（满时丢弃并记日志） |
| 事件循环 | 单协程消费 channel（顺序处理，天然避免状态竞争） |
| 状态轮询 | 独立协程，3 秒一次（发 `status` + 清理 10 分钟无心跳的陈旧行） |
| WS 广播 | 每客户端独立发送队列（256）；慢客户端直接断开（前端自动重连） |
| 位置推送 | 100ms 合并为 `robot_pos_batch`（大批量时避免逐条广播积压） |
| 状态容器 | `sync.RWMutex`，全部通过方法访问 |
| 日志写入 | 每次追加打开→写→关闭（跨日切换天然安全；Windows 无句柄占用问题） |
