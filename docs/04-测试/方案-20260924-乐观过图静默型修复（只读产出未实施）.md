## 0. TL;DR

- **现象**：`任务 0 换图推送迟迟未到, 无法走向跳转点`（`__do_walk` 等换图分支空转 12 次×2.5s → TASK_STUCK）。两天 error 行 **1286 次**，其中 **A 型 876 次 / 290 号（68%）**。
- **A 型判据**（STUCK 前 60 行窗口）：有 `跳转NPC过图成功`（乐观改图）且**无** `跨图跳转被拒绝`/`回滚乐观过图`。**876/876 全额命中"乐观改图"特征**；857/876 伴随 `前往图N…(寻路)` 并发重规划；**task_index 100% = 0**（纯抓鬼/游荡语境，非任务链）。
- **根因**：乐观改图（本地图=目标图）**与后续某条 route 的起点图（`hop.from_map`）不一致** → `__do_walk` 进"等换图推送"分支 → **这个推送永远不会来**（要么传送静默失败，要么本地/服务端图认知已分叉）→ 12 次后 TASK_STUCK。**不是"推送慢"**。
- **推荐修复**：**不改成图时机**（09-22 的"主动同步"必须保留——服务端推送会丢），改为**在 `__do_walk` 等待分支识别"乐观矛盾"**：三条件命中 → 回滚本地到服务端确认图 + 拉黑可疑跳 + 复用 `__replan_after_bad_hop` 换路。窄条件、零接口变更、不误伤"真·推送延迟"。
- **影响面**：跳转 NPC 过图全量两天 **41753 次 / 530 号**（正常路径不经过本分支）；本修复只作用于"等待分支 + 乐观矛盾"（A 型 876 次/290 号），对正常过图零介入。

## 2. 根因（逐帧还原）

### 2.1 铁证：robot0001013@xy3.com（09-23，ts 1790136835-6906）

```
6835 STATE mapid=609
6836 跨图 609→12 经 2 个跳转点                    ← route=[609→11(点13115), 11→12(dest13)]
6853 点击跳转NPC 13115（有来有去）
6854 对话打开 npc=13115 选项 ['长安东市集', '离开']
6854 跳转NPC过图成功 → 地图 11 (主动同步)          ← 乐观改图 11 + pop dest 175（保留，不动）
6856 走路: (2074,1322) → (76,541)                 ← 以图 11 网格寻路（dest 13 的坐标）
6874 到达跳转点(76,541), 发 DESTINATION 13
6875 发现鬼 1461322（在图10）, 前往图10 经 1 个跳转点 ← 抓鬼并发重规划, 用服务端图 609 作起点
6906 TASK_STUCK: 任务 0 换图推送迟迟未到             ← 32s 后（≈12×2.5s+开销）
```

关键：13115 的传送**静默未生效**（无 1116、无被拒回执、服务端不换图），而本地已乐观在 11 → 后续 route 每条 hop 的 from_map（609/11 两套）与本地图总有一边对不上 → 落入等待分支。

### 2.2 对照：robot0005231@xy3.com 同日"成功样本"（可证乐观改图本身没问题）

```
5336 跳转NPC过图成功 → 地图 11 (主动同步)
5356 到达跳转点(76,541), 发 DESTINATION 13
5356 跨图跳转成功 → 地图 12        ← 服务端接受了后续跳转（说明 13115 传送有效）
```
→ **乐观改图机制本身上作正常**；失败样本里"传送静默/图认知分叉"才是关键变量。

### 2.3 A 型"等待分支"入口的同一性

`__do_walk` 的判定：`hop != None and m_mapid != hop.from_map` → 等待"换图推送"。
- 正常过图（含推送丢失但服务端真换图，09-22 场景）：下一跳 `from_map == 乐观图 == m_mapid` → **不进分支**；
- 失败样本：route 起点（srv 图/旧图）与乐观图不一致 → **进分支 → 等一个不会来的推送**。

## 3. 方案对比

| | 方案一：乐观过图加"短确认窗口"（我最初方向，**已弃**） | **方案二（推荐）：等待分支识别"乐观矛盾"** |
|---|---|---|
| 思路 | 点中目的地后不立即改图，等 `S2C_CHANGE_MAP` 或 N 秒 | 保留立即改图；在"等换图"分支里识别"乐观态矛盾"并回滚换路 |
| 致命问题 | **与 09-22 修复冲突**：服务端推送会丢（7001145 周德快案例），等推送=倒退；且"失败/丢失"本地不可区分，固定窗口必然两头误伤（见 §4） | 不改过图时机与推送依赖；只处理"等待分支"这一异常路径 |
| 触发条件 | 每次跳转 NPC 过图 | `m_mapid_optimistic != 0` **且** `hop.from_map == m_srv_mapid` **且** `m_mapid == m_mapid_optimistic`（三条件同时） |
| 影响面 | 所有链路所有跳转 NPC（41753 次/两天） | 只命中"等待分支里的乐观矛盾"（A 型 876 次/两天） |
| 依赖 | 需定义窗口时长、双计时、与 09-22 兼容层 | 复用已交付的 `__replan_after_bad_hop` / `__hop_blacklist` / `last_hop_done`，+1 个纯判定函数 |

### 方案二的动作（拟）

在 `__do_walk` 的"跳转点走路前校验"段、`walk_hop_wait_count += 1` **之前**插入：

```python
# 2026-09-24 A 型: 乐观图与"本跳起点图"矛盾 —— 该"换图推送"永远不会来
_opt = int(getattr(robot_object, "m_mapid_optimistic", 0) or 0)
_srv = int(getattr(robot_object, "m_srv_mapid", 0) or 0)
if _opt and _srv and int(hop.get("from_map", 0) or 0) == _srv \
        and int(robot_object.m_mapid or 0) == _opt:
    # 回滚到服务端确认图 + 拉黑"把号带到乐观图的可疑跳" + 换路重规划
    _lh = getattr(quest, "last_hop_done", None)
    _note = "乐观过图未被服务端接受(本地 %d/服务端 %d, 本跳属 %d)" % (
        int(robot_object.m_mapid or 0), _srv, int(hop.get("from_map", 0) or 0))
    if isinstance(_lh, dict) and int(_lh.get("target_map", 0) or 0) == _opt:
        __hop_blacklist(robot_object, quest, _lh)
        _note += "; 拉黑跳转点 %s(地图 %s)" % (_lh.get("destination_index"), _lh.get("_from_map"))
    robot_object.m_mapid = _srv
    robot_object.m_mapid_optimistic = 0
    quest.walk_target = None
    quest.path_points = []
    __replan_after_bad_hop(robot_object, quest, hop.get("destination_index"), _note)
    return 0
```

顺序建议：置于本次已交付的 P7（`retry>0`）**之前**（乐观回滚携带更多信息；两者条件互斥——B 型回滚时乐观标记已被清）。
新日志（验收锚点）：`换路重规划(destination N, 免费优先): 乐观过图未被服务端接受(...)` + `拉黑跳转点`。

## 4. "短确认窗口时长"论证（team-lead 指定要的依据；结论=不采用固定窗口）

09-24 全量统计"跳转 NPC 过图确认延迟"（`跳转NPC过图成功 → 地图 X` 到后续首个 `robot_state(mapid=X)`）：

- 样本 9656 次；60s 内出现目标图 state：4661（48%）、未出现：4995（52%）
  （**口径局限**：机器人可能很快又离开目标图，故"未出现"含"快速再离开"，是确认率的下限）
- 可观测延迟：p50=5s、p90=43s、p99=351s；分桶 `<=3s 5.2% / 4-6s 57.8% / 7-10s 4.8% / 11-20s 9.4% / 21-40s 3.9% / >40s 19.0%`
- **判读**：正常确认集中在 **4-6s**（robot_state 周期 3s 的分辨率下=下一拍），但**长尾 >40s 占 19% 且含"永不确认"**。
  - 若窗口取小（≤6s）：**19% 长尾被误判失败** → 误伤（白回滚+拉黑）；
  - 若窗口取大（≥40s）：**静默型要等 40s 才被救**，与现状（30s 空转）无本质增益；
  - 且"失败"与"推送丢失"在本地**不可区分**——固定窗口无法同时满足"不误伤丢失"与"及时救静默"。
- **结论**：放弃"时长窗口"路线；采用方案二（用**状态矛盾**判失败，而非时间）。

## 5. 影响面与风险

- **分母**：`跳转NPC过图成功` 两天 41753 次 / 530 号（约全车队）。
- **命中面**：等待分支 + 三条件矛盾 ≈ A 型 876 次/290 号（两天）。**只在这时改变行为**：由"空转 30s → TASK_STUCK（重登）"变为"回滚 0.1s + 拉黑 + 重规划"。
- **误伤面分析**：
  - "乐观成功"的正常样本（如 5231 §2.2）：下一跳 from_map=乐观图 → **不进等待分支** → 不触发；
  - "推送丢失但服务端已换图"（09-22 场景）：同样不进等待分支（本地乐观图与服务端一致）；
  - **边缘场景**：`hop.from_map == m_srv_mapid` 且本地=乐观图 —— 这**只可能**出现在"乐观图≠srv 图"的时刻（=乐观未确认），此时回滚到 srv 图并重规划是**唯一自洽**的选择；即使该跳前一刻其实"传送已成功但推送全丢"（无法排除），回滚后的重规划也会从 srv 图再走一遍（有拉黑 10 分钟防热循环），**不劣于现状（30s 空转+STUCK+重登）**。
- **风险点**：① 改动落在 `__do_walk`（全链路共用的高频函数）——用"三条件同时"收窄到极窄面；② `last_hop_done` 可能是更早的 npc_jumper（条件里限定 `target_map == 乐观图` 防误拉黑）；③ 与 daily_ghost 的"前往图"重规划**不改变其行为**（旧 route 由本修复清理，daily_ghost 的下一轮 tick 会按新图重规划）。
