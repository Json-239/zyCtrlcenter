# 分析：批量上线（`POST /api/robots/batch`）池容量闸（2026-09-23 P2）

> 只读分析 + 修复记录。背景与三池口径见 [分析-20260923-抓鬼分配逻辑](分析-20260923-抓鬼分配逻辑.md)。
> 代码位置：`internal/api/handlers_accounts.go`（`handleRobotsBatch` / `batchOnline` / `batchOnlineBudgetOf`）、
> `internal/api/api.go`（`onlineInflight`）；测试 `test/api/batch_pool_test.go`（8 例）。

## 一、真实路径（修复前）

```
POST /api/robots/batch {action:"online", accounts:[...]}
  → handleRobotsBatch（解析 limit/chunk/interval/only_usable）
  → batchOnline：过滤已在线 → sendOnlineChunks 分批下发 robot_manage add（chunk=10, 间隔 500ms）
  → 机器人端 add → 号上线（IDLE，无任务）
```

- 这条通路**不经 autotask 的池配额、不经 waterline 的水位、不经 roampool 的游荡池**，
  与"下任务"的通道（`/api/start`(auto)、RESTORE 补发、autotask 补号）完全解耦。
- 数量上限只有两个：`limit`（仅对"自动选号"生效，默认 20、硬上限 500）与显式勾选集合本身
  （无上限）。现场实证：10:48 / 10:55 / 12:04 三次手动批量上线 **106 / 105 / 100** 个号
  （`type=api action=robots_batch requested=106/105/100`）。

## 二、"无约束"的具体表现与量化

| 表现 | 机制 | 现场证据 |
|---|---|---|
| 上线总数可超"在线总数"目标 | 一次 add 100~200 个号，直接叠加在水位 target（230）之上 | 230 在线时三次各 100+ 号 |
| 给超编通道供料 | 上线号按意图进入 `/api/start`(auto)、RESTORE 补发的可派集合 → 与两条通道叠加把抓鬼推到 218（目标 100） | `start_auto` 225~227 个 ghost_start；RESTORE 单条最多 87 个 |
| 游荡池被兜底冲垮 | 上线后空闲号 90s 被机器人端 `auto_roam` 兜底拉去游荡 → 游荡数可远超游荡 target（130） | 13:10 游荡 200 → 1（被 ghost_start 抢回） |
| 与水位器空转往返 | 超水位的号被水位器压下 → 又被补号通道/兜底拉起；团队已明确"不要用下线待命" | 三池交互分析（20260922）回收↔重派同型 |

关键：**"无约束"不在"上线"本身，而在"上线数不受任何总量口径约束"** —— 上线的号一定会上工
（被抓鬼/新手链吸收，或游荡兜底），所以"能上多少"必须与"三池能承载多少"对齐。

## 三、口径选择（方案论证）

候选（team-lead 提供）：① 上线后按池缺口归池并记账；② 超出三池目标总和的部分转待命/排队；
③ 给批量接口加可选"目标池/上限"参数。取舍：

- **用"总量"而不是"按池归口"**：号在池间是流动的（抓鬼满额转游荡、任务池缺人回收游荡号、
  满额只离线转游荡），按池硬分会让"该去游荡的满额号"上不了线；总量口径同时覆盖"水位
  target（在线总数，用户口径）"与"Σ 三池 target（抓鬼/新手/游荡余量）"两个用户可解释的数。
- **超出部分"不上线"而不是"待命"**：团队口径明确否掉"下线待命"（水位器会把压掉的号补回来，
  与 auto_roam 往返空转）；"后台自动排队"也不做 —— 它与水位器"按目标补号"职责重叠，
  且内存队列重启即丢。被拦的号作为 `queued` 回带给调用方，等池内收工或调大目标。
- **不做"目标池"参数**：号池归属由 `poolOf`（等级/毕业状态）唯一定义，用户指定目标池会与
  意图判据漂移；"上线后派什么活"是 `/api/start`(auto) 的职责（它已有池配额截断）。

落地口径（`batchOnlineBudgetOf`）：

```
额度 allow = max(0, cap - online)
cap    = 水位 target（水位 enabled 且 target>0 时；用户口径的"在线总数"）
       = 否则 Σ 三池 target（抓鬼/新手/游荡中 >0 的）
       = 都没配 → 0 → 不约束（保持旧行为）
online = 当前区在线数（本地快照） + onlineInflight（已下发 add、还没上线的在途号，TTL 120s）
```

超出额度的号：**本次不上线**（不改变任何状态，不标记移除/暂停），`queued` 回带 + 日志；
`force: true` 跳过闸门（人工强制上线/排障）。

## 四、四池影响评估

| 池 | 影响 | 说明 |
|---|---|---|
| **ghost 抓鬼** | 少一个"超编供料入口" | 本闸只约束"上线规模"，不改变派任务配额（`poolQuota` 的"在跑+在途"照旧）；抓鬼超编的另两条通道（start auto / RESTORE）已在 P0/P1 修复 |
| **newbie 新手** | 上线规模与总量对齐 | 新手池 target>0 即计入容量（不看 enabled，因为"停用"只表示不自动派活，不表示不能上线） |
| **roam 游荡** | 不再被"上线→auto_roam 兜底"冲爆 | 游荡 target 计入回退容量；游荡池自身回收/补位逻辑不受影响（本闸不管已在线号） |
| **hatch 孵化** | 无独立容量、不受改动 | 孵化号本来就在抓鬼/新手池里（游荡孵化），只受同一总量约束；孵化链路（hatch_start/stop/到期）零改动 |

交互：
- **水位保持器**：容量优先读水位 target（口径统一，面板看到的"在线总数"就是闸门用的数）；
  水位自己的补号通道（`waterlineOnline`）**不**走本闸（它有 target/死区/在途），互不干扰。
- **超编回收 / 满额转游荡 / 恢复引擎**：本闸只拦"新增上线"，不动运行中的号 → 不引入新的
  回收↔重派往返（与 P1 的超编收敛方向一致）。

## 六、已知取舍 / 残余

1. **面板（web/）不带 force**（本轮纪律：不改前端）→ 容量满时面板"批量上线"会被拦，
   提示文案会告诉用户怎么调（调大 target / 用带 force 的 API）。若要面板内可强制，
   后续加一个复选框（`force` 字段已就绪）。
2. 快照 `Online` 的时效性：重启瞬间残留在线（心跳未超时）会让额度偏紧 → 可 force；
   反向（刚 add 未上线）由 `onlineInflight`（TTL 120s）兜底。
3. 水位 `allow_local=false`（服务端口径含真人）时，"已占"用本地在线数与它不同源 →
   额度偏松（保护变弱，不有害；水位器仍会按自己的口径压号）。生产 `allow_local=true`，口径一致。
4. 未配置水位/三池的环境 → 不约束（旧行为）。
