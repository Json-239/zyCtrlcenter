## 1. 现象与 5 号样本（20:17 实测）

用户口径："抓鬼还是存在卡住问题，但（号）还是在运行的，面板显示卡住。"

主控核实（在线 48 个号）：

| 判据 | 实测 |
|---|---|
| 带 `err_code` 的号 | **5 个** |
| 其中 `state` 为活跃态（NAV / WAIT_GHOST） | **5 个（全部）** |
| 其中 `ghost.enabled=true`（在正常抓鬼） | **5 个（全部）** |
| `state=ERROR` 的真卡住号 | **0 个** |
| `err_code` 明细 | `NO_LEGAL_ROUTE`×4、`TASK_STUCK`×1（`err_repeat` 1~3，全是历史旧错） |

即：**面板"卡住"计数（5）与真实卡住数（0）完全脱节**——所有被报"卡住"的号都在正常抓鬼。

## 2. 根因链条（4 环，逐环复核源码）

```
① 机器人端 quest_state.mark_error()：last_error 一旦设置，永不失效/永不清理
        （原 L132-138，只有写、没有清）
                ↓
② error_fields()（心跳/状态上报唯一口径，quest_engine L154 / L3702 调用）：
        永远返回旧 err_code —— 号恢复后心跳仍带它
                ↓
③ 中控 internal/services/event/event.go L378-383：
        if err_code != "" → 写入(一直写)
        else if state != "ERROR" → 才清（只有"机器人不带"时才清）
        → 机器人一直带 → 永远清不掉
                ↓
④ 面板 Dashboard.vue："卡住" chip = r.err_code 非空（原 L55/L69）
        → 历史错误被当"卡住"，永久误报
```

关键代码（修复前）：

```python
# quest_state.py（修复前）
def mark_error(self, code, msg=""):
    self.last_error = {"code": code or "", "msg": (msg or "")[:200],
        "ts": int(time.time() * 1000)}
    return self.last_error

def error_fields(self):
    e = self.last_error or {}
    return e.get("code", "") or "", int(e.get("ts", 0) or 0)   # 无时效：永远返回
```

```go
// event.go L378-383（本次未改，保持现状）
if code := str(st, "err_code"); code != "" {
    r.ErrCode = code
    r.ErrTS = float64(toInt(st["err_ts"])) / 1000.0
} else if !strings.EqualFold(str(st, "state"), "ERROR") {
    r.ErrCode, r.ErrTS, r.ErrRepeat = "", 0, 0
}
```

`mark_error` 的出口覆盖看门狗超时（`STUCK_*`）、`TASK_STUCK`、`NO_LEGAL_ROUTE`、
`SHOP_NO_ROUTE`、`NAV_NO_FINAL`、前置战斗失败等——这些出口多数**不能立即停链**
（比如 `NO_LEGAL_ROUTE` 之后看门狗会重试、重规划成功后继续抓鬼），所以"出错 → 恢复"
是常态，而旧实现没有任何"恢复即清"的口径。

## 3. 修复设计

原则：**Python 端根治（停上报 + 恢复即清），前端显示兜底（"卡住"必须=ERROR 态）**。
中控 Go 侧**不动**——Python 修好后机器人不再常带 err_code，中控既有的
"不带错误且非 ERROR → 清"逻辑自然生效（跨中控重启也成立）。

### 3.1 机器人端：错误上报加时效（`quest_state.py`，主线）

```python
# L35-40 新常量（可配）
ERROR_TTL_MS = 3 * 60 * 1000   # "最近错误"上报时效: 超时仅停上报, last_error 本体保留

# L147-151 新方法
def clear_error(self):
    self.last_error = None

# L153-167 error_fields 加上时效判定（getattr 兜底热更旧实例）
code = e.get("code", "") or ""
ts = int(e.get("ts", 0) or 0)
if not code:
    return "", 0
if (time.time() * 1000) - ts > ERROR_TTL_MS:
    return "", 0     # 超时不再随心跳/状态上报（本体保留供本地诊断）
return code, ts
```

- **保留** `last_error` 本体（本地诊断/diag.log 不受影响），只改**上报口径**；
- 3 分钟：大于正常看门狗重试周期（最长 FIGHT 90s），又是面板可接受的"冷淡化"时间；
  常量可调，改一处即可。

### 3.2 机器人端：恢复即清（3 个语义最稳的恢复点）

新增 helper（`quest_engine.py` L846-861，getattr 兜底）：热更 `importlib.reload` 后
**已实例化的旧 QuestState 保留旧类**（`client.py` L242 注释即此坑），直接
`quest.clear_error()` 会对旧实例 AttributeError，故统一走：

```python
def _clear_recent_error(quest):

```

## 6. 部署后须知（给主控）

1. **热更即可生效，无需重启**（`importlib.reload` 加载的是**线上**文件，已同步 + diff 为空 + py_compile 通过）；本文件改动**未热更、未重启**，由主控执行；
2. **存量误报自动消失，不需要人工重登**：
   - 5 个样本号的 `last_error.ts` 都在数分钟前 → 热更后第一次心跳 `error_fields` 即返回空 → 中控走 `else if 非 ERROR` 分支清掉 `ErrCode` → 面板"卡住"归零；
   - 若某号恰好 3 分钟内刚出过错，最多 TTL（3 分钟）内自动消失；
3. **观察面板"卡住"数应与 `state=ERROR` 数一致**：
   - 推荐核对方式：`卡住` chip 计数 vs 列表里 state 为"出错"的行数；两者应恒等（前端同一判据 `isStuck`）；
   - 若仍不一致，说明前端未刷新（`npm run build` 产物需部署）或浏览器缓存旧 JS；
4. **行内"曾出错"（dim）是预期新现象**：正在运行、且 TTL 内有过历史错误的号会短暂显示弱化标签，属信息展示（title 里有错误码/信息），不计入"卡住"；超过 3 分钟自动消失；
5. **中控侧无需任何操作**：Go 清逻辑保持现状，Python 停带 err_code 后自然能清；`err_repeat` 熔断计数同样会在心跳清除时归零。

## 7. 残留风险与边界

1. **正在持续的错误仍会被看到**：`mark_error` 的出口每次失败都会刷新 `ts`，只要错误在 3 分钟内发生过，心跳仍带 err_code（面板行内"曾出错" + `state=ERROR` 时红色"卡住"），不会因为 TTL/clear 而掩盖**持续**故障；`clear_error` 只挂在"确实有进展"的 3 个恢复点上；
2. **`state=ERROR` 的真卡住仍按原流程处理**：`STUCK_*`/`TASK_STUCK` 后 `set_state(ST_ERROR)`，等中控 reset/stop；前端"卡住"=这类号——语义没有放松；
3. **TTL=3 分钟是折中值**：面板对"出错后已恢复 3 分钟以上"的号不再保留错误提示（本地 diag.log 与中控事件流仍可回溯）；如需要更长提示时间，改 `ERROR_TTL_MS` 一处即可；
4. **其它展示面**：`MapView.vue` 详情"最近错误"未改（历史信息语义）；`onlyFailed`（只看卡住的）已随新判据收敛到 ERROR 态；
5. **前置依赖**：热更需覆盖 3 个 py（quest_state / quest_engine / daily_ghost）；前端需重新 `npm run build` 并部署 dist（本次已 build，未部署）。
