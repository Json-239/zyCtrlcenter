## 2. 根因路径推演

### 2.1 主循环：`dialog_open` 挂着 = 号被钉死

`quest_engine.py` 的 tick 入口 `tester()`（3057 行）中，顺序是：

```python
3181:  if quest.pending != None:          # 待办动作：到点执行
3185:      quest.pending = None
3186:      return __do_action(...)
3188:  if quest.dialog_open:              # ← 对话挂着 → 永久 return 0
3189:      return 0
3191:  # 看门狗（超时重试/上报 STUCK_*）
```

**关键**：`dialog_open` 检查（3188）在看门狗（3191）**之前** —— 只要 `dialog_open` 是 `True`，
本 tick 直接返回，看门狗不复位也不上报 → 现场"无 err_code、日志停止、无任何兜底"完全吻合。

### 2.2 `show_dialog` 分支的守卫让清理不可达

修改前（原 1180-1193 行）：

```python
elif event_name == "show_dialog":
    quest.dialog = data
    quest.dialog_open = True                       # ← 无条件置 True
    ...
    quest.set_state(quest_state.ST_DIALOG)
    __emit(... "对话打开: ..." ...)
    __emit_state(...)
    if quest.pending == None:                      # ← 守卫：pending 非空时
        __handle_dialog(robot_object, quest, data) #    __handle_dialog 根本不被调用
```

而"零选项空对话主动清态"（2026-09-21 早上加的那段）只写在 `__handle_dialog` 内部
（`if npc_id == 0:` 块内的 `if len(option_list) == 0:`，现 `quest_engine.py:623-631`）：

```python
    if npc_id == 0:
        ...
        if len(option_list) == 0:                  # 唯一处理零选项的地方
            __emit(... "系统空对话(npc=0, 0 选项): 无可点项, 主动清对话态恢复" ...)
            quest.dialog_open = False
            quest.dialog = None
            quest.set_state(ST_WAIT_NEXT if quest.active else ST_IDLE)
            __emit_state(...)
            return
```

**`quest.pending != None` ⇒ `__handle_dialog` 不被调用 ⇒ 零选项清理永远跑不到 ⇒ `dialog_open` 永远为 True ⇒ 号一动不动。**

调用关系（修复前）：

```
S2C_SHOW_DIALOG(零选项, npc=0)
  └─ handle_quest_event → show_dialog 分支（1182）
       ├─ dialog_open = True / set_state(DIALOG) / 日志 / __emit_state
       └─ if quest.pending == None:  ── pending 非空（现场为 True）──► ✗ 不进入
                                          └─ __handle_dialog（562）
                                               └─ npc_id==0 → 623 零选项清理（唯一入口）✗ 不可达
```

### 2.3 为什么 `pending` 恰好非空（现场路径）

`__handle_dialog` 的引导对话分支（npc=0，命中"直接领取/续领/双倍"类选项，562-588 行）会：

```python
__schedule(quest, {"type": "dialog_click", "at_ms": __now_ms() + __human_delay(400), ...})
# __schedule 即 quest.pending = p（177-178 行）
quest.dialog_open = False
quest.dialog = None
__emit_state(...)
return
```

即：点掉"直接领取（双倍）"后，**`pending` = 一个 400ms 后才执行的 `dialog_click`**（拟人化延迟）。
同一秒服务端又推来"零选项空对话" → 走到 2.2 的守卫时 `pending` 仍非空 → 清理被挡住。

之后：

- 400ms 到点 → 3181-3186 执行这条 `dialog_click`（点的是已不存在的选项，无效）→ `pending` 清空；
- 但 `dialog_open` 仍是 `True` → 3188 每 tick 直接 return → **日志彻底停止、看门狗不跑、无 STUCK 上报**。

### 2.4 为什么这次没有兜底

- 早上加清理后，同类卡死曾被"补发 `ghost_start` → daily_ghost 30 秒兜底"间接化解；
- 现场这批号 **`ghost.enabled=false`** → daily_ghost tick 不跑 → 该兜底不存在；
- `stuck_count=3` 是中控侧 churn 防护（当日卡死达上限不再自动重登），也不会再救。

## 3. 修复内容（最小、安全）

把"零选项空对话"的清理**前置到 pending 守卫之前**，清理动作与 `__handle_dialog` 内原修复
**逐行一致**（`tools/quest_dialog_pending_selftest.py` 静态断言 S2 逐行比对证明，不引入新语义）：

```diff
 	elif event_name == "show_dialog":
 		quest.dialog = data
 		quest.dialog_open = True
 		...
 		__emit_state(robot_object, quest)
+		# 2026-09-21r2 修复(生产: 48/101 个号重登后卡 DIALOG 一动不动 ...)
+		# 现场路径: 领双引导对话点"直接领取(双倍)"后 __schedule(dialog_click, +400ms)
+		# 使 pending 非空, 同一秒服务端又推这个零选项空对话 → 守卫挡住清理; 动作到点
+		# 执行后 pending 清空, 但 dialog_open 无人清 → 永久卡死。
+		# 清理动作与 __handle_dialog 内 2026-09-21 修复完全一致(不引入新语义)。
+		if data[2] == 0 and len(data[5]) == 0:
+			__emit(robot_object, {"type": "log", "level": "warn",
+				"msg": "系统空对话(npc=0, 0 选项): 无可点项, 主动清对话态恢复(前置清理)"})

+				else quest_state.ST_IDLE)
```

要点：

- 索引口径与 `__handle_dialog` 一致：`data = [escapable, story_mode, npc_id, content, task_index, options]`，
  故 npc 用 `data[2]`、选项用 `data[5]`；
- 日志文案加"(前置清理)"后缀，便于现场区分是本分支还是原路径清的态（行为相同）；
- `__handle_dialog` 内原清理块**保留**（`quest_engine.py:623-631`，补 1 行交叉注释），
  `pending == None` 时它是等价路径；
- **未碰** `daily_ghost.py`（另一条链路刚修过）、Go 侧、`deploy/single_robot`（py 参考实现）。

修改后行号：前置清理 `quest_engine.py:1204-1212`，pending 守卫 `1213-1214`。
