| 指标 | 值 | 来源 |

| 在线（握手口径） | 230 | `/api/status.counts` |

- 230 = 218（抓鬼）+ 13（游荡）− 1（重叠号 robot0001045）。
- `pools.ghost.running` 与 `/api/status` 中 `ghost.enabled=true` 的号数完全一致 →
  **"218"= 当前活跃抓鬼会话数**（机器人上报口径，不是"池子派了多少"）。
- 状态分布（218 内）：WAIT_GHOST 101 / FIGHT 60 / NAV 30 / SUBMIT 12 / READY 10 / WAIT_NEXT 1 / IDLE 2 →
  绝大部分是真在跑，**不是脏状态堆出来的虚数**。
- 语义结论：**在线号里"没在游荡的"几乎全在抓鬼**（218/230），而业务口径是"抓鬼 100 + 游荡 ≈ 余量"。

## 二、218 是怎么形成的（时间线，均有日志/data 证据）

今天的核心事件（皆为已发生事实）：

| 时间 | 事件 | 证据 |
|---|---|---|
| 10:41–13:00 | 机器人进程重启 **11 次**（崩溃/换 zy 版/重拉） | `[PROC] 机器人进程退出/已启动` |
| 10:48 / 10:55 / 12:04 | **手动批量上线** 106 / 105 / 100 个号 | `type=api action=robots_batch requested=106/105/100` |
| **11:49:55 / 13:10:11** | **面板"启动(自动分配)"全量下发：231 个号 → 227 / 225 个 ghost_start** | `type=api action=start_auto accounts=231 assignments.ghost_start=227/225` |
| 10:55 / 11:51 / 12:04–12:13 | **恢复引擎批量补发 ghost_start**：107 / 125 / 220 个号次 | `[RESTORE] … 补发 ghost_start`，单条最多 76（10:55:23）、87（11:51:33）、60（12:04:39）个号 |
| 全天 | autotask 补号 120 号次（每轮 1–10，有 target-cur 限幅） | `[AUTOTASK] 抓鬼 挑中/已下发` |
| 全天 | reghost 重登补发 283 次（每次 1 个号，无池闸） | `[REGHOST] … 需要重登恢复` |

形成路径（自洽闭环）：

1. **触发**：批量上线（robots_batch 105/100）或机器人进程重启 → 大量号回到"在线 + IDLE、无活跃会话"。
2. **放大 A（最大单点）**：`/api/start`（auto）**按意图全量派发**，231 个号里 225–227 个直接 ghost_start，
   不受 `target=100` 约束 → 抓鬼会话量级一次到 200+（对应 11:51 的 250 次、13:10 的 414 次"抓鬼启动"；
   13:10 游荡数从 200 掉到 1，正是这批 ghost_start 把游荡号抢回抓鬼）。
3. **放大 B**：RESTORE 每 5 秒一轮，把"在线 + 意图=ghost + 没在跑"的号**全部合并成一条命令**下发，
   **单轮无批量上限**；其池闸（`poolAllowsDispatch`）只看补发瞬间的活跃会话数（无 in-flight 记账，
   新上线号会话尚未建立 → deficit 仍为 100）→ 放行。10:55 一条 76 个、11:51 一条 87 个即此类。
4. **无收敛**：没有任何模块把超编号移出抓鬼（见下）。

## 三、根因（分级 + 代码位置）

### P0-1 `/api/start`(auto) 无池配额 — 抓鬼量级的直接来源
`internal/api/handlers.go:456` `startAuto()`：`toGhost` 只受等级门槛过滤，**不看 target/running/缺口**；
231 个号一次全派。11:49:55 与 13:10:11 两次调用直接把抓鬼推到 200+。
> 建议：ghost 分组按 `max(0, poolTarget - running - inflight)` 截断，超出部分回带原因
> （或降级为 `random_walk` 游荡），并在接口返回里给出 `skipped_by_pool` 列表。

### P0-2 RESTORE 补发无批量上限 + 闸门无 in-flight 记账
- `internal/services/restorer/restorer.go:208` `TickForce`：产出 Action 数量无上限（按意图全量）。
- `internal/api/autotask.go:159` `poolAllowsDispatch()`：用 `st.Deficit`（= target − 当前活跃会话数）判断，
  **补发瞬间会话未建立 → 判为"缺人"**；且无"已派未确认"计数，同批号可被反复派。
> 建议：① `restorer` 增加单轮上限（壳层传 `min(deficit, 5)`）；② `autotask.go` 增加 in-flight 表
> （补发即记账，`GhostActive()` 或 TTL 120s 后清除），闸门改为 `deficit - inflight <= 0 → 不补`。

### P1 抓鬼池超编无收敛 / 三池无再平衡
- `internal/services/autotask/autotask.go:335`：`cur >= TargetOnline` 只是"暂不补"，**没有超编处理**。
- `internal/services/roampool/roampool.go:604` `Tick` 判决顺序只有两条：缺人→回收游荡号；游荡不足→派空闲号。
  **超编（deficit=-118）时不动作**；补位只挑 `Idle` 号，而抓鬼中的号不是 Idle → 永远拿不到号。
- 结果：游荡池长期 13/100，`last_action` 报"差 87 个，但没有空闲号可派（空闲 0）"。
> 建议：roampool 加第三条分支——`deficit < -threshold` 且 `running(游荡) < target` 时，
> 从"抓鬼中且未满额、等级达标"的号里挑 `min(max_step, 超编数)` 个下发 `random_walk`
> （机器人端 random_walk 会自行停抓鬼，互斥已有实现）。

### P2 目标口径不对齐
`waterline.target=230`，而抓鬼 100 + 游荡 100 = 200 → **30 个号无归属**，
只能靠机器人端"空闲 90s 自动游荡"兜底；一旦被 /api/start 全量吃满就无兜底可言。
> 建议：水位 target 调 200，或游荡 target 按"余量"口径上调（与用户"抓鬼100+游荡=余量"一致）。

### 次要
- `internal/api/autotask.go:79` `ReghostDeps.Launch` 直连 `LaunchTask`，不过池闸（每次 1 个号，影响小；
  建议只把它计入 P0-2 的 in-flight，不拦）。
- `agents` 侧无问题；机器人端"满额转游荡"（596 次/日）工作正常，不在 218 之列。

## 四、影响与结论

- **是设计缺陷，不是统计口径问题**：抓鬼池只有"下限（补到 100）"没有"上限（超了就收）"，
  且同时存在两条**无配额**的派发通道（`/api/start` 全量、RESTORE 全量）+ 一个批量上线入口（robots_batch）。
  三池的目标（100/100）与水位（230）互不约束，无任何模块对"总数 230 如何分给三池"负责。
- 直接代价：游荡池长期缺员 87（游荡产出/暗雷/孵化机会被挤掉）；单 IP 218 号同时抓鬼，
  钟馗点是全服共享 NPC，存在服务端压力/风控风险。
- 抓鬼本身没坏（FIGHT/NAV 状态正常、满额转游荡正常），**坏的是"谁来决定派多少"**。
