# 分析-20260928 每日/登陆/在线/等级奖励补领（储备金宝箱没领的根因与方案）

用户口径："每日奖励和登录奖励都有送储备金宝箱，是没有领取吗，储备金怎么可能会不够用这肯定不对"

结论：**属实。四个奖励系统（每日/登陆/在线/等级）机器人端从未领取**；机器人端只领了"丰富奖励"里的每日福利包
（`daily_ghost.py` welfare_tick：开元通宝/经验/储备金/虎符 5 项，可领的只有储备金那一项）。
ENCOURAGE 系列协议在 `protocol3.py` 未注册 FORMAT_MC（发不出），也没有任何实现。

服务端为只读副本 `F:/ZyBin/xm/2d-xiyou-server`（下文 file:line 均指该副本）。

## 二、四系统领取条件与节奏（逐一）

### 1) 每日奖励（everyday）
- 处理器：`encourage_dispatcher.py:75-96` `dispatch_accept_everyday_encourage`。
- 门槛：① `check_base_online_time`（= 本会话 `login_long_time_flag==1`，见下"15 分钟"）；② `role_daily.can_accept_everyday_encourage == 1`。
- 节奏：**每天一次**（role_daily 每日数据，跨天清零；领取后置 2=已领），索引按连续登陆天数推进。
- 档位表：`config/encourage/everyday_encourage.xml` 8 档 —— `condition_role_lasting lasting_lower/upper`：
  day0(0,0)/day1(1,1)/…/day6(6,6)/**第 8 档 (>=7, 无上限) = 每天 16 个「储备金财富宝箱」**，且 `next` 指回自己 → 长期在线的号每天都停在最大值档。
- 索引推进由 `check_everyday_encourage`（encourage_operator.py:68-90）在**进入世界**（role_observer.py:355）、
  **上线 buff 到期**（buff_action.py:969-975 LoginTimeAction）、**开每日界面**（dispatcher:37-39）三处触发。

### 2) 登陆奖励（login）
- 处理器：`encourage_dispatcher.py:121-141` `dispatch_accept_login_encourage`。
- 门槛：① 同上 15 分钟；② `role_cookie.can_accept_login_encourage == 1`。
- 节奏：7 档**一辈子各一次**（finish 列表持久化），**每档间隔 ≥23 小时**：
  `login_encourage.xml`：第 1 档 `condition_create_role_time=23`（创号满 23h），第 2~7 档
  `condition_accept_login_reward_time=23`（距上次领取 23h，role_condition.py:3351-3363；初值 0=永不满足，
  由领取成功时 `set_accept_login_encourage_time` 写为当前时间，dispatcher:140）。
- 索引推进：`check_login_encourage`（encourage_operator.py:118-141），入口：进入世界 + 开登陆界面 + 领取成功结尾。

### 3) 在线奖励（online）
- 处理器：`encourage_dispatcher.py:49-73` `dispatch_accept_online_encourage`。
- 门槛：只有 `role_cookie.can_accept_online_encourage == 1`；**不检查 15 分钟**、条目无有效条件
  （xml 里 `condition_open_online_gift` 在服务端无对应条件类，解析后被忽略）。
- 节奏：16 格**一辈子各一次**；领第 N 格时加 buff 3000000（`online_encourage.xml` 的 `buff_elapse`），
  到期 GiftAction 置 can_accept=1（buff_action.py:955-964）→ 可以领下一格。等待表（第 N 格领完等几秒）：
  N=1..15 → 60/120/180/240/300/420/540/720/900/900/900/900/900/900/900；N=16 无 buff（全领完）。
  全 16 格约 2.5 小时（60+120+…+720+900×7 = 8880s）。领取成功时 role_cookie.index 推进到 N+1
  （16 领完后清空 index → 后续 accept 静默无回执）。
- buff 3000000 `buff_savable=是 / offline_timed=是`：下线期间继续计时（config/buff.xml:6958-6970）。

### 4) 等级奖励（level）
- 处理器：`encourage_dispatcher.py:98-119` `dispatch_accept_level_encourage`。
- 门槛：① 15 分钟；② `role_cookie.can_accept_level_encourage == 1`。
- 节奏：7 档**一辈子各一次**，按等级 20/25/30/35/40/45/50（level_encourage.xml，role_condition `condition_role_level`）。
  领取成功后服务端**再跑一次 check_level_encourage**（dispatcher:118）→ 下一个达标档立刻可继续领
  （等级 50 的号可一次性连领 7 档）。

### "15 分钟"是什么
- 登录/重登进入世界时加 buff 3000001「上线 15 分钟」（`role_observer.py:107-111 / 350-353`，
  时长 `ENCOURAGE_ONLINE_ELPASE=900`，config/config/encourage.csv:6）。
- 到期动作 LoginTimeAction（buff_action.py:969-975）：置 `login_long_time_flag=1` 并触发四个 check。
- 每日/登陆/等级 accept 与四个界面查询都以 `check_base_online_time` 为准（encourage_operator.py:62-66）。
- 注：`C2S_CHECK_LOGIN_TIME`（dispatch:143-146）会把该 flag **无条件置 1**——本方案不利用该捷径，
  按正常在线 15 分钟走，避免依赖服务端非常规分支。

## 三、最小协议序列（结论）

- **每日/登陆/等级**：进入世界时服务端已自动跑过 check 并置好 `can_accept` → **理论上直发 accept 可行**；
  但"能不能领/今天领没领/是否已满"只有**界面查询回执**（S2C 90197/90104/90416 的 can 字段）能读到，
  而"已领/不可领"的无脑 accept 会换来一条服务端提示（1416/1417/1426/1432）刷屏。
  故实现取：**先 interface 查询 → 回执 can==1 → 再 accept**（每系统一轮）。
- **在线**：界面回执只有 index（不带 can），不能判断"buff 是否到期" → **查询只为对齐 index；
  accept 由"领完第 N 格的等待表 + 失败退避"驱动**（唯一能确定节奏的是 3000000 buff 的 elapse 表）。

## 四、失败提示清单（识别"没到时间"vs 成功）

服务端拒绝时 `send_notice_message`（S2C_NOTICE_MESSAGE，[4,""]，data[0]=id）：

| notice id | 含义 | 我们的处置 |
|---|---|---|
| 1439 | 没有到领取登陆奖励时间（15 分钟未满/会话被重置） | 每日/登陆/等级整体推迟 16.5 分钟后再试（`base_at` 重臂） |
| 1417 | 不能领取每日奖励（含"今日已领"） | 本轮结束，30 分钟后再查（跨天由回执 can==1 自动恢复） |
| 1432 | 不能领取登陆奖励（未满 23h） | 本轮结束，30 分钟后再查 |
| 1426 | 不能领取等级奖励（没有达标的新档） | 本轮结束，2 小时后再查 |
| 1416 | 不能领取在线奖励（buff 未到期） | 退避阶梯 60/180/300/600/900 秒重试 |

**成功识别**：accept 发出后若收到界面回执（无失败提示）即服务端已处理——
每日回执 can 变 2、登陆/等级 can 变 0、在线回执 index 前进一格（或变空=全领完）。
（不新增协议：不注册 `S2C_CHECK_OVER_LOGIN_ENCOURAGE`。）

## 五、收益量化（每号）

物品（config/item/item.xml）：101079「储备金财富宝箱」= **5000 储备金**；
103003「20 万储备金宝箱」= 200000；103005「30 万储备金宝箱」= 300000（reward_item_ext.xml
`stair_item_schoolcontri*` 的 `reward_role_contibution`，无等级/次数限制）。

| 系统 | 一次性合计 | 每日（稳定期） |
|---|---|---|
| 每日 | —— | 第 8 档 **16×101079 = 80,000 储备金/天**（+高级经验花炮×3/守护经验丹×3/坐骑券×1） |
| 登陆 | 7×103005 = **2,100,000**（每 23h 一个，7 天领完） | 前 7 天 300,000/天 |
| 在线 | 5×103003 = **1,000,000**（16 格 2.5h 内领完） | 无（领完即止） |
| 等级 | 29×103003 = **5,800,000**（1+2+3+4+5+6+8，按等级档） | 无（领完即止） |

→ 稳定期每号每天白拿 16 个储备金箱（8 万储备金）；500 个号 ≈ 4000 万/天。
这就是"储备金怎么可能会不够用"的答案：**这一块此前完全没领**。

## 六、实现（机器人端，最小侵入）

新增 `script/encourage_claim.py`（约 500 行，Py2.5/3.9、tab、UTF-8）：

- `tick(robot_object, now)`：挂在 `daily_ghost.tick` **最顶部**（早于抓鬼 enabled 判断）——
  main_tester 每帧对每个号都会调 daily_ghost.tick，因此抓鬼号/新手号/游荡号全覆盖
  （例外：摆摊激活号、route_walk 测试号在 main_tester 里提前 continue，见"已知限制"）。
- 会话起点 = 本连接首次 tick（`m_logined` 上升沿或 fd 变化）→ `base_at = +16.5 分钟`；
  未到点只跑在线（在线不受 15 分钟限制）。
- 每系统独立状态机（查询 → 回执 → accept → 回执/提示 → 冷却），节奏：
  每日/登陆查询间隔 30 分钟、等级 2 小时；在线按等待表精确重试，失败按阶梯退避。
- `on_interface(fd, datalist)`：`protocol3.g_handle_map` 新注册 4 个 S2C 回执；
  `on_notice(robot, datalist)`：挂在 `daily_ghost.on_notice` 最顶部，按上表路由失败码。
- 领到奖励后 5 秒：只 **使用** 三个储备金箱（C2S_USEITEM，实例 id 来自 `quest.bag`，与 __tidy_bag 同源），
  不碰装备/药品/助战令等其它物品（不与既有整理逻辑抢东西）；每轮最多 8 次、10 秒一轮、6 轮封顶。
- 跨重启状态：`state/encourage_<账号>.json`（原子写，同 pre_daily 惯例；`ZCC_ENCOURAGE_STATE_DIR` 覆盖）——
  只存在线格进度/等待点与统计字段；can_accept 一律以服务端为准。
- **热更安全**：`proto_ready()` 检查 8 个协议都在 FORMAT_MC/FORMAT_MS 里，缺任一（= 热更未重启）→
  tick/on_notice 全静默，不发任何包 → 落盘阶段零副作用；协议注册只随机器人重启生效。

改动面：
- `protocol3.py`：+1 import、8 条 FORMAT_MC（4 accept + 4 interface）、4 条 FORMAT_MS、4 条 g_handle_map 路由（仅注册行）。
- `daily_ghost.py`：tick 顶部 + on_notice 顶部各 3 行转调（try/except 吞异常，不影响原逻辑）。
- 不变更：quest_engine / shop_errand / booth / config / 任何既有链路。

等价性论证（不影响既有链路）：
- 触发点在 daily_ghost.tick 最首，只做本模块自有协议收发；异常全吞；不导航、不开对话、不改 quest 状态。
- 与 welfare_tick（福利包）、pre_daily（领双）、share_daily、抓鬼状态机零共享状态。
- 唯一公共资源：背包（只使用 101079/103003/103005，且这些物品既有整理链也会使用）与 C2S_USEITEM 频率（每轮 ≤8 条）。

已知限制：
1. 摆摊激活/route_walk 激活的号在 main_tester 提前 continue，不跑本模块（如需覆盖要动 main_tester，非本次范围）。
2. 15 分钟判断按"本机上线时刻 + 900s buff + 90s 余量"，若服务端会话时间被重置（如中途重登），
   1439 提示会把 `base_at` 重臂，自愈。
3. 储备金入账依赖箱子被"使用"：本模块领到即用；若背包满等异常，下次领取轮再试。
