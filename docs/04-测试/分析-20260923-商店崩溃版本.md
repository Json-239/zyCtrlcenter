# 分析-20260923：商店中间态版本导致机器人 0xc0000005 崩溃

**分析人**：general-purpose-6（只读取证，未改动任何生产文件、未重启任何进程）
**范围**：`deploy/zones/prod-240-2300/script/shop_errand.py.susp_20260923_1647`（16:47 中间态）vs 稳定版；
并核对 `quest_engine.py`（16:30）、`robot_operator.py`（16:47:59 修复版）、C 扩展 `pynetwork.h/.cpp`。
**结论一句话**：崩溃点是 16:47 中间态 `shop_errand.py` 里"**运行期协议补注册**"段的最后一步
`cnet.set_format_dict(protocol3.FORMAT_MC, protocol3.FORMAT_MS)`（日志里的 `replay_ok`）——
C 侧 `SetFormatDict` 对**自己从未持有引用**的旧 dict 做了 `Py_DECREF`，把模块级 `FORMAT_MS/FORMAT_MC`
引用计数多减 1 → 调用返回后 dict 被释放，C 层留下**悬垂指针** → 下一次收包访问已释放内存 → 访问冲突。

## 3. 逐条评估：为什么只有 `set_format_dict` 重放能崩（源码级）

### 3.1 C 侧实现（`F:\ZyBin\xm\2d-xiyou-server\robot\single_robot\pynetwork.h:41-55`，与生产 exe 同构建）

```cpp
void SetClientFormatDict(PyObject *dict) {
    if (m_client_format_dict != NULL) { Py_DECREF(m_client_format_dict); }  // ← 多减 1
    m_client_format_dict = dict;                                            // ← 借用，不 INCREF
}
void SetServerFormatDict(PyObject *dict) { /* 同上：先 DECREF 旧值，再存借用指针 */ }
```

调用链：`cnet.set_format_dict()` → `cnetwork.set_format_dict`（`pynetwork.cpp:844-862`）→ 上面两个 setter。
- **存的是借用引用**（`PyArg_ParseTuple("OO")` 不 INCREF）；模块级 dict 靠 Python 侧自己活着——冷启动时能跑通纯属侥幸。
- **旧值被 `Py_DECREF`**：C 层从没 `INCREF` 过，所以这次 DECREF 是**多余的一减**。

引用计数推演（`FORMAT_MS` 仅被 `protocol3.__dict__` 持有，refcount≈1）：

| 时点 | 动作 | FORMAT_MS refcount |
|---|---|---|
| 冷启动 `client.init():867` 首次调用 | `m_server_format_dict==NULL` → 不 DECREF，只存指针 | 调用中 2（参数 tuple）→ 返回后 1 ✔ 安全 |
| 运行期重放 | tuple INCREF →（调用中）2；setter `Py_DECREF(旧值)` → 1；调用返回、tuple 释放 → **0 = 释放 dict** | 0 ✘ C 层指针悬垂 |

**崩溃点**：下一次收包（C 层收包线程/主循环）执行
`format_list = PyDict_GetItem(m_server_format_dict, msgid)`（`pynetwork.cpp:237`）
—— 对已释放对象取项 → 访问冲突 `0xc0000005`。同秒即崩（16:42:31、16:47:53 均与 `replay_ok` 同一秒）。
即便解包线程侥幸先没走到，Python 侧下一次读 `protocol3.FORMAT_MS[...]` 同样崩。

### 3.2 其余嫌疑点逐条排除

| 嫌疑 | 结论 | 依据 |
|---|---|---|
| `.susp` diff 的 5 处改动 | **不可能**致崩 | 纯 Python dict/bool/str/注释，不触 C 层；崩溃时刻与它们无时间相关 |
| 90327 解析/framing（`[8,2]`、`__parse_item_count_records`） | **正常**，且已生产验证 | 17:01:08 `recv 90327 data=[17615264693848921, 3] → handler OK`；item_id<2^63、count<2^16，形参形状兼容三种打包 |
| 购买参数（npc/item/count） | 正常 | `start()` 有 `_n<1→1`、`>500→500`、item 白名单、npc 兜底；且崩溃前该路径只走到"无跨图路径 12→612 → SHOP_NO_ROUTE"（纯逻辑返回，未触 C 扩展） |
| `m_bag_cache` 非法值 | 不会致崩 | 全是 Python dict 读写；`bag_count()` 全程 try/except，写入形状与既有 `[item_id,count,pos]` 一致 |
| 与 `quest_engine`(16:30) 的接口 | **匹配** | 新增 `on_item_count_add / __shop_retry_check / notify_done(reason,skipped)` 与 shop_errand 新签名一一对应；调用处全在 `try/except` 内 |
| 导航/`robot_path` C 扩展参数 | 无证据 | 崩溃尾部日志无导航栈；同一批导航改动在 16:50 重启后长期运行无异常（17:02 仍在跑） |
| 线程竞争类偶发 | 不成立（是确定性 bug） | "调用一次不崩、调用两次必崩"由引用计数决定；两次崩溃都精确对齐 `replay_ok` 行 |

### 3.3 同族根因（顺带闭环）

`client.py:354-359` 注释记录的"reload `protocol3`/`msghandle` → 0xc0000005"与 11:47:00 那次
`exit 0xc0000005`（`ctrlcenter_20260923.log:3006`）是**同一根因**：
`importlib.reload(protocol3)` 会 `FORMAT_MS = {}` 换新对象 → 旧 dict 失去唯一引用被释放 →
C 层 `m_server_format_dict` 悬垂 → 下次收包崩。
**一句话铁律**：凡是交给 `cnetwork` 的 format dict，任何"运行期替换/重注册/reload"都会释放它 → 必崩。
（C 侧 `~CNetWork` 里也照样 `Py_DECREF` 这两个未持有的指针，属于同族缺陷。）

## 4. 结论与修复建议

### 4.1 结论
- **崩溃点**：16:47 中间态 `shop_errand.py` 中"运行期协议补注册"段的
  `cnet.set_format_dict(protocol3.FORMAT_MC, protocol3.FORMAT_MS)`（→ `pynetwork.h:41-55` 的多余 `Py_DECREF`）。
- **触发条件**：进程内第二次调用 `set_format_dict`（热更后补注册 / reload 协议层 / 任何重放）。
- **责任面**：Python 侧"免重启补注册"是**错误用法**（框架层不支持二次注册）；C 侧引用计数缺陷是**根因**。
- `.susp` 留存件的 5 处 diff 与本事故无关，可放心沿用（其中 3 处正是 P1 目标的一部分）。

### 4.2 修复建议（保留 P1 目标的前提下）
1. **P1 目标本身照留，落地方式只能是冷启动**（已在做）：
   - 90327 采集 = `protocol3.py:362` `FORMAT_MS[...]=[8,2]` + `:572` `g_handle_map` **静态注册**；
   - "已买到"证据链 = `m_bag_cache` 下单前快照/数量增加核对 + 90327 回执 + 1276（剥壳）+ 1110 已扣款宽限
     （`quest_engine.__shop_retry_check / SHOP_PAID_CONFIRM_GRACE_MS`）——纯 Python，无崩溃风险。
   - 新协议一律"改文件 + 重启机器人"，**不要**再尝试 `set_format_dict` 重放。
2. **加硬护栏（防复发）**：`cnet.set_format_dict` 包装成**只允许调用一次**（第二次直接 `raise RuntimeError`，
   失败即显性报错而不是 0xc0000005）；`client.py` 的 `_NO_RELOAD` 已把 protocol3/msghandle/cnet 列入禁热更，保留。
   （现有 `tools/shop_errand_selftest.py` 两项护栏断言保留，并在 shop_errand 侧再断言"模块内不得出现
   `set_format_dict`/`install_*_hooks`"。）
3. **可选根治（C 侧，需重编译 + 重启）**：`Set{Client,Server}FormatDict` 必须
   `Py_INCREF(new)` 后再 `Py_XDECREF(old)`（或深拷贝成不可变 C++ 表、加锁原子替换），
   并把该 API 语义明确为"仅冷启动、可重复安全"。否则协议层永远不能热更。

4. **本批部署清单复核**：`protocol3.py / msghandle.py / client.py / robot_operator.py` 两副本一致、
   C 层无需变动、17:01 收包实证生效；`quest_engine.py` 由另一路（f→g 连通兜底）在制，不在本次改动面。

### 4.3 不确定项（低影响，已尽量交叉验证）
1. `.susp` 归档前那段补注册代码的**原文**已不可得（无 pyc/编辑器历史/临时副本），本文为日志+注记+护栏复原；

3. 11:47:00 那次崩溃的 diag 尾部已被日志轮转覆盖（`diag.log.2` 尾到 14:16），只保留了 ctrl 侧
   `exit 0xc0000005` 记录；与本文同族的判断基于 `client.py:354` 注释口径，未取到当次钩子行。
