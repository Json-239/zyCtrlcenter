## 4. 发现（P0/P1/P2/P3）

### P0：无
### P1：无

### P2-1（新发现，建议随下一批修）陈旧意图残留 → 池统计虚高 + 保持数低估
- **现象**：`decideIntent` 的私池闸（event.go:694-699）只挡"产生新意图"，**不清旧意图**。
  "老号先跑后有意图 → 移入私人池"路径下，旧意图长期残留（心跳也不清——闸直接 return）。
- **影响**：
  ① `/api/autotask` 的 `pools.*.running` 把私号计入（实测 newbie running=1），违反计划 §1.8"私号…不计入池统计"；
  ② `Runner.States().Deficit = TargetOnline - autotaskOnlineCount`（autotask.go:332-337）随之**低估** →
     自动任务少补号、`roampoolDeficit`（游荡池回收口径）偏移 1 个单位。**不会把私号派进自动链**（候选/Skip 等重闸均安全）。
- **复现**：`TestTmpPersonalStaleIntentPoolStats`（10 级号 feed→newbie 意图 → 入池 → running 仍 1；心跳后再查仍 1）。
- **建议**：入池端点内清意图（`Events.Intents.Apply(acc, Decision{}, ...)` 或专用清法），或 `autotaskOnlineCount` 循环首部加 `IsPersonal` 一行（最小改）。

### P2-2（派单点名的边界，已复现）ensure_online 8s 窗口内移出私池，任务仍下发
- **现象**：`handlePersonalTask` 在受理时构造命令，`go func(){sleep 8s; SendCmd}`（personal.go:400-404）**不复查 IsPersonal**。
  实测：受理 → 窗口内 remove 出池（名单推送正常）→ 8s 后 `ghost_start` 仍到达。
- **影响**：小概率（用户"点了开始又反悔移出"）；命令已在途，可作为"已受理"语义接受；但与"移出=回到自动编排、不应再收私池任务"的直觉冲突。
- **建议**（可选）：延迟 goroutine 内 `if !a.IsPersonal(acc) { 记录跳过; return }` 复查一次（两行）。

### P3-1 重复 `/api/team/dispatch` 重复补发（修3 无幂等闸）
- 第二次 dispatch 会再发一轮 captain+member（实测）。机器人端待命语义幂等（member 归一待命），无副作用；
  但"连点"会给全队重发命令。可接受现状，建议后续给 dispatch 加同 captain TTL 去重（与 ghostInflight 同口径）。

### P3-2 batchOnline 显式给号（面板"上线"按钮）在池容量满时会拦私号
- `batchOnlineBudgetOf` 已让私号**不占额度**（handlers_accounts.go:413-416），但容量闸对"显式 accounts"统一截断
  （accounts 含私号，`len(accounts) > allow` 时私号也被 queued）——逻辑上"不占额度却被额度拦"。
- 勘查报告已口径化（"私号手动上线走直发 sendOnlineChunks（或 batch force:true）"，§74 行）；`/api/personal/task` 的
  ensure_online 走直发不受影响。**建议前端批（私人池操作卡）私号"上线"按钮走 force=true 或直发**。

### P3-3 注册表并发落盘竞态（低概率）
- `Add/Remove` 锁内 marshal、锁外写盘（personal.go:93-97 / 115-119）：两个并发变更先后落盘可能乱序
  （后写覆盖先写 → 重启后丢一个新标记）。窗口极小（手动操作），失败写入本身也是静默设计。
- 建议：可在返回前持锁写盘，或加"写盘序号"防御；当前接受。

### P3-4 修4 仅覆盖 member（队长丢态不告警）
- `need_rejoin` 判据 `role=="member" && TeamBlock()==nil`（team.go:481-489）；队长重登丢态无同款告警。
  属修4 划定范围（深挖结论"队员丢态被埋"），队长路径建议阶段 3 一并处理（重建队流程）。
