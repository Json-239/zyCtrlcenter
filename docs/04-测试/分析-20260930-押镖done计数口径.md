# 分析-20260930-押镖"done 计数"口径疑点（只读排查单）

**来源**：team-lead 派单（多号试点发现；影响批量轮次管理，批量前必修）。
**现象**：①做过前置试镖 5001607 后，主镖启动行即显示"今日已完成 1"（1142/1037 实证；5240 同模式）；②主镖主任务 FINISH 后 done 不涨（5240 轮1 抵押品版 2001110 完整交付后仍 1/5）。
**范围**：只读；不改码、不碰进程。机器人 share_daily.py 现行 sha `0dd89f69`（live 核实）。

---

## 0. 结论（TL;DR）

1. **服务端计数正确且权威**：按 `share_daily_key` 分桶、每轮"根任务"FINISH +1；主变体 2001108~2001113 各自为根、逐轮 +1。
2. **现象①根因＝机器人端计数作用域泄漏**：`done_count` 在机器人端**没有 share_key 维度**——内存态跨 key 继承（`_cur`）+ 本地文件按**账号**落盘（`{date,done}`）。嘱托轮（key=镖局嘱托）把 1 写进账号级计数 → 主镖（key=镖行天下）启动读到 1。
3. **现象②＝两个因素叠加**：
   - **伪结算（bug）**：`__check_settle` 的"下一轮已开"守卫只认"在身任务==链尾(2001113)"；抵押品线每轮结构是 入口2001107→变体，入口 FINISH 接力变体时被误判"下一轮"→ 16:28:45 提前结算（rounds_local+1）。
   - **污染基线与首轮权威值碰撞（机制巧合，非计数错误）**：真结算（16:41:42）时服务端权威值 srv=1（直证见 §7），与已被污染的 done=1 相等 → 无校准日志、显示维持 1/5。**数值恰为真实轮数（1 轮），只是前值已被拔高**。第 2 轮起 srv=2 会打校准并正确显示（预测锚点见 §6）。
4. **服务端侧无缺陷**：5001607 无 `share_daily_key` → 从不计数（diag 零条直证）；2001107/20011999 各自独立桶（key=…07 / …999）且不在 `count_roots` → 不污染主计数（设计正确）。
5. **最小修正＝机器人端 share_daily.py 三处**（§5，报批后施工）；中控/协议/服务端零改动。

## 3. 现象定性（含反证）

### 3.1 现象①：嘱托→主票启动=1（作用域泄漏）
时间线（5240，本地时间）：16:02:31 嘱托启动(0) → 16:17:14 FINISH → 16:17:16 结算"1/1" → 16:17:58 DAILY_LIMIT 停 → **16:23:56 主票启动"今日已完成 1"**。
链路：嘱托结算把 g.done_count=1（srv=None，max(0,rounds_local=1)）→ 同时写账号级文件 done=1；主票启动时 `_cd==今日`、`_srv=scan(主roots)=None` → `done=_cur=1`（**且未打"本地计数恢复"日志——反证走的是 _cur 分支**，:2324 只在 _loc>done 时打）。
1142/1037 同型（17:15:57 嘱托结算"1/1" → 17:16:31 主票启动"已完成 1"）。

### 3.2 现象②-a：伪结算（守卫误判"下一轮"）
16:25:36 接 2001107（入口）→ 16:28:43 FINISH、同秒接到变体 2001110 → 16:28:45 **"本轮完成: 今日 1/5"**。
判定：结算时在身=2001110；链尾=**2001113**（`biaoxing_nav.task_order[12]`）→ `_ti != _last_ti` → 守卫放行结算（:4252-4268 注释的"下一轮主任务"假定，对"入口→变体"的同轮接力误成立）。
副作用：rounds_local 提前 +1；本轮轮换态被中途复位（:4283-4290）；本地文件提前写 done=1。

### 3.3 现象②-b：首轮显示冻结（污染基线与权威值碰撞）
16:41:39 2001110 真交付 → 16:41:42 结算：rounds_local=2；srv=**1**（直证 §7）→ `srv==done(1)` → 不打校准、维持 1/5。
反证：若 srv=None，该分支应为 `max(1,2)=2` → 必打"2/5"，与实际矛盾 ⇒ srv 非 None 且=1。
**结论：单轮数值没错（服务端真值 1），错在起点已被拔高 1**。次轮起 srv 超过基线即自愈（预测见 §6）。
另注：早期两次主票启动（15:49 被预检拦 / 15:52 未接票）与 2001107 桶（=1）均被正确排除在扫描外（count_roots 12 项，数据与代码双侧核实）。

## 4. 影响面（不修的代价）

1. **启动显示/满额判定偏差**：做过任意"跨 key"日常（嘱托属之）后，另一 key 启动即显示 +N；**limit=1 场景可"启动即满"误停**（e.g., 主票手动 daily_limit=1 派发会被 done=1 直接拒跑）。
2. **伪结算**：每轮抵押品线多一次结算——rounds_local 虚增（srv=None 链路上会把"日限 N"折半触发）；本轮轮换态中途复位（tried_locations/shop_bought/kill_tries 清空，影响本轮剩余路径/采购逻辑）。
3. **批量轮转**：轮转/收工若按 done 排程，首轮显示冻结 + 起点偏移造成口径混淆；面板"今日 x/limit"读数同样受影响。
4. 心跳 daily.done（:2671）与中控面板/满额表/我的 `ShareDailyFullToday` 均读此值——数值错不爆，但口径不一致会误导运维判断。

## 5. 最小修正方向（**报批后用**；本单不施工）

**A（必修｜现象①）计数器 key 化——share_daily.py 两处：**
- 本地文件加 `"key": share_key` 字段；`__load_local_count` 仅 key 匹配才恢复（旧格式无 key → 不恢复，可接受）。
- 启动三态：g 记录 `count_key`（上次会话 key）；`count_key != share_key` 时 `_cur` 视为 0（跨 key 不继承）；同 key 续跑/重登语义不变。
- 边界：同 key 同日断点续跑仍继承 ✓；跨夜已由现有逻辑清零 ✓；嘱托同日重跑将被本地文件挡（现状亦如此，语义不变）——如需放开，由日限参数决定，属产品口径。

**B（必修｜现象②-a）结算调度闸——`__on_task_finish`（:1675-1680）arm 条件收紧：**
- 候选方案 1（推荐）：仅当 `ti ∈ count_roots`（或 `ti == 链尾收尾`，覆盖神捕 reply 重排）才 `settle_summary=True; settle_at=...`。
- 候选方案 2：守卫改"在身非空即等"——**回退 2026-09-24 的 5275 修复，不采用**（秒接下一轮会再卡计数）。
- 回归面：神捕（main 2 任务 + reply 2028399 两段 arm）、烽火（5 子任务）、嘱托（单环）、押金版单任务轮——须四条链路全过。

**C：无需改。** srv 非 None 时 `done=srv`（不取 max）是"服务端权威"既定语义；A+B 后基线正确，碰撞自然消失、校准日志（:4277-4279）恢复可见。

**施工影响**：仅 share_daily.py（可热更模块）；无协议/中控/服务端/前端改动；自检+坏版灵敏度按既有模式补（建议两条变异：跨 key 继承必逮 / 入口 FINISH 伪结算必逮）。
