## 2. 配置历史（两次变更）与回落推论

配置注释里记录的两段历史（原文保留，未删）：

1. **2026-08-26/27（0.1 的来源）**：
   - 3 秒 → 0.5 秒（用户反馈"停顿严重、移动一跳一跳"）；
   - 0.5 秒 → 0.1 秒（用户反馈"走路断断续续，跟速度无关"，0.5 仍一跳一跳）。
2. **2026-09-11（机制变更，`quest_whole_path`）**：
   - 走路改为**一次发整条路径**（对齐真人客户端 `__send_moving_path`），服务端逐点消费路径推进角色位置，其他客户端看到平滑移动；
   - 过去"逐段发"（每次 2 点，服务端只消费 1 点）导致的错位/一跳一跳问题**已由该机制解决**。

**推论（本次核实成立）**：`0.1` 是 8-27 为掩盖"逐段发卡顿"留下的历史值；9-11 机制变更后，位置上报（80360）已退化为"权威位置同步 / 遇怪累计 / check_point 弹路点"用途（见 1.3：**不参与其他客户端的移动观感**）→ **可以回落到服务端设计值 1.0**。

## 3. 影响面核实结果

### 3.1 使用点：`quest_walk_report_interval_sec` 共 5 处读取，全部在 `quest_engine.py`

| 行号 | 函数 | 语义 |
|---|---|---|
| 2668 | `__walk_send_whole` | 整条路径模式启动：首次上报时刻 `walk_report_next_ms = now + interval*1000` |
| 2724 | `__start_walk_segment` | 逐段模式启动：同上 |
| 2857 | `__tick_walk` | `_dt` 异常兜底（时钟回退/长时间卡顿 → 用标准间隔换算位移） |
| 2910 | `__tick_walk` | **核心**：行走中每次位置上报后重置下一次上报时刻 |
| 2944 | `__tick_walk` | 整条路径模式切换到下一路点后重置上报时刻 |

- 另有 2351 / 3368 两处"取消行走时 `walk_report_next_ms = 0`"（清理，不读配置）。
- 语义确认：它就是控制**走路过程中 `C2S_NOTIFY_POSITION`（80360）发送间隔**（同时是本地插值推进节奏，见 3.5）。
- 全 `script/` 目录 grep：除 `quest_engine.py` 外无其他模块读取该配置；`daily_ghost.py` 不读（3.2）。

### 3.2 战斗 / 抓鬼场景

- **战斗中**：`quest_engine.tester()` 在 `m_fight_state` 分支直接 `return 0`（`quest_engine.py:3184-3200`）→ 不行走、不发位置包；服务端也丢弃 80360。**与本次间隔无关**。
- **抓鬼（追鬼）行走**：去钟馗/跨图/找鬼走位复用 quest_engine 行走机制 → **共用该间隔**（这是预期行为，非"误伤"）。
- `daily_ghost.py:2750` 的兜底位置上报（点跳转 NPC 卡住时校准一次）是**写死的单次发送**，不读该配置 → 不受影响。
- 结论：**不需要**为追鬼单独加更勤的同步 —— 点击距离校验（600px）依赖"到点/点击前校准上报"（写死、精确），不依赖行走中频率。

### 3.3 其他"发送频率"配置（区分，避免混淆）

| 配置 | 用途 | 与本次关系 |
|---|---|---|
| `inform_point_time_interval = 3` | `main_tester.py`/`map_tester.py`（模拟客户端游荡程序）专用 | **生产机器人主程序不用**，无关 |
| `quest_segment_min_gap_ms / pause_min / pause_max / skip_ratio` | **逐段模式**的段间节奏（避开服务端 300ms 广播节流） | 不受本次影响（间隔两模式共用，段间逻辑不变） |
| `quest_walk_delay_ms = 160` | 每段行走前置停顿 | 无关 |
| `manage_add_interval_sec = 0.4` | 建连节流（登录） | 无关 |
| `quest_walk_speed = 120/60` | 本地插值速度（120px/s）→ 1.0s 后每步位移 ≈120px | 相关：决定"每步跳多少像素" |
| `quest_human_walk` / `quest_path_dither_px` / `quest_walk_speed_jitter` | 拟人化行走开关 / 路点随机偏移 / 速度扰动 | **均非"发送频率"**，与本次无关 |

### 3.4 服务端机制核实（决定 1Hz 是否安全）

见 1.3 表。关键三条：
1. 服务端**不校验频率**、无超时踢人 → 1Hz 与 10Hz 均被接受（1Hz 是设计值）。
2. 80360 **不广播** → 其他玩家客户端看到的移动由 80301 整条路径广播 + 客户端本地播放决定，**与上报频率无关**（9-11 机制之后）。
3. 上报只影响：服务端权威位置更新粒度、遇怪累计距离采样（按累计直线距离，1Hz 误差可忽略）、`check_point=1` 路点消费（到点上报始终发送，不受间隔影响）。

### 3.5 本地影响（重要，别忽略）

- `__tick_walk` 的"本地插值推进 + 上报"在**同一个 if 分支**里（`now_ms >= walk_report_next_ms`）→ 间隔改 1.0 后：
  - 位置包（80360）**1 次/秒**（目标）；
  - **中控大屏的实时位置回显（`robot_pos` emit）也随之从 10Hz 变为 1Hz**（每步 ~120px），"一跳一跳但每步正确"；
  - 到点上报（`check_point=1`，写死）不受影响，点击前位置仍精确。
- **副作用（需主控处置）**：`quest_engine.py:2859-2868` 有一段 TEMP-DIAG 诊断 —— `STEP_GAP` 在 `_dt > 0.35s` 时打 warn（该阈值按 0.1s 间隔设计）。改成 1.0 后**每步 `_dt≈1.0` 都会告警**（行走中的号 ~1 条/秒/号，日志噪音）。
  - 本次约束"只改 config.py，不碰 quest_engine 逻辑"，**未动该诊断**；建议主控热更时一并删除该诊断块（注释已标"用完可删"）或把阈值改为随间隔取值。
