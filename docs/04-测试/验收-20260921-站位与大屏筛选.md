| **需求 2（大屏筛选）** | **合格** | 判据/计数/兼容与验收口径逐条一致；dist 与 dev server 实际下发代码均含新 chip；`/api/intents` 数据可 join。存在 2 条可用性缺口（见第 5 节），但均属口径/数据状态，不属实现未落地 |
| **总判定** | **有条件合格** | 见下方条件 |

**条件（两条）**：

1. **停摆号离场（决定性）**：当前 30 个号停在钟馗格 [108,66]，其中 24 个为 DIALOG 卡死号，`/api/intents` 的 `recover` 已明确"**不补发：当日卡死已达 3 次（等人工/跨日清零）**"——**今日不会自动恢复**。在它们离场前，现场（客户端看钟馗）**仍会看到大量号叠在同一格**，与用户抱怨的观感一致。需人工补发/上线，或等跨日清零后由既有重登路径把它们带回（先例 robot0001089 已落到分散格 [1704,1048]）。**该停摆缺陷（GHOST_DIALOG_STUCK）不在本次改动范围，建议单列跟进。**
2. **👻抓鬼 chip 口径收紧（建议）**：若要真正"查看当前在抓鬼"，建议判据由 `r.ghost != null` 收紧为活跃态（如 `r.ghost?.enabled === true` 或 `state ∉ {IDLE}`），否则该 chip 恒命中 ~89% 的号，区分价值极低。
   （此条为建议，不减损"合格"判定；条件 1 为现场可见效果的前置。）

### 6.2 局限（哪些是抽样、哪些无法当场验证）

1. **未做浏览器点击验证**：无法用浏览器实际点两个 chip 看列表；替代证据是"源码 = dist = dev server 转译产物"三段一致 + `/api/intents` 与 status 的 join 可用性。**两个 chip 的实际渲染效果（计数显示、分页/叠加行为）属代码级验证，不是端到端点测。**
