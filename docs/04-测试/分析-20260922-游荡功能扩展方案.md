**一句话总纲**：把现有"游荡档位（profile）= 走/停节奏"扩展为**"游荡任务 = 档位 × 目标图(可白名单) × 时长 × 附加行为(action)"**，
附加行为用**注册表 + 钩子**接入（加用途 = 加一个模块，不改主循环）——这是本文 §3 的核心设计。

## 2. 可行性评估（逐项）

### 2.1 野外游荡（通用）——**可行；"指定图"已够用，"随机图/限时/避人"是新增量**

- **现有能力**：`/api/random_walk` + `default`（拟人走停，25s~4.5min 停顿随机、每号独立 RNG）已实现"野外挂机感"
  （`RB/random_walk.py:268-300`）；`dense` 档 = 密集游荡（几乎不停）。
- **要不要"图内选安全区/避 PK"？**
  - 证据：本服**没有**通用"安全区/免 PK 图"配置；PK 地图开关默认开（`SV/script/maps/map_object.py:21-30`），**强P 存在**（`SV/fight/operator_pk.py:159-184`）。
  - 结论：技术上加"选安全区"没有服务端配置可依托，**只能做"选图 + 拟人化 + 避开热门时段"**；
    是否需要"遇战/受击即转移"等策略，**建议由用户确认业务口径**（§4-C1）。
- **依赖**：①机器人端 `minutes`（限时）；②Go 侧"随机图"包装（白名单内随机 `mapid`）；③前端入口。
- **结论**：`可行`。P0 落地"限时 + 前端入口"，P2 再加随机图/避人。

### 2.2 选图游荡——**已可用；只缺"白名单校验 + 前端入口"**

- `/api/random_walk` 已支持任意 `mapid`；链载荷校验保证"到得了 + 图内有网格"（`CC/internal/api/chainpayload.go:160-172`）。
- 11 张采集图在基座链 `map_grids` 里**全部存在**（本机核 `CC/data/chains/newbie_full.json`），不会触发硬失败。
- 需要补的：①Go 侧"可选图"列表接口（给前端下拉 + 拒绝明显不适合的图，如无网格图直接给出可读错误——现错误信息已够用）；
  ②前端入口（`web/src` 目前 grep 0）。
- **结论**：`可行（工作量最小）`。

### 2.3 游荡挖矿/采集（重点）——**可行；但 3 个前置必须先实测（见末尾"待实测"）**

#### ① 怎么发现采集 NPC？（**模板白名单**，不需要反查 rect）

- **模板号范围从哪来？** 不是从 `gather.xml` 的 rect 反查，而是**固定模板表**：
  `CFG/npc.xml` 里 `npc_handler=gather_handler` 的 24 条 = 17100~17111（药草）/ 17200~17211（狩猎）/ 17400~17411（挖矿），
  与 `gather.xml` 的 `npc_entry` 一一对应（§1.5C）。
- **机器人凭什么知道"眼前这个是采集 NPC"？** `S2C_ADD_NPC` 的第 2 个字段就是模板号（`RB/msghandle.py:749-751`），
  已落 `m_npc_add_raw[npc_id]=[tpl, raw]`（`:773-777`）→ **`tpl ∈ 24 表` 即采集节点**，坐标取 `m_npc_positions[npc_id]`。
- **兜底/加固**：位置消息 `NPC_MOVE/NPC_STOP` 同表更新（`:706-734`）；`m_npc_pos_seen` 已有时间戳（TTL 参照 `RB/quest_engine.py:186-212` 的 120s）。
- **风险（必须实测）**：C++ 层是否把**采集类 NPC（类型=物品/动物）**也广播成 `S2C_ADD_NPC`。现有注释只给了任务 NPC 样例（`:738-746`）。
  - 实测方法（P0 第一步，成本极低）：修 `RB/msghandle.py:785` 的 `_map` 未定义 → 让 `ADD_NPC` 日志真正落地；

    或让心跳临时上报 `m_npc_add_raw` 的模板直方图（只读观测）。
  - 若**不广播**：退路 = 用 `CFG/map_rect` 的采集区域（245 个矩形，坐标口径已验证一致）做"区域扫街"（在区域内小步游荡 + 盲点最近可走格），效率下降但可行。

#### ② 怎么走到 NPC 旁并点击？

- 走：`m_npc_positions` 给坐标 → 复用"目标点走位"（`w.target`，`random_walk.py:371-398`）或用 `quest_engine.__build_path`
  （无网格宁停不穿墙，`RB/quest_engine.py:2635-2659`）；边界：`min_bot_dist` 避让已在游荡里实现。
- 点：`quest_engine.__teleport_click(robot, quest, npc_id, npc_index, 0, delay)`（`RB/quest_engine.py:215`）→ 发 `C2S_CLICKNPC`（`:3102-3110`）。
- **距离要求**：服务端校验 ≤600（`SV/script/npc/npc_dispatcher.py:35`、`SV/script/common.py:220-227`）；
  现有 target 机制到点阈值是曼哈顿 ≤200 → **天然满足**。
- **注意**：`click_type` 用 0 即可（`role_click_npc` 只对 `click_type==2` 走"直接执行任务"，其余都走 `click_npc_object`，`npc_dispatcher.py:50-62`）。
- **注意（重要）**：采集期间服务端给角色加 `ROLE_STATUS_CHANT` + `begin_chant`（记吟唱起始时间，`SV/restrict/restrict_ruler.py:200-207`），
  期间**不要继续发移动**（避免本地走位状态机与服务端不一致）→ 采集循环内"点击→吟唱窗口"必须独占移动权。

#### ③ 采集开始/进度/完成的信号？

- **开始**：`S2C_CHANT_START [chant_id, chant_time, msg_id]`，**`msg_id == C2S_FINISH_GATHER(80309)` 即"采集吟唱已起"**
  （`SV/role/role_chant.py:101-117`，`msg_id` 就是"吟唱完成后要执行的消息"）。
  → 机器人端需注册该消息（当前未注册，§1.2.4），用它区分"点击被接受"与"被拒"（被拒会先到一条 notice，见下）。
- **进度**：服务端**没有**进度包；有 `S2C_TERMINATE_CHANTING`（结束吟唱，`s2c_list.py:893`）可作"吟唱结束"信号（可选）。
- **完成（何时发 `C2S_FINISH_GATHER`）**：
  - 服务端吟唱时间 = `GATHER_REQUEST_TIME=3s`（`CFG/config/config.csv:74`），合法性要求 **≥3s**，否则 `check_chant_time` 拒（`SV/role/role_session.py:231-245`）；
  - 客户端可发两种等价消息：`C2S_FINISH_GATHER[npc_id]`（`SV/gather/gather_dispatcher.py:12-14`）或
    `C2S_FINISH_CHANT[chant_id]`（`SV/role/role_dispatcher.py:134-140` → `active_chant` → 内部执行挂起的 `C2S_FINISH_GATHER`）；
  - **兜底**：若什么都不发，服务端在 `now + chant_time*2 = 6s` 时自动执行（`SV/role/role_chant.py:119-127,69-80`）。
  - → 机器人策略：**点击后等 ≥3.2s（建议 3.5~4s）再发 `C2S_FINISH_GATHER [npc_id]`**；拿不到 `chant_id` 也不影响（`npc_id` 自己知道）。
- **失败信号（notice，机器人已全量落 diag，`RB/msghandle.py:819-849`）**：
  31 体力不足 / 166-168 被抢 / 170-171 没工具 / 172-174 没技能 / 175-178 熟练度不够 / 786 耐久不足 / 133 奖励失败。

## 3. 实施方案（分阶段 + 改动清单）

### 3.0 架构：从"游荡档位"到"游荡任务"

**问题**：现在每个新用途（孵化/挖矿/打猎）都要在 `tick` 里塞分支 → 主循环会越来越脏。

**设计**：把随机走拆成**两层**，用注册表接附加行为：

```
游荡任务 = 档位(profile: default|dense|gather_*)  ×  目标图(mapid 或 mapids 白名单)
          ×  时长(minutes)  ×  附加行为(action: none|gather|hunt|egg)

┌─────────────── 移动层（random_walk 主循环, 已有）───────────────┐
│ tick: 战斗等待 → 对话防卡 → 跨图(nav) → 到位随机走(walk)         │
│         ↑ 每帧先问一次: ROAM_ACTIONS[action].on_tick(robot,w,now)  │  ← 新增唯一钩子(3 行)
└──────────────────────────────────────────────────────────────┘
ROAM_ACTIONS = {
  "":       None,                       # 纯游荡（现状）
  "gather": roam_action_gather,          # P0: 药草/挖矿（点击→吟唱→提交→冷却→换点）
  "hunt":   roam_action_hunt,            # P2: 先 hunt 再 skin
  "egg":    mount_egg(现有逻辑薄适配),     # P1: 固定孵化图 + 灵气计数（复用）
}
行为模块的约定（4 个可选钩子，全部 getattr 兜底调用）：
  on_start(robot, w)                 任务启动（预检：技能/工具/体力/图）
  on_tick(robot, w, now) -> bool     True=本帧已占用(不随机走) / False=交回移动层
  on_event(robot, w, kind, data)     点击回执/吟唱开始/notice/战斗结束
  on_stop(robot, w, reason)          收尾统计 + 上报
```

**命令契约（向后兼容，旧 `random_walk` 语义不变）**：

```
{"cmd":"roam_start",                 # 新命令；机器人端等价 random_walk + action
 "accounts":["a@x.com"],
 "mapid":6,                          # 或者 "mapids":[6,17,34,40]（随机图，P2）
 "profile":"dense",                  # 缺省 default
 "minutes":60,                       # 新增：机器人端真正限时（到点自行停+上报）
 "action":"gather", "action_args":{"kind":"herb"|"mine"|"hunt","level":"any"},
 "range":[[x1,y1],[x2,y2]], "min_bot_dist":200,
 "chain":{...}}                      # 由 Go 侧 Payloads.Walk 组装(不变)
{"cmd":"roam_stop","accounts":[...]} / {"cmd":"roam_status","accounts":[...]}
```

- `random_walk`/`random_walk_stop` **保留原样**（现有孵化链路/补发逻辑不受影响）；`roam_*` 是超集。
- 心跳新增 `gather` 字段（与 `walk`/`hatch` 同构）：`{state, mapid, kind, ok, fail, last_reason, stamina?}`。

### 3.4 部署与协作注意（重要）

5. **前端改动需重新构建**（`web/` 有 `dist/`，`vite` 构建产物入库）。
