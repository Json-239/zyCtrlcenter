## 0. 结论速览（先看这段）

1. **三步路径（定时任务在跑 → 大屏批量添加 → 链数据页「启动链路自动分配」）不会造成永久脏状态**：
   命令下发是"提示式"的，机器人端对重复命令有幂等/续跑保护，配额与在途记账（2026-09-23 P0）把抓鬼超编挡住。
2. **但会"多发一次命令"，并发点/连点时有残余窗口**：
   - 抓鬼侧有在途（TTL 120s）+ 配额闸 → 连点第二次基本被挡；
   - **新手链侧没有在途记账** → 连点第二次仍会重发一遍 `start_chain`（机器人端同链续跑，不重置任务，代价较小）；
   - **定时任务（autotask）的候选与"在跑"口径都不含在途** → 手动派发后 120s 内若定时任务到点，
     会再派最多 `batch_max` 个重复命令（抓鬼重复下发 = 机器人端 `g.reset()` 重新去钟馗，打断当轮）。
3. **"乱点"最容易被当成故障的三件事**（都是观感问题，不是脏数据）：
   - **点「停止/停链」停不住**：生产 `CTRL_AUTO_RESTORE=1`，restorer 在 ≤5~8s 内按意图补发（`stop` 只取消 reghost）；
   - **手动派游荡被立刻回收**：游荡池 `interval_sec=10 + reclaim_on_deficit=true`，任务池有缺口时 <10s 回收；
   - **批量下线又被拉回**：`batch offline` 不取消 reghost（`/api/robots/manage remove` 有取消），当日卡死过的号会被自动重登拉起。
4. **写接口默认无鉴权**：`config.local.json` 的 `api_token` 是 `CHANGE_ME_*` 占位 = 未配置 → 同网段任何人都能点这些按钮（含重置/重启/清空）。

## 3. 交互矩阵（用户操作 × 四套编排）

交叉格 = "谁覆盖谁 / 结论"。"—" = 无实质交互。

| 用户操作 ↓ / 编排 → | autotask（抓鬼/新手定时） | restorer（恢复引擎，生产开） | waterline（水位 230） | roampool（游荡 130/10s） | reghost（卡死重登） |
|---|---|---|---|---|---|
| 批量上线（D1/D2/A2） | 下一轮按意图派任务（正常接力） | 上线后 IDLE/ONLINE → 视作"没在跑" → 若意图已登记则**补发**（与 autotask 谁先到谁赢，都发同一命令） | 计入 online；超 target 时**可能被压号下线**（用户会看到"刚上就被下"） | 空闲号 90s 后机器人端自动游荡；keeper 也会派（target 130） | 无 |
| 行内/批量启动（D3/D4/C1/T4） | 抢同一批候选：**候选不含在途**，90~120s 窗口内可能重复派（R2） | 与手动派发互斥地"再确认一次"；在途记账让 restorer 看得见手动派发（`restoreInflight`/`poolQuota`） | 不直接交互（只认在线数） | 若游荡中且任务池缺人 → 回收让位 | 无 |

**矩阵中"同一号被多路派发"的组合（按发生概率排序）**：
1. 手动「启动/启动自动分配」+ autotask 定时轮（窗口 90~120s，见 R2）；
2. 手动启动 + restorer 补发（两者都在线下发；restorer 的 Skip 只挡池/满额/等级/churn，**不挡"刚被手动派过"**；在途记账只让 restorer 看得见，反之 restorer 的补发会被手动侧的在途计入）；
3. 批量上线 + restorer（上线瞬间 IDLE → 补发）+ autotask（下一轮）→ 同一号收到 2 次同命令；
4. 「立即补发全部」+ autotask 定时轮（restorer 冷却 300s，只影响首次）。

> 机器人端对"重复同命令"的实际代价：`ghost_start` **每次都会 `g.reset()` 重新去钟馗**（`daily_ghost.py:1300` 分支 → `:1386` `g.reset()`，无"已在抓鬼则忽略"判断）→ 打断当轮抓鬼；`start_chain` 同链续跑、不清任务（`quest_engine.py:3778-3790`）；`random_walk`/`hatch_start` 有明确幂等（§4 引用）。

## 4. 三步路径逐步推演

### 步骤 ①：开着定时任务
- 抓鬼定时（60s/轮，5~10 个，target 100）在 goroutine 中跑（`autotask.Run`，`internal/services/autotask/autotask.go:467-478`）。
- 恢复引擎 5s 一轮（`restorer.Run`），水位 60s 一轮，游荡池 10s 一轮。
- **关键事实**：这四套彼此之间**没有全局互斥锁**，只在"池闸/在途/资格"这些共享口径上互相可见。

### 步骤 ②：从大屏批量添加（= 选号上线/批量上线；若"加号入池"则只是入池不上线）
1. `POST /api/robots/batch {online}`（`handlers_accounts.go:203-284`）：先过滤已在线，再按批（默认 chunk 10、间隔 300~500ms）下发 `robot_manage add`，密码只从账号池按区取。
2. 机器人端 `manage_robots`：**已在登录队列的号跳过**（`robot_mgr.py:190-191`）→ 连点/重复添加幂等；建连另有批次限速（默认 5 个/秒）。
3. 号登录后：`robot_online` 心跳 → 登记意图（<31 新手链 / ≥31 抓鬼，`event.go:329-375`）→ 抓鬼定时下一轮把它列入候选 → 派 `ghost_start`（带导航数据）；新手定时若停用则不拉。
4. 同时：水位把它计入 online（超 230 会挑空闲号压回）；游荡池/机器人端空闲兜底可能把它派去游荡（它是空闲的话）。
   **影响面**：用户"刚加的一批号"会被四套编排按各自口径接管，且**互相之间不是排队关系**（可能今天先抓鬼、被抓满后转游荡等）。

### 步骤 ③：链数据页点「启动链路自动分配」
请求 = `POST /api/start {auto:true}`（`ChainView.vue:140-152`，下拉默认值就是 AUTO；`accounts` 输入框留空 = 不带 accounts）。

`startAuto` 的执行链（`handlers.go:431-601`）：
1. **目标集合**（`:432-447`）：无 accounts → **意图表全部账号（含离线）** + 运行时在线号（去重排序）。
2. **分组**（`:452-481`）：
   - 意图=抓鬼 → `ghost_start`（先过等级门槛 `ghostGateFor`，不过就跳过并回带原因）；
   - 意图=空闲 → 不发；
   - 其余（新手链 / 捉鬼链 / **未登记意图**）→ `start_chain` + 默认链（`newbie_full`）。
3. **配额截断**（`:489-514`）：`max(0, target - 在跑 - 在途)`；
   - 抓鬼：`在跑` = 活跃抓鬼会话数，`在途` = 手动/定时派发 120s 内 + restorer 补发 120s 内（`api/autotask.go:270-289`）；
   - 新手：`在跑` = 在线且意图=newbie 数，**在途恒 0**。
   - 手动通道特例：池停用不拦（用户点了就是要跑），但仍按 target 截断。
4. **抓鬼载荷前置**（`:516-532`）：导航数据取不到 → **一条命令都不发**（避免半成功）。
5. **下发**：新手组一条 `start_chain`；抓鬼组一条 `ghost_start`（带 `done` 防丢进度）；成功后 `markGhostDispatch` 记在途（`:578-582`）。

**点完之后的实际影响**：
- 已经在跑的抓鬼号：如果它在"在跑"里（会话活跃）→ 占配额；若配额仍有余额，它**也会被重复下发**一次 `ghost_start`（`toGhost` 不做"已在跑则排除"）→ 机器人端重启该号抓鬼会话（重新导航钟馗，当轮进度/路程损失）。
- 离线号/未登记意图号：命令下发进机器人端 `g_pending_cmds` 缓冲队列（`client.py:370-503`，**append 无去重**），登录后逐条应用。
- 新手链号：同上，重复 `start_chain`（同链续跑、不清任务；已毕业直接 `already_done`）。

**连点两次「启动链路自动分配」会不会重复派？**
- 抓鬼组：**基本不会**——第二次进入时第一批仍在在途（TTL 120s，且会话未建立）→ 配额 `target-在跑-在途 ≤ 0` → 不派（日志会打 `[START] 抓鬼池配额拦下 N 个`）。
- 新手组：**会**——无在途记账，`在跑`（在线且意图=newbie）在短时间不变 → 第二次仍会重发同一批 `start_chain`。
  - 代价：机器人端同一号队列里多条 `start_chain`，登录后重复应用（同链续跑，不重置任务 → 一般只表现为"重新评估续跑/路径中断"，无破坏性）。

**残余风险（修复后还剩什么）**：
1. R1（新手链无在途）+ R2（定时任务候选/在跑不含在途）→ 短窗口重复派发；
2. R6（配额检查与发送非原子）→ 极端并发下仍可能各派 ≤quota 个；
3. `zhuaogui`（捉鬼链）意图在 `startAuto` 里走 default → 被发成 `newbie_full` → ≥31 级号机器人端 `already_done` 跳过（"点了没反应"观感）；
4. 空账号=全部（含离线）→ 2MB 级抓鬼载荷对离线号也下发（占用控制通道 + 机器人端队列堆积）。

## 5. 风险清单

> 级别定义：**P0** = 会造成生产超编/掉线/数据错误，必须修；**P1** = 会造成可复现的重复派发/观感故障，建议本批修；**P2** = 取舍或提示即可；**P3** = 记录。

### R1（P1）新手链派发没有在途记账 → 连点重复下发 `start_chain`
- 证据：`handlers.go:513-514`（只对 ghost/newbie 做配额，但 `poolQuota` 的 inflight 只在 `KindGhost` 计算：`api/autotask.go:281-284`）。
- 最坏后果：连点 N 次 → 机器人端 pending 队列 N 条 `start_chain`；登录后重复应用（同链续跑，一般无害；若期间链上下文为空还可能重评估续跑）。
- 现有防护：配额按 target 截断（若 target>0）；机器人端"同链续跑/毕业跳过"。
- 建议：把 120s 在途记账扩展到 `start_chain`（`markChainDispatch`），或在 `tickKind`/`startAuto` 里对"最近派发过的号"做排除。

### R2（P1）autotask 候选与"在跑"口径都不含在途 → 手动派发后定时任务再派
- 证据：`api/autotask.go:401`（`isTasking` 只看运行时态）；`api/autotask.go:567-594`（`autotaskOnlineCount` 只数活跃会话；抓鬼无会话即不计）；`internal/services/autotask/autotask.go:346-386`（tickKind 用 `OnlineCount`，不查在途）。
- 最坏后果：手动派 100 个后，会话建立前的 90~120s 内若定时任务到点，`cur=0` → 认为缺口 100 → 每轮再派 `batch_max`（生产 10）个重复命令；抓鬼重复 = 会话重启（打断当轮）。这正是历史上"直派 + 定时 + RESTORE 叠加超编"的残余通道。
- 现有防护：`poolQuota` 只在 restorer 的 Skip 与手动通道里用；定时通道未接在途。
- 建议：`autotaskCandidates` 排除 `ghostInflight`（或 `autotaskOnlineCount` 计入在途），让定额判断与闸门同口径。

### R3（P1）「停止/停链」会被 restorer/autotask 立刻拉起（生产已开恢复引擎）
- 证据：`handlers.go:655-669`（stop 只 `cancelRegHost`）；`restorer.go:186-190`（IDLE/ONLINE → `needsRestore=true`）；`api/autotask.go:132-157`（Skip 不含"用户刚停过"）；`api/autotask.go:508-521`（`isTasking(IDLE)=false` → 候选）。
- 最坏后果：点"停止"后 ≤5s 被补发（restorer 首次无冷却）；用户以为"面板坏了"。
- 现有防护：restorer 只对"在线+闲着"补发；熔断/冷却；stop 会取消 reghost。
- 建议：二选一——① 面板文案明确"停止=停当前会话，自动编排会按意图再派"；② 增加"人工暂停"标记（stop 时打标、手动启动/恢复时清除），编排跳过。

### R4（P2）批量下线不取消 reghost → 卡死号被自动重登拉起
- 证据：`handlers_accounts.go:326-381`（`batchOffline`/`sendOfflineChunks` 无 `cancelRegHost`）对比 `handlers.go:750`（remove 有）、`handlers.go:660`（stop 有）。
- 最坏后果：用户下线一批号，其中当日卡死过的号被 reghost 重登 + 补发任务（"下线没效果"）。
- 建议：`sendOfflineChunks` 内统一 `cancelRegHost(accounts)`（与 remove/stop 同口径）。

### R5（P2）手动「立即补发」被池闸拦（与注释口径不一致）
- 证据：`handlers.go:169-223` 注释写"总开关关着也能手动触发"；但 `TickForce` 仍执行 `Skip`（`restorer.go:239-245`）→ `GhostSkipFunc` 首次判 `poolAllowsDispatch(kind)`（`api/autotask.go:139-142`）用的是**自动通道**语义（池停用 → 不补）。
- 最坏后果：面板点「立即补发」提示成功但实际 `sent=0`（"补发没用"观感）；不产生脏数据。
- 建议：`GhostSkipFunc` 增加 manual 参数（手动补发用 `poolAllowsDispatch(manual=true)`），或面板提示"池停用/满额时不会补发"。

### R6（P2）配额检查与发送非原子（并发窗口）
- 证据：`handlers.go:489-514`（查配额）→ `:516-532`（取 2MB 载荷）→ `:578-582`（SendCmd + 记账）之间无锁；`ctrl.SendCmd` 只串行化单条写（`ctrl/server.go:252-270`）。
- 最坏后果：浏览器并发两次请求（间隔小于窗口）+ 定时任务同刻 → 各派 ≤quota → 超编（历史上 11:49/13:10 两次 231 号即此类）。
- 现有防护：在途 TTL 120s 把窗口压到"同一瞬间"；同步 `markGhostDispatch`。
- 建议：`startAuto` 按 kind 加进程内互斥（或"乐观占位：先 mark 再发，失败回滚"）。

### R7（P2）手动批量上线不计入水位在途 → 短时超调
- 证据：水位 inflight 只记自己下发（`waterline.go:659-664`）；`batchOnline` 不下发记账（`handlers_accounts.go:263`）。
- 最坏后果：用户上线 100 个，水位看不到在途 → 每轮再补 ≤5 个（登录需数十秒）；随后水位又按差值压空闲号（用户看到"刚上就被压"）。
- 建议：手动上线也写入水位在途（复用 `waterline.NoteInflight` 之类）；或面板提示。

### R8（P2）手动派游荡被游荡池立刻回收
- 证据：`roampool.go:704-723`（`deficit>0 且 reclaim_on_deficit` → 立刻 Stop，生产 interval 10s）；`randomwalk.go:188+`（手动派发不看任务池缺口）。
- 最坏后果：用户刚把 10 个号派去游荡，<10s 被回收 5 个（max_step）→ "游荡派不进去"。
- 现有防护：回收资格闸只挑"回收后能进任务池"的号（`api/roampool.go:51-60`）；领双号优先回收去抓鬼（设计如此）。
- 建议：面板提示"任务池缺人时会立刻回收"；或给手动派发加"本轮豁免回收"。

### R9（P2）空账号=全部（含离线号）+ `zhuaogui` 意图回落默认链
- 证据：`handlers.go:432-447`（targets 含意图表离线号 + 在线）；`:472-480`（default 分支含 `zhuaogui` 与空 kind）；对比 restorer 支持 `zhuaogui → start_chain(zhuaogui)`（`restorer.go:205-206`）。
- 最坏后果：① 捉鬼链意图号被判成新手链 → `already_done`（"没分配"）；② 离线号也收大载荷（带宽/队列）。
- 建议：`startAuto` 补 `zhuaogui` 分组；面板把"空=全部（含离线）"写清楚（ChainView 输入框已有"空=全部"，但没提离线）。

### R10（P2）写接口默认无鉴权
- 证据：`config.go:407-420`（`CHANGE_ME*` 占位视为未配置）；`api.go:230-241`（未配置 token = 不校验）；`config/switch` 甚至不挂 `requireToken`（`api.go:186`）。
- 最坏后果：同网络任意客户端可调用全部写接口（重置/重启/清空/下线）。
- 建议：生产填真实 `api_token`；至少给 `config/switch` 也挂上（低风险但会改变编排口径，见 R11）。

### R11（P3）切区会在编排运行中改变"当前区"口径
- 证据：`handlers_config.go:87-115`；各 keeper 用 `currentZoneKey()` 过滤（`api/waterline.go:57-71`、`api/roampool.go:63-77`）。
- 最坏后果：切到无号新区后，水位可能按新区地址补号（每轮 ≤5）；机器人仍在旧区 → 期望与现状不一致。
- 建议：面板切区后提示"需 apply+重启机器人生效"（已有部分文案）。

### R12（P3）机器人端 pending 队列无去重/无上限
- 证据：`client.py:370-503`（`g_pending_cmds.setdefault(...).append(cmd)` 无去重；`apply_pending_cmds` 逐条执行）。
- 最坏后果：对离线号反复下发命令 → 队列堆积，登录后逐条重复应用（重复 `ghost_start` = 多次会话重启）。
- 建议：中控侧对离线号少发（R1/R9 的修复会顺带缓解）。

## 6. 安全判定表（给用户直读）

### ✅ 随便点（幂等/只读，连点无副作用）
- 各页「刷新」、筛选、翻页、地图可视化；`GET /api/status|chains|maps|accounts|autotask|waterline|roampool|intents`。
- 地图页：**批量游荡 / 分配到所选图 / 停止游荡**（机器人端 `random_walk` 同图重复=刷新或忽略、跨图途中忽略；孵化 `hatch_start` 同蛋同图只回执不重启）。
- 任务页：「立即跑一轮」（有 `next_at` 闸，连点第二次已过时）、「立即补发」（300s 冷却 + 熔断；只补在线且闲着的号）。
- 大屏：行内启动/停止/行内移除，重复点基本无害（抓鬼有在途+配额；移除幂等）；「清空已移除名单」安全（当日满额号仍被挡）。
- 账号池：加号入池（已存在计 existed）、批量上线（机器人端去重）。

### ⚠️ 可以点，但要知道后果（会触发编排/有代价）
- **「启动链路自动分配」/「全部启动」**：会再次下发一轮（抓鬼重启在跑号的会话；新手链重复发但续跑）；空账号=全部（含离线）。
- **「停止 / 停链」**：会取消卡死重登，但**会被恢复引擎/定时任务按意图再拉起**（生产已开 `CTRL_AUTO_RESTORE=1`）→ "停不住"是预期行为。
- **批量下线**：会被水位/定时任务按缺口再补号；当日卡死过的号可能被重登拉回。
- **移除 / 移除掉线**：进"已移除名单"，之后不会被自动拉起；要恢复得点「清空已移除名单」。
- **水位/游荡池开关与目标**：立即驱动上下线（水位 230/游荡 130，单轮 ≤5/≤10）；调小目标会立刻压号下线。
- **切区**：编排口径随"当前区"变化；真正切换要「应用到机器人 + 重启」。
- **清空日志**：只影响观察（但丢排障证据）。

### 🚫 别乱点（破坏性/全局影响）
- **重置重跑**：清该号链路进度、从起点重来（面板有二次确认；已毕业号机器人端会拒绝：`quest_engine.py:3863`）。
- **重启机器人** / **应用到机器人（勾重启）**：全部号掉线重连（几十秒到几分钟恢复，靠水位与定时任务重推）。
- **热更脚本**：只在任务间隙用；协议/框架层已被拦截，其余模块 reload 可能影响运行中实例。
- **删除服/区**、**从池删除账号**、**未配置 api_token 时对外暴露面板**（同网段任何人可操作）。

**语义变更（用户可感知）**：
1. 点「停止 / 停链」后，号会被标记为**人工暂停**：恢复引擎、定时任务、水位、游荡池都不再自动派它，直到再点「启动 / 立即补发 / 上线」。
2. 「启动(自动分配)」对 **120 秒内已派发过**的号会跳过并回带原因（不再重复下发；抓鬼原先重复=机器人端重启会话）。
3. 批量下线（含水位压号）现在也会取消"卡死自动重登"（此前只有「移除」和「停止」会取消）。
