## 5. 并发/状态核对与 resume 交互（读码论证 + 链路测试）

### 5.1 换出后现场（状态快照语义）

- `RestoreCapped` 来自 `State.Snapshot()` 的 overlay（state.go:839-844，独立 `restoreCap` 表，跨日 0 点惰性失效）；换出走 `sendOfflineChunks`（handlers_accounts.go:521-547）= `cancelRegHost + MarkRemoved + Remove(删行) + robot_manage remove`。
- 实测链：换出后 `IsRemoved=true`、`Has=false`、**`IsRestoreCapped=true`（熔断表不被解除）**、轮换名单 1 条。熔断表独立存活 ⇒ 该号不会因"删行→计数归零"被 reghost/restorer/autotask/roampool 重新拉起（autotask.go:752、roampool.go:67/137、rescue48.go:58 均按 IsRestoreCapped 跳过）；水位器也不拉（在移除名单且非 waterline 自压号，waterline.go:139-141）。

### 5.2 用户 resume（POST /api/reghost/resume）的实际行为链条

1. `uncapAccounts`（autotask.go:1490-1516）：清熔断表 + 清行内卡死计数 + 取消 reghost 条目 → `RestoreCapped=false`。**不解除 removed**（state.go:1018 的 UnmarkRemoved 不由 resume 调用）。
2. 因此 resume 后：止损通道不再匹配（RestoreCapped=false），但号仍 `MarkRemoved` 且无行 → 既不会被止损换出，也不会被常规通道换出/拉起；**两条出路**：
   - 到龄回池：`rotationReturnAged`（KeepHours=24h）→ `UnmarkRemoved` → 水位器按"最久未上线优先"拉起；
   - 手工/机器人上线：`/api/robots/unremove`（handlers.go:1311）或机器人真的重新上线（event.go:696 `onRobotOnline → UnmarkRemoved`）。
3. 号回常规候选体系后按**常规条件**竞逐（满额+纯游荡+30m+…）。本通道不做任何"记忆"。
- 链路测试（独立）：resume 后 `resumed=[cand]`、熔断清、removed 仍在、名单不动；unremove+建行后 `Candidate` 返回 false·"今日抓鬼未满"（常规判据）；`store.Aged(now+25h)` 含该号（不 resume 也可回池）。无冲突。

### 5.3 窄窗口竞争（P2，非阻塞）

- resume 与 tick 并发：tick 的候选判定基于 tick 开头快照（`snap`），若 uncap 落在"快照后-执行前"（单 tick 毫秒级窗口），该号本轮仍会被换出；后果可逆（仍在轮换名单，24h 到龄/手工 unremove 可回）。反向（uncap 在快照前）则本轮不动作。
- 跨日亚秒窗口：快照在 0 点前（capped=true）、执行在 0 点后（熔断刚失效）→ 仍按止损换出。概率极低、后果同上，可接受；如需绝对严谨可在 sendOfflineChunks 前复核 RestoreCapped（非必需）。

### 5.4 与"今日 25 个熔断号已 resume"的现场一致性

- 熔断号 resume 后 RestoreCapped=false → 止损通道不再命中，号回常规体系按常规条件竞逐 —— 本改动与 resume **无冲突**（两通道互斥：capped=true 走止损、=false 走常规）。
- 生产日志佐证：08:16-08:41 轮换摘要持续出现"当日卡死熔断×19/20"（旧版一律拒）；08:49 降至"当日卡死熔断×1"（与批量 resume 吻合）。今日 `data/rotation.json` 已有 entries（今日轮换下线 79 次）。**注意：现行日志仍为旧编译产物**（无"熔断·止损换出"字样），与"待重新编译+温重启"状态一致。
