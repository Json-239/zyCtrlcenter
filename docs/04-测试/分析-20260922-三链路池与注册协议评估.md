## 二、三链路批次池设计（推荐落法）

**总原则：任务链路优先，游荡吃余量；名额由"池目标"分配，不靠人手动点。**

```
在线总数（水位，例：200）
├─ 抓鬼池 ghost   target = 150   ← 任务链（消耗：助战令已去掉，无前置门槛）
├─ 新手池 newbie  target = 30    ← 任务链（等级 < 31 走新手链）
└─ 游荡池 roam    target = 余量   ← 兜底业态：任务池用不上的号去游荡打野
```

**调度规则（每 60s 一轮）**：
1. 先满足任务池：`ghost.deficit`、`newbie.deficit` > 0 时，**从游荡池回收** ——
   对正在游荡的号下发 `random_walk_stop`（"回收游荡"）→ 再派任务；
2. 若任务池仍缺 → 从"空闲在线号"补（现有逻辑）；
3. 任务池都满足后，剩余空闲号 → 派游荡直到 `roam.target`（或"所有空闲号都游荡"）；
4. 水位负责"总在线数"，三层互不打架：`水位 ≥ ghost + newbie + roam`。

**实现要点（Go 侧，需重启生效）**：
- 给 autotask 增一个 kind `roam`（复用现有池框架：`running` = 上报 `walk.enabled` 的号数）；
- 回收动作 = 现有 `/api/random_walk/stop` 的同一实现（抽成内部函数，别走 HTTP 自调）；
- 优先级常量：`ghost > newbie > roam`；
- 面板：大屏"池"卡片展示三池 running/target/deficit（现成结构上扩一列）。

> 当前状态：**已能达成近似效果**——ghost=150 + newbie=30 由 autotask 保持，剩余空闲号由今天的"空闲自动游荡"自动去游荡 ✓；
> 差的是"**游荡名额可控 + 任务缺人时主动回收**"这两点。

## 三、机器人注册协议评估

### 3.1 现状与瓶颈
- 现有链路：中控直连游戏服 `106 → 104 → 700`，字段固定 8 个：
  `[验证码, 账号, 密码, 确认密码, 激活码, 姓名(可放 agent_key), 身份证, QQ]`；
- 已知风控：**同 IP 过频 → 112**（因此有 并发 ≤8、批量 ≤20 的保守限制）；
- 服务端注册处理器在 **C++ login_server**（`login_server/`），Python 侧无注册逻辑 → 风控规则**改不动**（要么改 C++，要么绕）。

### 3.2 三条可选路线（按性价比排序）

**A. 服务端加"内部建号接口"（最稳，推荐）**
- 照抄 `/gm/online` 的模式：`POST http://<游戏服>:8080/gm/register`，带 token + `account/password/agent/serverId`；
- 服务端直接落库（跳过验证码/身份证/风控），返回结果；
- 我们中控加一个 `register` provider（默认关闭 + 限速），批量建号变成普通 HTTP 调用：
  **快、稳、可限速、可观测**，且与现有 `livecount` 同一套模式（改动量小）。
- 需要服务端侧实现（你/运维）。

**B. 不改服务端：把注册"分散化 + 自适应限速"（可立刻做）**
- 现状基础上加：① 失败(112)自适应降速（连续 112 → 并发减半/批间隔翻倍，成功后再回升）；
  ② 建号任务排队 + 错峰（例如每批间隔 3~10s 抖动）；③ 统计 112 率；
- 若能配置**多出口 IP**（多网卡/代理），轮流建号 → 绕开"同 IP 频控"（需网络侧支持）；
- 局限：验证码/身份证等字段仍要按客户端规则填，风控策略若变（如加设备指纹）会再受限。

**C. "机器人自注册"（把注册下放到机器人进程）**
- 由每个机器人进程自己跑 106/104（而不是中控集中建）→ **时序/连接特征天然分散**；
- 但仍受"同 IP 频控"约束（除非机器人分布在多台机器/多出口）；
- 价值：把建号并入机器人链路（新号注册完直接登录做新手链），减少中控耦合。

### 3.3 建议
1. **立刻**：先落 **B 的自适应限速**（改动小、当天可做）；
2. **与运维确认**风控判据（是否只看 IP？是否看 UA/设备码/验证码？）→ 决定是否需要 A；
3. 若确认走 A：我这边把客户端（配置 + 限速 + 重试 + 落库）先写好，服务端接口一旦就绪即可切换。

## 四、需要你确认的三点
