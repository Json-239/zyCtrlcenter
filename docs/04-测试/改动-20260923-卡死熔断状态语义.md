# 改动-20260923：卡死熔断后的状态语义（capped：明确"等次日"+ 不再空转 + 可手动解除）

> 现场入口：`robot0001009@xy3.com` 今天多次卡死 → 自动重登 3 次 → 中控日志
> `[REGHOST] robot0001009@xy3.com 跳过重登：当日卡死已达上限 3 次（状态 WAIT_NEXT 重试 4 次仍无进展）`
> → 之后**再无自动恢复动作**，账号一直停在 `ERROR` / `err_code=STUCK_WAIT_NEXT`
> （在线、占水位、不产出；面板看不出"已熔断等次日"）。
>
> 本次（Go 侧，**未部署**）：给这类号一个显式语义 `restore_capped` + `cap_until` + `cap_reason`，
> 让调度侧"据此停手"有单一权威判据，并给出手动解除入口。**不改机器人端、不改抓鬼业务口径。**

## 一、链路分析（卡死 → 重登 → 计次 → 触顶跳过）

| 步骤 | 位置 | 行为 |
|---|---|---|
| ① 机器人上报卡死 | `error{code:STUCK_*}` | 机器人端看门狗/抓鬼在多次无进展后上报（如 `STUCK_WAIT_NEXT`） |
| ② 计次 | `internal/services/event/event.go:678-694` | `isStuckCode`（event.go:713-719）命中 → robot 行内 `StuckDay/StuckCount++`（**不随进度清零**，跨日重置） |
| ③ 触发重登 | 同上 690-694 → `reghost.Request` | 下线（`robot_manage remove`）→ 等摘掉 → 重登（`add`）→ 延迟 8s 补发任务 |
| ④ 触顶判定 | `internal/services/reghost/reghost.go:139-159`（旧 144） | `StuckCount >= ChurnLimit(3)` → **跳过重登**（旧行为：记一条 `failed` 状态 + 一行日志） |
| ⑤ 之后 | — | 没有任何后续动作：不重登、不补发、不再上报"为什么"（10 分钟后连那条 `failed` 也过期清掉，`reghost.go` step 的 `PhaseDone/PhaseFailed` 分支） |

### 计数口径（现状）
- **存哪**：`state.Robot.StuckCount/StuckDay` —— **内存、随 robot 行**。中控重启清零；行被删也清零
  （`event.removeAccount` → `St.Remove`；`pollOnce` 陈旧清理同样 `St.Remove`，见 event.go:806-813、882-888）。
- **口径**：按号按天（`StuckDay == 今天` 才认），跨类卡死**共用一份计数**（`GHOST_DIALOG_STUCK` /
  `TASK_STUCK` / `STUCK_*` 一律计入，见 `isStuckCode`）。

### 触顶后各模块的实际行为（现状）
| 模块 | 行为 | 判定依据 |
|---|---|---|
| reghost（重登） | 不再重登；只记 10 分钟的失败条目 | `StuckCount >= 3` |
| restorer（补发） | 不补发（该号 `state=ERROR` 本身 `needsRestore=false`；即便回到 IDLE/DIALOG，`Skip` 闸也会按 `stuckCountToday>=3` 拦） | `restorer.go:185-203` + `api/autotask.go:159-163` |
| autotask（候选） | 不进任何池的候选 | `api/autotask.go:542-548` |
| 在跑/在途额度 | **不占**：`autotaskOnlineCount` 按活跃会话计（无会话=不在跑）；在途表无记录 | `api/autotask.go:718-745` |
| 水位/游荡 | `waterline.Busy(ERROR)=true` → 不派活、不回收、不派游荡；但号**在线就占水位名额**（水位=在线数） | `waterline.go:443-454`、`roampool.Idle` |
| 面板 | `/api/status` 只见 `state=ERROR`/`err_code`；`/api/autotask` 的 reghost 列表 10 分钟内有一条 failed（之后消失） | — |

## 二、现状问题清单

1. **可观测性差**：触顶的"为什么"10 分钟即消失（`failed` 过期清理）；面板只能看到 ERROR，分不清
   "卡住等人工"与"已熔断等次日"。
2. **无恢复路径**：跨日才自然恢复；期间无任何提示/入口。手动「立即补发」会被 Skip 闸拦下且**不被告知**
   （restorer 只在自身 Status 里记 `LastMsg`，接口响应无痕迹）→ 观感"点了没用"。
3. **计数易丢 → 熔断会"漏"**：`StuckCount` 随 robot 行存活，行被删（陈旧清理/下机）或中控重启即归零 →
   同一天又给 3 次重登机会（今天 50 个号被"跳过重登"，重复日志 167 条，说明反复回到触顶）。
4. **计数>=3 却无熔断记录**：第 3 次卡死事件若落在上一轮重登的冷却窗口内，会被冷却去重**吞掉**触顶判定
   → `StuckCount=3` 但既没有熔断记录也没有关闭动作，调度侧静默拦死（无法解释）。
5. **占水位**：卡死号在线时计入"在线数"，水位保持器认为达标 → 不会补新号（名额被不产出的号占着）。
   本次**不改**水位语义（水位=在线数），只登记为已知项。

## 三、方案与实现（最小改动，Go 侧）

**语义**：当日卡死触顶 → `restore_capped=true`（熔断到**次日 0 点**，`cap_until`），期间
"不再自动重登/补发/进候选"；到期（跨日）/中控重启/手动解除后自动清零。

| 文件 | 改动 |
|---|---|
| `internal/state/state.go` | 新增独立表 `restoreCap`（account → {Until, Reason, At}，与 `paused`/`ghostUnavail` 同款，**不存 robot 行**）+ `MarkRestoreCapped/IsRestoreCapped/RestoreCapInfo/RestoreCappedList/ClearRestoreCapped/ClearAllRestoreCapped/ClearStuckToday`（595-700）；`Robot` 加 `restore_capped/cap_until/cap_reason` 三字段（Snapshot 填充，跨日惰性失效）；`/api/status` 顶层加 `restore_capped[]` |
| `internal/services/reghost/reghost.go` | 新相位 `capped` + `CapUntil` 字段；`Deps` 加 `Cap`（写熔断表）/`Capped`（入口闸）；触顶改为 `markCapped`（明确文案"熔断到 X 自动恢复"，首次触顶打日志、重复上报静默）；**触顶判定提前到冷却去重之前**（解决问题 4）；`capped` 条目跨日自动清除（step，332-343） |
| `internal/api/autotask.go` | `ReghostDeps` 注入 `Cap/Capped`；`GhostSkipFunc` 加熔断闸（**对所有 kind**，与人工暂停同层）；`autotaskCandidates` 加熔断过滤；新增 `handleRegHostResume`（POST `/api/reghost/resume`，单个/全部解除）+ `uncapAccounts`（清熔断表 + 清行内当日计数 + 清 reghost 条目） |
| `internal/api/handlers.go` | `handleIntentsRestore`：指定 `account` 的「立即补发」= **顺带解除该号熔断**（回带 `uncapped`）；全表补发**不**批量解除，但把被拦号列在 `capped_skipped`（不静默） |
| `internal/api/api.go` / `protocols.go` | 路由与协议映射文档 |

### 额度口径（明确）
- **不占在跑额度**：无活跃会话，`autotaskOnlineCount` 不计；**不占在途额度**（不会被派发，也没有在途记录）。
- 池配额计算不受影响（`poolQuota = Target - 在跑 - 在途`，熔断号不在这两项里）。
- 熔断号若**在线**仍占作业系统"在线水位"（既有语义，未改）。

### 解除路径（三选一）
1. **跨日自动**：`cap_until = 次日 00:00`，到期惰性失效（reghost 条目同时清除）。
2. **手动单个/全部**：`POST /api/reghost/resume {"account"?}`（省略=全部）。
3. **指定账号补发**：`POST /api/intents/restore {"account": X}` = 解除 + 立即补发（用户显式要救它）。

## 五、影响评估

- **对"待恢复"**：熔断号在 `/api/autotask.reghost[]` 里的条目从"10 分钟后消失"变为**保留到跨日**
  （面板/接口能一直看到"等次日"）。修 restorer 的 `LastMsg` 也会写明"不补发：当日卡死已熔断…"。
- **对水位**：无变化（水位=在线数）。已知项：熔断号在线占名额（见问题 5）；需要换号可手动下线 +
  批量上线（或后续做"熔断号自动下线"，本次不做）。
- **对池**：无变化（不占在跑/在途额度）；三池候选均排除熔断号（新增，原只有 StuckCount 判据）。
- **行为变化**（需要知晓）：
  1. 触顶判定提前到冷却之前 → 第 3 次卡死**立即熔断**（不再可能被冷却吞掉）；
  2. 熔断**跨 robot 行删除存续** → 同一天不会因"删行/重启候选清理"再获得 3 次重登机会（重启中控仍会清空内存表）；
  3. 熔断闸对所有 kind 生效（含新手链/孵化）；「立即补发（全表）」对熔断号不再生效但会明确回带名单。
- **前端**：**需要配合才好用**（本次只报告，未改 `web/`）：① 面板标识"已熔断等次日"（读
  `restore_capped/cap_until/cap_reason` 或 `/api/status.restore_capped[]`，把 ERROR 桶里这类号单列/加标签）；
  ② 加「解除熔断」操作（调 `POST /api/reghost/resume`）。接口已向前兼容（新字段/新接口，不改老语义）。
- **今天受影响账号数**（20:30 口径）：
  - 实时仍卡死且已触顶：**1 个**（`robot0001009`，`online=true`、`STUCK_WAIT_NEXT`、`stuck_count=3`）；
  - 当日 `stuck_count>=3`（触顶过）的号：**8 个**（`1009/1111/1113/1116/1147/1195/5046/5190`，
    其中 7 个当前在 NAV/SUBMIT/WAIT_GHOST/DIALOG 干活 —— 说明是"触顶后又自愈/被其它路径拉起"）；
  - 今日日志"跳过重登"：**167 条 / 50 个不同账号**（`logs/ctrlcenter_20260923.log`）—— 平均
    3.3 条/号，即触顶后被反复跳过（本次改动后每号只剩首次一条日志，其余静默）。
