## 0. 结论速览（先看这段）

1. **不是"不再补派"，而是"候选池只剩 1 个、且那 1 个是已在跑的号"**：shenbu 配额 = target5 − 在跑4 = 1，
   每轮（300s）从候选里挑 1 个"补位"，但挑中的是**已在大唐神捕里的号**（ACCEPT/KILL 相位不算"忙"，
   waterline.Busy 白名单没有 share_daily 相位）→ 重派被机器人端幂等吸收（no-op）→ 名额永远填不上。
2. **真·候选源被三道闸门压到 ≈0（live 量化）**：
   - 等级闸（sharedaily.go:430，min_level=40）×**账号池等级字段是陈旧垃圾**：当前区池记录 <40 有 **4893 个、≥40 只有 4 个**；
   - 余额闸（sharedaily.go:436，balance_gate=1000 按 `r.Money`=银两）：在线 230 里 **227 个 0<money<1000 被挡**；
   - 让路+在跑闸：在线抓鬼满额 161 个，其中 **157 个在游荡**（isTasking 挡）；满额+非游荡+过余额闸 = **2 个**。
3. **17:39 重启后 5165/5167/5176/5240 没被补拉 = 成立**，确切机制：
   它们**池内当前区等级 = 1/10/33/32（<40）**（accounts.json）；一旦 Store 无行（中控 17:39:37、
   20:25:07 两次重启清空内存），候选判定回落到池内陈旧等级 → 直接进不了 shenbu 候选；
   而能救的其它路径：restorer **只对在线号补发**（restorer.go:276 离线静默跳过）、
   waterline 只在**低于在线目标**时拉号且"最久未上线优先"（轮换反而把它们排到老死号后面）；
   对照实证：池内等级 45/41 的 **5274/5256 在 20:25/20:30 被池成功补拉**（"挑中 1 个（上线 1/1）"），
   池内等级 1/10/33/32 的四号零动作——同夜、同池、唯一差异=池内等级。
4. **台账不占配额**（在途记账 TTL 仅 120s；配额按"心跳在跑数"算）——"已派台账占名额"的猜想不成立；
   但**意图表会随中控重启 + 无心跳而消失**，restorer 从此连遍历都不到它们（17:39:50 是 5165 的最后一条 RESTORE-SKIP）。

## 2. 直接原因：为什么补不到 target=5（逐项排除）

**排除 A：target=5 是硬上限？** 不是。配额=5−4=1>0，池每轮都在"派"（21:00 还 `已下发…5232`）。
**排除 B：已派台账占名额？** 不成立。配额只看"心跳在跑 + 120s 在途"；持久台账不参与配额
（充其量在候选里"放行续跑"，是帮助不是阻碍）。
**成立 C：候选池≈空 + 假补位。** live 证据链：

1. `/api/autotask`（21:0x）：`candidates.shenbu=1`、`pools.shenbu={running:4,target:5,deficit:1}`；
   最近 4 轮（20:25 5274 / 20:30 5256 / 20:55 5326 / 21:00 5232）**每轮只挑到 1 个**并"已下发"。
2. 被挑中的 4 个**全部是正在跑的号**（`/api/status`：5232 ACCEPT、5256 KILL、5274 ACCEPT、5326 ACCEPT，
   心跳 daily 均在）——它们能被当候选，是因为 **ACCEPT/KILL 不在 `waterline.Busy` 白名单**（#9），
   `isTasking` 判"没在忙"；重派到机器人端=同会话"重复启动"被幂等吸收 → **假动作**。
3. 真候选源量化（21:0x live）：
   - **等级闸**：池内当前区记录等级 `≥40` 仅 **4 个**（4893 个 <40）——而**离线号只能用它**（无心跳覆盖，
     `autotask.go:687-700` 的 level 回落链）；
   - **余额闸**（balance_gate=1000，`r.Money`=银两）：在线 230 个里 **227 个 0<money<1000 → 挡**；
     运行中的 5256（money=19）/5274（money=36）印证"小额银两"是常态；
   - **让路/在跑闸**：在线抓鬼满额 161 个，其中 **157 个在游荡（walk）→ isTasking 挡**；
     满额+非游荡+过余额闸的仅剩 **2 个**——与 `candidates.shenbu=1` 数量级吻合。
4. 结论：**deficit=1 每轮被"在跑号重派"消费掉，真正的补位候选≈0**；分子（在跑）卡在 4 不动。

## 3. 重启补拉缺口：5165/5167/5176/5240 为什么没回来（确切代码点）

时间线（日志）：
- 17:39:37 中控重启（+机器人重启〔组队阶段2〕）；17:39:40 四号心跳重建意图 shenbu；
  17:39:50 5165 最后一条 `[RESTORE-SKIP] 闸门跳过：shenbu 池配额已用满（在跑 5+在途 0 ≥ 目标 5）`；
- 之后四号**零日志**（bot 日志同在 17:39:5x 截止，最后状态是"集合走…等中控重派"的僵尸会话刷屏）；
- 20:25:07 中控再重启 → Store/意图表清空重建；四号无心跳 → **无行、无意图**。

代码层，四号重回自动链需要闯过：
1. **候选池**（`autotask.go:663` 遍历账号池）：在池 ✓（accounts.json 有当前区记录、usable=true），
   但 `:687-700` 等级回落 = **池内 zone-record level**（`data/accounts.json.zones["47.96.8.240:2400"].level`）：
   5165=**1** / 5167=**10** / 5176=**33** / 5240=**32** —— 全部 <40 → `sharedaily.go:430` 等级闸直接淘汰。
   （对照：同一晚被成功补拉的 5274=**45**、5256=**41**——唯二 ≥40 的台账号。）
   > 池内等级只在**建号/验证**时写入（`handlers_verify.go:331-353`、`handlers_create.go:464/579`），
   > **心跳等级从不回写池**（event.logLevelUpdate 只打日志）→ 池里的等级是"当年快照"。
2. **恢复引擎**（唯一带 shenbu 语义的在线补发）：`restorer.go:276 if !ok || !robot.Online { continue }`
   —— **离线号静默跳过**（连 RESTORE-SKIP 都不落）；且中控重启后意图表里也没有它们（无心跳重建）。
3. **水位补号**（唯一的 add 通路之一）：`waterline.go:420 PickOnlineCandidates` 只在"低于目标"时拉，
   且"**最久未上线优先**"（:424-426）——刚掉线的号排在"离线数天/从未上线"的号后面；
   当前在线 230 ≈ 目标 230±3（死区）→ **无压力、不拉**。
4. **池派发**：候选进不去（#1），`Online(kind,accs)` 的"上线步"自然轮不到它们。
→ **结论：'重启后已派号不补拉'成立**；闸门组合 = 「等级回落池陈旧值（<40）+ 离线即出候选」
（`autotask.go:687-700` × `sharedaily.go:430`）+ 「restorer 离线跳过（restorer.go:276）」+ 「水位无压力不拉」。
另有隐性：**5232/5326 池内等级 31/35 也在 40 以下**——这两号一旦掉线且无心跳，**会以完全相同的方式再陷一次**。

## 4. 修法候选（按影响面/风险排序；未改码）

### 候选①（最小、直击死结）台账号等级豁免 / 池等级回填
- 落点 a：`sharedaily.go:430`——**"已派（心跳或持久台账命中）"的号不受等级闸硬拦**
  （它们今天已在跑，服务端票条件必然已过；等级准确性交给接取时服务端校验）。
  行为变化：台账号离线也能进候选 → 被池"重新上线+续跑"（与 5256/5274 同路）。
  副作用：极少数极端号可能被派后服务端拒（机器人停+上报，可观测、可逆）。
- 落点 b（更彻底、建议同时做）：**心跳等级回写账号池 zone 记录**（event 心跳 / `autotask.go:697` level 处
  → `Accounts.SetZoneStateNoSave(acc, addr, ZoneState{Level: lv, ...})` 合并写，落盘节流）。
  行为变化：任何号"上线过一次"后，池内等级=真实等级，离线回落不再是垃圾值（4893 个陷阱随在线潮自然消解）。
  副作用：池文件写入频率升高（需合并+限频，参考 SetZoneStateNoSave 的批量写回机制）；
  与 verify 写入的权威性需约定（心跳级只在"较大且合理"时更新，沿用 LEVEL 回退防抖口径）。
### 候选②（解"重启缺口"）离线台账号定向补拉
- 落点：`restorer.go:276` 的离线分支——意图/台账命中且**离线超 X 分钟**（如 10min）→ 触发一次
  `robots_manage add` 补拉（复用 `sendOnlineChunks`；按号 1 小时冷却；跳过暂停/移除/熔断）。
  或更小改动：在 `api` 侧做一个 30min 周期巡检：`shareDailyAssignedToday ∧ !Online ∧ ¬Paused ∧ ¬Removed`
  → 走批量上线通路（与水位互补：水位管"总量"，这里管"已派台账欠账"）。
  副作用：与水位/池的"上线"重复（机器人端 add 幂等，仅多几行日志）；补拉的号若已不可用会再次掉线→冷却兜住。
### 候选③（制止假动作 + 报表真实）Busy 补 share_daily 相位
- 落点：`waterline.go:493 Busy` 白名单加 `ACCEPT/KILL/READY/WAIT_GHOST` 之一组（share_daily 运行相位；
  建议先只加 `ACCEPT/KILL`，与 ghost 的 ACCEPT/HEAL 注释对齐）或 `sharedaily` 在候选外层加
  "心跳 daily 在跑（未满）→ 不算候选"。
  行为变化：在跑号不再被当候选重派；deficit/候选数变成真话（当前 deficit=1 的"1"会变成真缺）。
  副作用：**需同步复核 restorer/水位/游荡等所有 Busy 消费方**（Busy 是全局"别打扰"判据；
  walk/ghost 已覆盖的语义不受影响；把 share_daily 号标忙=行为加强，方向安全）。
### 候选④（需产品确认）余额闸口径
- `balance_gate=1000` 用**银两**（`r.Money`），全池 227/230 小额 → 几乎全员被挡；
  而实际"传送费"消耗的是银两/开元（teleport 计价）。建议复核：阈值是否应为 100~200 量级、
  或改看 `reserve`/`kaiyuan`、或仅"钱包=0"才拦。**这是口径决策，不是纯 bug**。
