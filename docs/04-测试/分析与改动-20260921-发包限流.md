## 3. 峰值 QPS 估算

**方法**：走路时每号按 `config.quest_walk_report_interval_sec = 0.1`（10 Hz）发 `C2S_NOTIFY_POSITION`；
把"走路段距离"按 `quest_walk_speed*60 = 120 px/s` 换成走路秒数，×10 得位置包总数。

```
16:34–20:01 全量（跨度 12,414 秒）：走路 28,931 段，距离总和 30,101,665 px
      → 走路总时长 ≈ 250,847 秒（跨所有号累计）
      → 位置包 ≈ 2,508,472 个 / 12,414 秒 ≈ 202 包/秒（全局平均）
```

| 指标 | 估算值 |
|---|---|
| 全局平均 QPS（含全部包类） | **≈ 203 包/秒** |
| 其中 `C2S_NOTIFY_POSITION` | ≈ 202 包/秒（**≈ 99%**） |
| 高峰时段（17–18 时走路量约为均值 2 倍） | **≈ 300–400 包/秒** |
| 单号实测（5 号抽样） | 0.29–2.88 QPS（走路占空比 3%–28%）；活跃抓鬼号 ≈ 1–3 QPS |
| 其余包类合计 | 约 4–5 包/秒（click 1.2 + dialog 0.5 + playermove 1.3 + dijkstra 1.6） |

> 注：tick 实测有卡顿（`STEP_GAP` 事件 42,782 条，间隔 0.43–0.49s），实际位置包频率可能低于 10 Hz；
> 上表为"按配置上限"的估算，真实值可能打 3–5 折（**保守估计全局 50–200 包/秒**）。方向一致：位置包是绝对大头。

- 有钟馗对话的号 **97 个**，其中 **95 个（98%）出现过空菜单**；

### 5.3 结论

1. **数据不支持"瞬时并发号数越多 → 服务端越忙 → 空菜单越多"**：号最多的 16:30–16:50 空菜单率最低（11.5%–13.6%），号更少的 18–19 点反而 25%–30%。
2. 负相关更可能是**反向因果**：空菜单 → 号被重登/停摆 → 活跃号数下降（16:40 的 270 号 → 19:50 的 213 号，少掉的正是被吃掉的号）。
3. 空菜单呈现**时间台阶**：17:20 前 11%–21%，17:30 后稳定 25%–30% —— 更像**服务端侧的时间性/状态性因素**（当日累计负载、连接/内存劣化，或服务端自身 bug），与瞬时发包量无直接相关。
4. **给主控的行动项**：建议在服务端侧（4核4G 那台）核对 **17:20–17:30 前后**的 CPU/内存/连接数曲线；若曲线无异常，则空菜单根因更可能在服务端逻辑/数据侧，而非客户端发包压力。

## 6. 改动 1：钟馗点击最小间隔（daily_ghost.py）

**数据支撑**：同号相邻两次「点击NPC 10146」间隔分布（n=4175）：`<1s 17.4%`、`<2s 37.4%`、`<3s 41.3%`；同秒连点簇 33 个（>=3 连点），其中 **>=8 连点的簇 17 个（最大 18 连点）**，且 14 个集中在 **17:20:09–17:20:20 的 11 秒内**（robot0001187 单号贡献 12 个，约 170 次点击）。这些连点：①纯无效重复包；②快速消耗 `broker_nodlg`（同秒连点 8 次无对话即误判"服务端对话卡死"触发重登）。

**改动**（3 处，见 diff）：

```python
# 常量区
BROKER_CLICK_MIN_GAP_MS = 1200   # 同号两次"发射钟馗点击"最小间隔

# GhostState.__init__（不随 reset 清: 重登后也不该立刻连点）
self.broker_click_ts = 0

# __goto 钟馗分支入口（在 __check_broker_nodlg 计数之前!）
if npc_id == BROKER_NPC_ID and g is not None and getattr(g, "enabled", False):
    _now = __now_ms()
    _last = float(getattr(g, "broker_click_ts", 0) or 0)
    if _last and (_now - _last) < BROKER_CLICK_MIN_GAP_MS:
        __log(..., "钟馗点击节流: 距上次 %.2fs < %.1fs, 跳过本次")
        return                      # 不发包、不计 broker_nodlg
    g.broker_click_ts = _now
    if __check_broker_nodlg(robot_object, g):
        return
```

**为什么它能降 QPS 且不影响产出**：
- 被拦的是"亚秒/同秒重复"，正常接取流程的对白轮次点击实测间隔 ≥1 秒（1.2s 不误伤）；最坏情况单次点击延迟 1.2 秒；
- 拦下的点击**不发包、不计** `broker_nodlg` → 直接消除"连点把 8 次无对话计数耗光"的误重登（当天 98 次"连续无对话"重登中的一部分）；
- 预期降幅：钟馗点击包 **-17.4%**（<1s 的亚秒重复全部拦下；全局占比 <0.1%，属"消除纯无效包+防误重登"，不是主要降幅项）。

## 7. 改动 2：跨图被拒后的递增退避（quest_engine.py）

**数据支撑**：destination 被拒 11269 次（57.4% 拒绝率）；同号相邻两次被拒 **97% 间隔 <2 秒（中位数 1 秒）**——被拒后 `300ms` 立即重走/重发，位置未变又被拒（服务端每次都要做一次路径校验再拒绝）；连拒 3 次拉黑后**立即**换跳转点重新规划（10681 次）。

**改动**（3 处，见 diff）：

```python
# 常量区 + 纯函数
HOP_RETRY_BACKOFF_MS = (1000, 3000, 6000)   # 第 1/2/3+ 次重试递增退避

def __hop_retry_delay_ms(retry):
    _i = max(0, int(retry or 1) - 1)
    if _i >= len(HOP_RETRY_BACKOFF_MS):
        _i = len(HOP_RETRY_BACKOFF_MS) - 1
    return HOP_RETRY_BACKOFF_MS[_i]

# ① 被拒重试（原 300ms 立即重走）
"at_ms": __now_ms() + __human_delay(300) + __hop_retry_delay_ms(hop["retry"]),

# ② 拉黑后"换跳转点重新规划"（原立即重规划）
_plan.get("click_type", 0),
int(_plan.get("delay_ms", 500) or 500) + __hop_retry_delay_ms(_n),
```

**为什么它能降 QPS 且不影响产出**：
- 被拒后的重试是**注定无效**的（97% 在 2 秒内再被拒），退避把"1 秒 1 连发"摊平成"1s/3s/6s"，给位置包收敛留时间，降低服务端瞬时校验压力；
- 总量变化有限（拒绝次数由服务端校验决定，预计总量 **-0~5%**），主要收益是**峰值摊平 + 减少无意义重走**（每次重走本身带一串位置包）；
- 跨图最坏多等 6 秒/次重试（单跳转点重试上限 4 次，即最多 +18 秒），换路最多 +6 秒 —— 相比"被拒 4 次后拉黑重规划"原本的几十秒等待，影响可控。
