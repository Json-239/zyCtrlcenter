# 修复-20260921-STUCK错误自动恢复

- 日期：2026-09-21
- 现象：8 个号 16:39 起 `state=ERROR` / `err_code=STUCK_WAIT_NEXT`，**25+ 分钟无人恢复**
- 文件：`internal/services/event/event.go`（+ 注释同步 `internal/state/state.go`）
- 测试：`test/event/event_test.go`、`test/fixtures/events/error_stuck_wait_next.json`
- 状态：**已改码 + 构建/静态检查/测试全绿；未部署（不重启/不热更）**

---

## 1. 现象与 8 号样本

现场（2026-09-21 16:39 起）8 个号同时卡在 ERROR，`err_code` 全部是同一个码：

| 账号（@xy3.com） | 状态 | 说明 |
|---|---|---|
| robot0001065 / 1066 / 1074 / 1088 / 1099 / 1109 / 1111 / 5266 | `state=ERROR`、`err_code=STUCK_WAIT_NEXT` | 16:39 起，25+ 分钟无恢复 |

抓鬼进度：**7 个 done=52（已抓满）**，**1 个 done=43（未抓满，卡在半路）**。

行为特征（这就是"永久卡住"的形态）：

1. 机器人端看门狗判死后**只上报一次** error 事件，然后把 `quest.state` 置为 `ST_ERROR` 停链
   （`quest_engine.py:3185-3188`：`__emit({... "code": "STUCK_%s" % quest.state ...})` → `set_state(ST_ERROR)`），
   之后**不再重报**（注释明写"出错，等中控 reset/stop"）。
2. 中控收到这一条后只记了账（`err_repeat=1`），**既没有累计当日卡死次数，也没有触发重登**。
3. 中控 3 秒状态轮询（`pollOnce`）只做"清陈旧行 + 拉状态"，**不判 ERROR 态**（`internal/services/event/event.go:661`）。
4. 于是没有任何入口再碰这个号：机器人不重报、中控不动作 → 一直停在 ERROR，直到人工介入。

> 注：`pollOnce` 的清陈旧逻辑（10 分钟无心跳删行）也不适用 —— 机器人活着、心跳正常，只是"停链等人"。

## 2. 根因：`onError` 里的两个**白名单** switch

修复前 `internal/services/event/event.go:497-536`（`onError`）中，卡死类错误码被硬编码枚举了两次：

```go
// 516-525 行：当日卡死计数（churn 判据的数据来源）
switch code {
case "GHOST_DIALOG_STUCK", "TASK_STUCK":
    today := time.Now().Format("20060102")
    h.St.Update(account, func(r *state.Robot) { ... r.StuckCount++ })
}

// 527-533 行：触发"下线 → 重登 → 延迟补发"
switch code {
case "GHOST_DIALOG_STUCK", "TASK_STUCK":
    if h.reghoster != nil { h.reghoster(account, str(ev, "msg")) }
}
```

而机器人端 `quest_engine.py:3185` 看门狗统一上报的是 **`STUCK_<state>`**：

```python
_ev = {"type": "error", "code": "STUCK_%s" % quest.state,      # STUCK_WAIT_NEXT / STUCK_CLICK / STUCK_NAV / ...
       "msg": "状态 %s 重试 %d 次仍无进展" % (quest.state, quest.retry_count),
       "task_index": quest.active_task_index}
...
quest.set_state(quest_state.ST_ERROR)
```

（`STUCK_NAV` 另有一处独立上报：`quest_engine.py:3115`。）

**结论：所有 `STUCK_` 前缀的码都被白名单漏掉**，两条链路同时失效：

| 失效项 | 后果 |
|---|---|
| `StuckCount` 不累加 | 当日 churn 判据（`autotaskCandidates` 的"当天不再拉起"）拿不到数；`reghost.Request` 的 `ChurnLimit` 防护也失去数据（`internal/services/reghost/reghost.go:144`） |
| 不调 `reghoster` | 没有"下线 → 重登 → 延迟 8 秒补发"的恢复动作（`internal/api/autotask.go` 的 `ReghostDeps`） |

即 ERROR 态的恢复入口**根本没接上**，与 `restorer`（`needsRestore`）的 ERROR 分支设计无关 —— 本次修的就是这条入口。

## 3. 修复内容（diff 摘要）

### 3.1 新增 `isStuckCode`（放在 `onError` 之后）

```go
// isStuckCode 是否"卡死类"错误码（要计入当日 churn 计数 + 触发重登恢复）。
// GHOST_DIALOG_STUCK/TASK_STUCK 是抓鬼专属码；quest_engine 看门狗统一上报
// STUCK_<STATE>（STUCK_WAIT_NEXT/STUCK_CLICK/...）—— 2026-09-21 前只认前两个，
// 导致 8 个号卡 ERROR 25 分钟无人恢复。
func isStuckCode(code string) bool {
	switch code {
	case "GHOST_DIALOG_STUCK", "TASK_STUCK":
		return true
	}
	return strings.HasPrefix(code, "STUCK_")
}
```

### 3.2 两个 switch → `if isStuckCode(code)`（逻辑不变）

```diff
-		switch code {
-		case "GHOST_DIALOG_STUCK", "TASK_STUCK":
+		if isStuckCode(code) {
 			today := time.Now().Format("20060102")
 			h.St.Update(account, func(r *state.Robot) {
 				if r.StuckDay != today {
 					r.StuckDay, r.StuckCount = today, 0
 				}
 				r.StuckCount++
 			})
-		}
-		// 卡死类交给 reghost 下线重登后重新下发（与上面计数互不影响）
-		switch code {
-		case "GHOST_DIALOG_STUCK", "TASK_STUCK":
-			// 这两类都是"卡住等重登/等人工"（机器人自己会停链）；交给 reghost 下线重登后重新下发。
+		}
+		// 卡死类交给 reghost 下线重登后重新下发（与上面计数互不影响）。
+		// churn 防护仍生效：reghost.Request 内部有"当日卡死 ≥ ChurnLimit 不再自动重登"
+		// （internal/services/reghost/reghost.go:144，读的正是上面累计的 StuckCount）。
+		if isStuckCode(code) {
 			if h.reghoster != nil {
 				h.reghoster(account, str(ev, "msg"))
 			}
-		}
+		}
```

- 顺序保持"**先累计当日计数，再调 reghoster**"：这样 `reghoster` → `reghost.Request` 里的
  `Stuck(account) >= ChurnLimit` 判据读到的就是**含本次**的计数（与 `autotaskCandidates` 同口径）。
- 非卡死码（`NO_LEGAL_ROUTE`、`TASK_STUCK` 之外的各种 `error`）行为**完全不变**：仍只走
  `MarkTaskError` 记账 + 落盘 + 广播。

### 3.3 顺手同步注释（无逻辑改动）

`internal/state/state.go:38`：`StuckCount/StuckDay` 的口径说明补上"看门狗的 `STUCK_<STATE>` 一律计入"。

**未改动**：`internal/services/restorer/` 的 ERROR 语义（ERROR 交 reghost 链路，本次只接入口）、任何 `.py`
（机器人端 `daily_ghost.py` 由另一路并行修改）。

## 5. 部署后须知

1. **已卡住的 8 个号不会自动恢复**：机器人端 16:39 只报过一次 error 事件、之后不再重报，中控**不做历史事件补发** ——
   新代码只能接住"部署之后新发生的" `STUCK_*`。这批存量号需要人工重登/补发一次（由主控执行）：
   `POST /api/robots/manage`（remove + add 该号）或直接 `POST /api/autotask/run` 让它按候选重新补号；
   `done=52` 的 7 个按"已抓满"口径走，`done=43` 的那个需补发抓鬼。
2. **新发生的 `STUCK_*` 立即自动恢复**：计入当日卡死次数 → `reghost` 下线 → 重登 → 在线后延迟 8 秒补发任务。
   观察点：`GET /api/autotask` 的 `reghost` 列表（`phase` 依次 `waiting_offline → waiting_online → waiting_launch → done`）。
3. **churn 防护仍然生效，且现在才真正有数**：同一号当日卡死 ≥ `reghost.ChurnLimit`（3 次）后
   **不再自动重登**（面板 `reghost` 里显示 `failed` + "当日卡死已达 3 次"），当日也不再被自动任务拉起，
   等人工或跨日清零。这是**预期行为**，不是故障 —— 部署后如看到某号"卡死不救"，先看当日计数是否已满。
4. **部署前已卡死的号当日计数为 0**（正是本次缺陷导致没累加），所以部署后它们可以正常被重登/补发；
   若当天又连续卡 3 次，则按上一条转人工。
5. 本次**未部署**：Go 侧需重启中控（或按既定流程热更）后才生效。
