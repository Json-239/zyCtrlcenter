# 实施：机器人内存治理（路径缓存 + NPC 缓存，2026-10-28）

## 1. 背景

- 机器人单进程（C++ 外壳 + python39.dll）承载 ~280 号，commit **约 1.2GB/天**增长：
  10-27 14:07 达 4.52GB，叠加 msedge 4.41GB / Godot 3.59GB → Windows 提交内存耗尽
  （WER 2004），中控退出、全队重登、当日产出 -17%。
- 中控侧护栏（`robotguard.go`，10-27 16:58 部署）只能"到阈值低峰重启"（每 1-2 天一次，
  每次全体重登 5-15 分钟）；本批是**根因治理**。

## 2. 代码定位（三个无界缓存）

| # | 位置 | 机制 | 本轮处理 |
|---|---|---|---|
| 1 | `robot_path.py:35-55` `GridPathFinder._cache` | key=(起格, 终格) → 路径列表，**永不淘汰**；280 号共用按图的 finder | **加上限 300/图，超了整图 clear** |
| 2 | `msghandle.py:827-831` `m_npc_add_raw`；`robot.py:146-147` `m_npc_positions/m_npc_pos_seen` | 按 npc_id 累积，无 TTL/上限 | **TTL 30min + 上限 3000（FIFO）** |
| 3 | `quest_engine.py:135-152` `quest.chain.map_grids/dijkstra` | `set_quest_chain` 永久并集 | **本轮不裁**（见 §4） |

## 3. 改动（可热更，只加清理逻辑，不改业务）

### `quest_engine.py`（CRLF，`34f25d69` → **`b244300b`**，+99 行）

在 `g_chain_dijkstra_cache` 之后插入模块级常量与 4 个函数：

- `_MEM_PATH_CACHE_MAX = 300`：每图路径缓存上限；
- `_MEM_NPC_MAX = 3000` / `_MEM_NPC_TTL_MS = 30min`：每号 NPC 缓存上限/TTL；
- `_MEM_TRIM_INTERVAL_MS = 5min` / `_MEM_LOG_INTERVAL_MS = 10min`：节流；
- `__mem_trim_global(now)`：遍历 `_FINDER_CACHE`，单图 `_cache > 300` → `clear()`（全局节流 5min）；
- `__mem_trim_robot(robot, now)`：`m_npc_pos_seen` 超 30min → 删；超 3000 → FIFO 删最旧；`m_npc_add_raw` 超 3000 → FIFO；
- `__mem_log(robot, quest, now)`：`[MEM] <acc> graphs= paths= max_per_graph= grids= npc_pos= npc_raw= chain_cache=`（10min 节流）；
- `__mem_guard(robot, quest, now)`：入口，每号 5min 节流（只跑 trim_robot + trim_global + log）。

`tester()` 的 `now_ms = __now_ms()` 之后插入调用 `__mem_guard(...)`。

### `daily_ghost.py`（LF，`af0ce7ce` → **`315627f0`**，+6 行）

`def tick(robot_object, now):` 首行插入 `quest_engine.__mem_guard(...)`：
抓鬼号在 `main_tester` 提前 `continue`，不进 `quest_engine.tester`，此处补挂覆盖抓鬼号。

## 4. 为什么本轮不裁 `map_grids/dijkstra`

复核（P1/P2）实测：

1. **dijkstra 无独立兜底**：`reachable_maps`（quest_engine.py:1186）只认 `quest.chain["dijkstra"]`，
   表为空才回退 `g_chain_dijkstra_cache`；真实链 89 键，裁到 6 后 BFS 由 3 跳变 None → 跨图断链。
2. **全局表引用**：`shop_errand` 里 `quest.chain = g_nav_chain`（quest_engine.py:2025，引用赋值），
   裁 `quest.chain["map_grids"]` 会直接改全局表，影响所有号。
3. **收益有限**：网格是静态数据、浅拷贝共享，条目数上限 = 图数（131），不是主要增长源。

## 7. 观察（2026-10-28 10:33，热更后 32 分钟）

| 时点 | mem | 斜率 |
|---|---|---|
| 10-28 09:28 | 1826MB | 改前 09:28→09:58 = **64MB/h** |
| 10-28 09:58 | 1858MB | 改前 08:58→09:28 = 100MB/h |
| 10-28 10:01 热更 | 1858MB | — |
| 10-28 10:13（+12min） | 1849.9MB | — |
| **10-28 10:33（+32min）** | **1851.3MB** | **+1.4MB/20min = 4.2MB/h（-93%）** |

- `[MEM]` 快照（热更后从 0 重建）：`paths` 3400(10:11) → 5451(10:21) → 6145(10:31)；
  `max_per_graph` 517 → 512 → 463 —— 单图上限 300 每 5min 清一次，清除后 5 分钟内回填到
  460-520（280 号共用同一 finder 的正常业务速率），不会无界累积；
- 已清理：路径 **7261 条**、NPC **250508 条**（一次性存量；之后每号每次只清 2-70 条，进入稳态）；
- 回归：`PATH_GRID_MISS` 0 / `NO_LEGAL_ROUTE` 0 / `MEM_GUARD_RAISED` 0 / `Traceback` 0（近 5000 行）；
- 结论：**增长斜率降 93%**（64→4.2MB/h）。内存未回落是 CPython pymalloc 不归还 OS（正常现象）；
  最终验证看下次重启后从 0.4GB 起的稳态（预期 0.6-0.8GB，而不是 4 天 4.5GB）。
- 双副本已同步：`quest_engine.py` `b244300b`、`daily_ghost.py` `315627f0`（生产 ↔ `deploy/zones/prod-240-2300/script`）。
