# 分析-20260922：钟馗"空菜单"→抓鬼下线换号 根因

> 只读分析（未改动任何生产代码）。证据来源：生产机器人日志 `data/bot_logs/<账号>/runs_20260922.log`、
> 服务端源码 `f:\ZyBin\xm\2d-xiyou-server\`、机器人源码 `deploy/zones/prod-240-2300/script/`、中控 `internal/`。
> 结论对上一轮文档《改动-20260922-抓鬼链路与三池批次化.md》第七/八节（把"闲聊菜单"一律归因于"每日 50 上限"）做**修正与补充**。

## 0. 结论速览（TL;DR）

1. **主线根因（占全天 NO_ACTION 下线的 78.6%）**：机器人把**"交付捉鬼任务"的成功对话**误判成"钟馗空菜单/无可动作项"。
   服务端在玩家点钟馗时会**自动交付**已完成的捉鬼任务，并下发一条
   `S2C_SHOW_DIALOG`：`npc=10146 / task_index=2019511 / 选项 0 个`；紧接着由 `action_talk_npc` 再推一条正常菜单。
   机器人只看第一条包 → `first is None` → 走 `__note_no_action()` → 计数 `no_action_rounds += 1`。
2. **放大器（2026-09-22 当天的改动）**：`no_action_rounds` **不随"拿到正常动作项/成功交付"清零**
   （只随 `抓鬼启动` 清零），而当天把阈值 `NO_ACTION_OFFLINE_LIMIT` **3 → 2**、空菜单退避 **60/120s → 5/10s**。
   于是**每个抓鬼会话在做到第 2 个鬼、第 2 次正常交付时，必然被判"下线换号"**。
3. **伤害扩散（中控）**：`ghost_offline(code=NO_ACTION)` → `MarkGhostDoneToday()`
   （`internal/services/event/event.go:702-704`，`isGhostUnavailableCode` 含 `NO_ACTION`）
   → 该号**当天不再被派抓鬼**。所以"误判一次 = 健康号丢一天"。
4. **次要根因（占 21.6%）**：真·满额号（服务端 `task_limited` 打鬼计数 f=50/50）的菜单确实只有静态 3 项；
   但机器人的"服务端次数校准"把键写死为 `2019510`，而服务端记账的 `episode_root` 是**当日首个接到的打鬼任务号**
   （实测 2019501~2019510 都有）→ 校准失败 → 误判"已抓 0" → 再去接 → 空菜单。
5. **无效自愈**：`C2S_DROP_TASK`（协议放弃）对捉鬼任务**必然被服务端拒绝**
   （`task_ruler.py:204-209` 要求 `task_dropable==True`，而 `20195.xml` 全系列 `task_dropable="否"`），
   所以"盲试放弃 2019501~2019513"是死路，只会白清本地缓存。

## 2. 服务端菜单生成规则（回答"什么条件下菜单会变成 3 项"）

钟馗 10146 的菜单 = **NPC 静态/条件选项** + **任务按钮（catcher 交付）** + **ticket 按钮（接取）** + **关闭按钮**，
顺序即客户端看到的顺序（`dialog_module.py:77-126`：task 按钮 → dynamic → option → close）。

### 2.1 NPC 配置侧（`config/npc/zhongkui.xml`，npc_step 1）

| 选项 | 条件 | 代码 |
|---|---|---|
| `离开` | 无条件（`option_step="0"` → 关闭项，永远排最后） | `zhongkui.xml:10` |
| `【捉鬼任务】活动说明` | 无条件 | `zhongkui.xml:11`（子菜单 step 12） |
| `领取助战令` | 无条件（开商店 `sale_index_taskitem_task_ghost`） | `zhongkui.xml:12` + `128-130` |
| `我今天身体不舒服。（放弃捉鬼任务需扣除金钱5银）` × 12 | **持有** 2019501~2019510 / 2019512 / 2019513 时各出现一条 | `zhongkui.xml:13-72` |
| （**没有** 2019511 的放弃项） | —— | 交付任务 design 上不可放弃 |

→ 结论 A：**"没有放弃项" ⇔ 服务端不认为角色持有任何打鬼任务**（2019501~2019510/12/13）。

### 2.2 任务按钮侧（catcher 交付）

`npc_action.py:141-144` → `task_story.check_task_list` → `task_story.py:60-98` →
`task_ruler.get_catcher_task_list`（`task_ruler.py:431-443`：`dialog_visible==True` 且 `task_catcher==该 NPC`）。
2019511（交付捉鬼任务，catcher=钟馗，`dialog_visible=是`，`20195.xml:641-682`）本会生成一条
`【可交付】交付捉鬼任务` 按钮——**但通常看不到它**，因为点击钟馗时已被"自动交付"抢先：

```
script/npc/npc_dispatcher.py:56-62   （C2S_CLICKNPC，click_type != 2）
    task_object = get_can_finish_catcher_task(npc)        # 交付任务且可交
    if task_object and not check_already_auto_submit() and can_check_task_list():
        set_already_auto_submit()
        task_object.execute_task_step(role_object)         # ← 直接执行 step1
```
step1 = `action_dialog`（**只有台词、没有选项**）+ `action_submit` + `action_talk_npc` + `action_update_acceptable_ticket`
（`20195.xml:671-681`；`DialogTaskAction` 见 `task_action.py:130-137`，把 `task_index=2019511` 塞进对话包；
`TalkNpcTaskAction` 见 `task_action.py:731-741`，随即重推钟馗 step1 菜单）。
S2C 包布局：`[escapable, story_mode, npc_id, content, task_index, buttons]`（`dialog_operator.py:8-13`）。

→ 结论 B：**持有 2019511 并点钟馗时，正常表现就是"先来一条 0 选项、带任务号 2019511 的交付对话"**，
交付同时已完成；随后那条菜单里"接取项是否恢复"直接反映真实可用性。

### 2.3 ticket 接取项（`挑战捉鬼任务` / `捉鬼【组队完成…】`）

`npc_entry.check_task_ticket`（`npc_entry.py:46-73`）对挂在 10146 上的 ticket 逐个 `can_accept_task`：

- ticket 2019501（`20195.xml:2-37`）：`group_index="抓鬼"` → 组内含 **12 个 entry**（2019501~2019510/12/13），
  每个 entry 必须 `is_task_undone()==True`（`task_ticket.py:69-89`）；
- `is_task_undone` → 每日上限分支（`task_operator.py:93-104`）：`today_finish_count >= daily_limit(50)+buff` ⇒ 不可接；
  → episode 分支（`task_operator.py:105-114`）：**该 entry 的 episode 状态 = ACCEPTED ⇒ 不可接**；
- `ticket_condition`（`20195.xml:11-13`）：等级 20~999 **且 `condition_result="相反"` 不持有 2019511**。

→ 结论 C：**接取项消失 = ①已满 50 次 或 ②正持有打鬼/交付任务（episode ACCEPTED 或持 2019511）或 ③等级不够**。
配合结论 A（无放弃项）+ 结论 B（交付会被自动提交），可得**三种菜单形态**：

| 形态 | 选项 | 含义 |
|---|---|---|
| A 可接 | `[接取项, 活动说明, 领取助战令, 离开]` | 无任务在身且未满额 |
| B 已有任务 | `[活动说明, 领取助战令, 放弃捉鬼任务, 离开]` | 持有 2019501~2019510/12/13 |
| C 闲聊/满额 | `[活动说明, 领取助战令, 离开]` | **未持有任何任务且接取项被隐藏**（满额 / 等级不够 / 计数异常） |

（现场还可见第四种：**`task=2019511` + 0 选项的"交付对话"**，它不是菜单，而是交付结果通知。）

## 3. 协议放弃为什么必然失败（回答"盲试为什么一直不生效"）

- 协议：`C2S_DROP_TASK = 80357`，格式 `[4]`（单字段，值 = `task_index`）→ `protocol2/c2s_list.py:148`；
  服务端 `task_dispatcher.py:19-21`：`task_index = msg_data[0]; task_ruler.drop_task_object(task_index)`。
- 服务端校验（`task_ruler.py:204-209`）：
  ```python
  task_object = self.get_task_object(task_index)
  if task_object == None: return False
  if exceptional == False and task_object.get_task_dropable() != True: return False   # ← 协议放弃被卡在这
  ```
- 而捉鬼全系列 **`task_dropable="否"`**（`20195.xml:38 / 78 / 118 / … / 641`；含交付任务 2019511）。
  ⇒ 机器人发的 `[2019511]/[2019501]/…` **一定 return False，服务端什么都不做**（也不会回包提示）。
- 唯一合法放弃途径是钟馗对话框的"放弃捉鬼任务"（`zhongkui.xml:13-72` → step 2..14）
  → `DeleteTaskNpcAction`（`npc_action.py:553-562`）：**要求持有该任务 + 现金 ≥ 500（5 银）**，
  再 `drop_task_object(task_index, exceptional=True)`。机器人号现金常年只有几十 → 走不通（历史上已踩过"空点死循环"）。

→ 所以机器人 `daily_ghost.py:1836-1915` 的"第三形态自愈：协议放弃 → 重试接取"**方向就是错的**；
它还会顺带 `g.last_task = {}`、清空菜单退避计数，把真实状态（本地有 2019511）抹掉。

## 4. "本地任务表为空 / 计数为 0"的机制（回答任务不同步与校准问题）

1. **打鬼/交付任务不在登录全量里**：机器人自己的注释（`daily_ghost.py:1713`）与实采一致——
   重登后 `READY 诊断: 抓鬼任务=[] … 缓存任务=None`，但服务端仍持有任务 → 菜单形态 B/C；
   此时机器人只能靠**对话载荷 `data[4]`**或缓存判断（`daily_ghost.py:1569-1574, 1855-1867`）。
2. **服务端每日次数记账的键会漂移**：`TaskLimited` 由 `share_daily_key` 共享，但对象里记的 `episode_root`
   是**当天第一个触发创建的打鬼任务号**（`task_ruler.py:331-361`，只有 `episode_root == task_index` 的 entry 能建/加）；
   而 2019501~2019510 每个都是自己的 episode root（`task_parser.py:101-131`）。
   实测同一天不同号出现 `er=2019501/2019502/2019504/2019508/2019510` 各种值。
3. **机器人把键写死**：`GHOST_DAILY_ROOT = "2019510"`（`daily_ghost.py:35`），校准只读 `_tl.get("2019510")`
   （`daily_ghost.py:1288-1294`），日志摘要也只认这个键（`2116-2124`）。
   → 只要该号当天首个打鬼任务不是 2019510，**服务端权威计数就校准不上**，`done_count` 保持中控给的旧值（0/1/3/6）。
4. 后果：满额号（f=50）被以"已抓 0"重新拉起 → 闲聊菜单 → 第 2 次即 NO_ACTION →
   中控标"当天不可用"（**这一支恰好把"满额"这一真实原因的错误代价转移成了制度化的当天停派**）。

## 5. 修复方向建议

### A. 机器人端（可自行兜底，建议最优先）

| # | 建议 | 依据 |
|---|---|---|
| A1 | **把"交付对话"当成功信号**：`npc=10146 且 task_index==2019511 且 0 选项` ⇒ 交付成功（清本地 SUBMIT/交付任务、关对话回 READY 或按完成计数），**不得计入 no_action** | §1.2 日志；`daily_ghost.py:2016-2022` 已有"信息型交付对话"分支，但被 `1972` 的 `first is None and npc_id==BROKER_NPC_ID` 提前 return 挡住，**在钟馗场景不可达** |
| A2 | **`no_action_rounds` 语义改为"连续"**：拿到正常动作项/接到任务/交付成功/任务完成时清零 | `daily_ghost.py:640-695` 只增不清；`375/405` 注释显示"不随 reset 清"；`698-703` 只清 `no_action_retry` |
| A3 | 阈值/退避口径复核：若保留快速二连，必须配合 A2（否则每会话必死在 2 次交付） | `daily_ghost.py:599(3→2)`、`613(60/120→5/10s)` |
| A4 | **删除"盲试协议放弃"**（或先本地判定 `task_dropable`），改为"本地有交付任务但服务端不给交付对话 ⇒ 重登"；不要在自愈里清 `last_task`/计数 | §3；`daily_ghost.py:1868-1915` |
| A5 | **满额判定修正**：校准改为扫 2019501~2019513 取最大 f；发现 `f>=50` ⇒ 直接走 `ghost_done`（而不是 NO_ACTION） | §4；`daily_ghost.py:35/1291/2116` |
| A6 | 闲聊 3 项菜单（无接取/无放弃/无交付）判定细化：先排除"满额/等级不够"，再报"不可用" | §2.3 结论 C |

### B. 服务端（如需，改动面更大，建议先评估）

- B1：给 2019511 的 `task_step 1 action_dialog` 加一条**关闭选项**（如"我明白了"），
  让"交付对话"与"空菜单（0 项）"在协议层可区分——会改变客户端表现，需同步评估机器人/客户端。
- B2：把每日计数的 `episode_root` **固定为链首**（如 2019501）而不是"当天首个接到的任务号"，
  消除键漂移（涉及旧存档数据兼容，谨慎）。
- B3：（可选）`C2S_DROP_TASK` 对 `task_dropable=否` 回一条失败提示，便于客户端区分"没生效"。

### C. 中控（Go）

- C1：`NO_ACTION` 从 `isGhostUnavailableCode` 里拆出来或细化原因码：
  只有"满额/等级不够/明确的今日不可用"才 `MarkGhostDoneToday`；
  "交付误判/对话异常"类应走重登或短冷却，**不要当天停派**
  （`internal/services/event/event.go:646-654, 699-704`；`state.go:151-183`）。
- C2：机器人上报的 `done`（本地计数）不可信（实测 0/1/3/6 vs 服务端 46/47/50），
  中控的"已抓"展示与候选筛选应以服务端 `task_limited` 口径为准（可让机器人补一个 `srv_done` 字段上报）。

### D. 部署注意（不改代码的运维动作）

- 已上线版本造成的"被误标当天不可用"的号：`State.ghostUnavail` 表在内存里，**中控重启即清空**
  （《改动-20260922》第八节已注明），重启后这批健康号会重新进入候选（每个约 20 秒再被误判一次，循环）。

### 8.5 未纳入本次范围（遗留与取舍）

1. **中控侧仍会无条件"标记当天不可用"**：`internal/services/event/event.go:646-654 / 699-704`
   —— `isGhostUnavailableCode` 仍把 `NO_ACTION` 视为"本号今天抓鬼不可用"并调 `MarkGhostDoneToday`。
   本次机器人端修好后 `NO_ACTION` 的触发面已从 ≈8 次/分收窄到 0，但如果将来又出现新的 `NO_ACTION` 误报
   （或 3 项闲聊菜单被误归因），**仍会误伤一整天**（标记落在内存表 `State.ghostUnavail`，中控重启才清空）。
   建议后续细化：机器人上报更细的原因码（满额/等级不够 vs 对话异常），中控只对"真不可用"打标记。
2. **豁免后不主动回 READY / 不主动补点钟馗**（取舍）：实测交付对话后服务端会随即 `action_talk_npc`
   重推正常菜单（本次 22/22、离线样本 76/78 均在 1~3 秒内到达并接取成功）；未到达时由既有 SUBMIT 看门狗
   兜底（重试 → 再点钟馗），因此不在豁免分支里新增状态机跳转，避免引入新的分支与竞态。
3. 满额号的"已抓 N"显示口径仍以服务端 `task_limited` 为准（本次已修键漂移）；中控面板若仍展示本地 `done`
   计数，可能与服务端存在偏差（历史数据本来就不可信，见 §4），未在本次改动内统一。
