- 低蓝血正常 → 采购 MP 药 ✓。

### 3-B 攻击点 2 深挖：stop-share_daily 与恢复引擎（重点）

**a) stop 语义**：`share_daily_stop`（dispatch_cmd :1961）= **本地停止**（`enabled=False`+`stop_code="MANUAL"`+`reset_runtime()`+STOPPED）——**不是** Go 侧的"人工暂停"（`/api/stop` 的 pause 标）——**语义选择正确**：对恢复引擎它等价于"可被按意图补发"，而不是"死到人工解除"。核查：Go 侧 **无任何代码消费 `stop_code`/"MANUAL"**（grep 0 命中）→ 无副作用；`reset_runtime` 不清 `share_key/done_count/task` 进度（逐字段核对）→ **本地进度保留**。

**b) 在途成果（最坏情形）**：停时不走 `__request_stop`（自动收工——会清 quest）——**quest 残留不清**（既有"人工/自动不对称"，两池复核 P2-2 同款，此处被采购 start 覆盖 + 恢复时 `__cmd_start` 清，实际无碍）。服务端任务在身（20195xx）；RESTORE/restorer 补发**带 done**（groupCommand 补齐）→ **已完成轮次不受影响**；**最坏**=停时正处交付对话/交付在途 → 该轮交付动作**重做一次（秒级）**，无永久损失。

**c) RESTORE 真恢复（关键机制链，只读 Go 侧核对）**：
- 恢复引擎 = `internal/services/restorer`（`CTRL_AUTO_RESTORE=1`，**5s ticker**）。
- 补发判据 `needsRestore`（restorer.go:186-218）：**`r.Walking()`（游荡中）→ 不补**；state ∈ {IDLE/""/ONLINE} → 补；WAIT_TASK→task_index==0；**NAV/CLICK/FIGHT/SHOP/RECYCLE/ALLOC/WAIT_NEXT/DONE/ERROR → 不补**（default false）；DIALOG 仅 ghost 意图特例。
- **采购期的 quest 状态**（shop_errand 执行体=quest_engine 商店执行器：NAV→CLICK→DIALOG→SHOP）**全部落在"不补"集合**（DIALOG 对 shenbu/fenghuo 意图=false）→ **采购期间恢复引擎不会抢** ✓；**采购收尾后** quest 回 IDLE → **5s 内按意图补发 `share_daily_start`（带 share_key/daily_limit/done）→ 号恢复日常** ✓。
- 意图来源：decideIntent 台账兜底（09-28 B 修复：神捕台账已派未满 → shenbu）✓。
- **结论**：设计注释"采购完成后中控恢复引擎按意图重派"**机制上成立**——且比"等采购完成"的实现更稳（无需通知中控，靠状态自然衔接）。
- **残余窗口（P2-3）**：stop→start 为**同一次 tick 调用内连续执行**（毫秒级）——restorer 5s 边界命中的概率 ≈ 0.5%，命中后果=采购导航被 `__cmd_start` 清理（90s 超时+退避兜底）——可接受。
- **失败循环收敛（P2-2）**：买不成的号（no_money/超时）每轮 = 停日常→采购→失败→恢复→冷却（60s×2^n，封顶 30min）——**30min 级打扰**，且 ④告警 5min 内可见（可定位）——代价/收益成立。
