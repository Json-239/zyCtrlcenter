# 实施记录-20260929-切换让路保护（抓鬼在途时切换指令排队，交付完成后执行）

## 一、用户口径（原文）

> "可以做个保护，不管是下发什么或者游荡，在切换下一件时候一定是当前现有先做完，
>  比如当前已经在抓鬼路上了，然后我让他去游荡，那也要先把这只鬼抓完去提交，
>  才开始去游荡。"

结论：**切换类指令（游荡 / 摆摊送图等）遇号上有"在途工作单元" → 不打断、挂起排队；
当前工作单元完成（抓鬼=交付完成）后自动停抓鬼并执行挂起指令。**

## 二、现状与核心改动点

`random_walk.py::dispatch_cmd`（random_walk 分支）原有"互斥: 停止当前任务(新手链/抓鬼)"
（旧版 ~1740-1760）读 `m_ghost`，**非空闲即 `daily_ghost.dispatch_cmd({"cmd":"ghost_stop"})`
停抓鬼再启动游荡** ← 本次改为"等当前工作单元完成"。

既有拒绝闸（保持不变，排队点在其后）：跨图冷却/禁游荡图/排除图/shop_busy（采购中拒绝）/
share_daily（分享日常中拒绝）——注定被拒的指令**不进队列**（零副作用）。

## 三、机制设计（终稿）

### 3.1 "在途工作单元"判据（抓鬼状态枚举）

`random_walk.__ghost_busy(robot_object)`：抓鬼会话 `enabled` 且（战斗中 或）状态在：

| 状态 | 语义 | 处理 |
|---|---|---|
| ACCEPT | 点钟馗接取中 | **排队** |
| NAV | 追鬼/去交付点途中（含跨图） | **排队** |
| FIGHT | 打鬼中（含野外战斗中窗口 `m_fight_state`） | **排队** |
| SUBMIT | 交付中 | **排队** |
| WAIT_NEXT | 刚打完等任务推进（交付前） | **排队** |
| HEAL | 疗伤中（买药/用药） | **排队** |
| READY | 待接（无在身任务） | 直接切换（既有行为） |
| WAIT_GHOST | 等刷鬼（无鬼可打） | 直接切换（等不存在的鬼无意义） |
| ERROR / DONE / IDLE | 卡住/满额/未启动 | 直接切换 |

判据与中控游荡池 `roampool.Interruptible`（超编收敛白名单：WAIT_GHOST/READY/IDLE/ONLINE
可中断，FIGHT/SUBMIT/DIALOG/NAV 不碰）**同向**，机器人端是最后防线（覆盖面板手动派发/
booth 送图/restorer 等绕过 Interruptible 的路径）。

### 3.2 挂起数据结构（robot_object.m_roam_switch_pending）

```
{"cmd": <重放命令: 指令原文 + 解析后最终目标图/白名单覆盖>,
 "sig": <指纹: mapid+maps+mode+minutes>, "at_ms": <首次入队毫秒>}
```

- **覆盖**：不同指令（新目标）→ 覆盖（最后生效）、重新计时；
- **去重**：同指纹重派（游荡池 60/120/300s 退避重发 / 中控补发）→ 只刷新命令、
  **保留首排计时**（超时不被恢复重派无限刷新）、不重复记日志；
- 重放走 `dispatch_cmd` 全流程 → 既有闸（排除图/冷却/采购锁等）全部复检。

### 3.3 三个触发点（daily_ghost.py）

1. **主路径（正常完成）**：`on_finish_task` 中**交付任务 2019511 FINISH**（= 一次完整
   工作单元"接取→打鬼→交付"结束）→ `random_walk.run_switch_pending(reason="ghost_submit_done")`
   → 停抓鬼 + 重放挂起指令。
   *只认交付任务 FINISH* —— 打鬼 FINISH 后还要去钟馗提交，不能在那时切（用户口径原文）。
2. **满额拦截**：`__emit_ghost_done`（满额转野外游荡）里，有挂起指令 → 先执行切换、
   **不转默认游荡**（避免覆盖用户刚下的摆摊/送图意图）；`ghost_done` 事件照常上报。
3. **每帧兜底**：`daily_ghost.tick` 顶部挂 `random_walk.tick_switch_pending`（所有登录号都跑，
   早于抓鬼 enabled 判断）：
   - 抓鬼会话已停（ghost_stop/满额/下线）或已回空等（READY/WAIT_GHOST/ERROR）→ 立即执行；
   - 等待超 `ROAM_SWITCH_TIMEOUT_MS = 15 分钟` → 判卡住，执行切换（只做切换、**不上报**卡死，
     避免误触发中控 churn 熔断；卡死号另有重登兜底）。

### 3.4 边界

- **停止类不排队**：`random_walk_stop` 立即执行，并**撤销**挂起的切换（"停"= 不再切）；
  `ghost_stop` 等 = 抓鬼会话结束 → 下一帧兜底立即执行挂起指令（用户最终意图=切走）。
- **超时论证**：P0 修复后抓鬼单只周期均值 ~1.6 分钟（完成 2286/h 基线），15 分钟 ≈ 9 倍
  余量；超时几乎必然是 NAV/交付卡死。
- **新手链（quest）不纳入排队**：无明确"完成点"（多环链，完成可能在几十分钟后），排队只能
  靠超时切换、延迟更大；用户点名的是抓鬼场景。保持"下发即停链"（既有行为）。若后续用户
  要求，可按"当前链环完成"扩展（`quest_engine` 侧挂钩，属于他线）。
- **号重登**：pending 挂 robot_object 上，重登重建后丢失 → 中控重派即可（不粘滞）。
- **booth 一体化**：`/api/booth/start` 送图 = `DispatchRoamEx` 走本 gate，**无需改 booth**：
  Go 侧 `res.Sent = 已下发号数`（SendCmd 成功即算），不看机器人端 reply → 排队不影响
  "送图成功→写计划"链路；到图 11 后 booth.tick 自动开摊（计划文件驱动）。
- **中控游荡池**：keeper 生效判据 = 心跳 `walk.enabled`（Roaming），不看 reply；排队期间
  keeper 以 60/120/300s 退避重派（被机器人端覆盖去重），执行后 `walk.enabled=true` 自然结案。
- **mount_egg（孵化）边缘**：孵化内转 random_walk，若命中排队会按"孵化启动失败"warn 返回
  （不 emit error）。孵化池与抓鬼池不重叠，命中概率≈0；不修他线模块，仅记录。
