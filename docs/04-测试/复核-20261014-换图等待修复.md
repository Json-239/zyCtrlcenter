## 3. 风险点专查：C 清状态 return 0 后会不会死循环？（最重要）

**问题**：下一拍推进器会不会把同一个 hop 重新走行走 → 再进等待分支 → 每 5s 空转但不报 STUCK？

**结论：不会形成无限循环；生产命中形态会被推进器正确消化并继续任务。** 三层依据：

1) **C 的清理动作与 A 分支（2026-08-23 既有设计，:4128-4137）逐字段一致**（独立断言 S2/S3 + F1 对照实证），且 C 与 A 一样**不自行弹 route**，把处置交给同一"跨图推进"入口 `__tick` 内 **:5199-5221**。A 分支运行至今依赖该入口消化 hop，未产生死循环；C 复用同一机制 ⇒ 同向行为。

2) **命中 C 后推进器的两种实际去向（用真实函数跑通）**：
   - **生产 5215 形态**（route=[10→11, 11→12]、m=12 直达目标图）：`__winnow_route_by_map`（:3874-3928）`k=1` 命中"跳级换图"分支 → pop 0..k → route 清空 → 无连贯性问题 → `__start_next_hop`（:1234-1307）走 **final 段**（图 12 (2265,1846) 交付）——P3-3 实测 final walk 被调度（npc_id=13297），P3-4 全程零 STUCK/零回滚。
   - **m 命中更靠后的跳（k>0 且 route 非空）**：弹到 k 后，winnow 的连贯性检查（:3918-3927）保证 `route[0]._from_map == m` ⇒ **下一拍走路的外层条件 `m_mapid != hop.from_map` 为 False，结构上不可能重入等待分支**（P1-2/3/4 实证）。

3) **若 m 不在剩余 route（winnow k<=0，非常规形态）**：推进器不动作（P2-1；与 :3891-3892 注释"交各模式既有兜底"一致）→ 状态看门狗（:5244-5288，ST_NAV=10s，`quest_state.py:22-28`）触发 `__recover`（:3392-3400）→ `__start_next_hop` 重走同一 hop → 等 2 次 C 再清。该环被 retry 计数**硬性终止**：每次看门狗触发 `retry_count+=1`，第 4 次 `retry(4) > quest_max_retry(3)`（`config.py:348`）→ **STUCK_NAV + ERROR**（:5258-5283）。P2-2 实测 3 个恢复周期后终止 ⇒ **有界（约 40-50s 兜底报错），非"无限静默空转"**；且与改前同级（改前该形态 ~33s 报 TASK_STUCK）。k<=0 属 route 不含当前图的异常形态，未见于 10-13 生产命中（5215 为 k=1），非本次修复目标场景，亦无回归。
   - 唯一差异备注（P3 观察项）：k<=0 时错误码由 `TASK_STUCK` 变 `STUCK_NAV`，部署后可据此 grep 观察残余。

4) **不存在"5s 紧循环"**：C 命中路径中 `__schedule` 重排（:4195-4199）在其**之后**，C `return 0` 使该行不可达（A3 实测调度数不增）；2.5s 重排只发生在 wait_count<2 或 srv!=m（B2/E1 实测）。C 后唯一可能重走同一 hop 的驱动是 ≥10s 的状态看门狗（且每次 +retry，见 3）。
