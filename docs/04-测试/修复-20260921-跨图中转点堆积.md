## 2. Q1—Q4 逐条结论

### Q1 13115 这一跳在 `__start_next_hop` 里怎么被消费？为什么过图后没有进入下一跳？

**不在 `__start_next_hop` 里消费，而在 `__handle_dialog` 的"点中目的地主动同步"分支**
（quest_engine.py 修复后 777-817 行；行号按已修复版）：选项"长安东市集"命中 `jumper.target_name` 后
pop 掉 `dijkstra_route[0]`（13115 跳）、本地 `m_mapid` 直改 11、并调
`__start_next_hop(robot_object, quest, 800)` 排下一跳 walk。

**"之后没有下一跳"的原因：这次 `__start_next_hop` 排入的 walk 被后面的
`__schedule(dialog_click)` 覆盖丢弃，从未执行。** 证据链：

1. `__schedule`（177-178 行）是**无条件单槽赋值**：`quest.pending = p`；
   `__tick` 消费 pending（修复后 3262-3267 行）后置 None，全程只有一个槽。
2. 同一次调用栈内先后两次 schedule：`__start_next_hop` → `pending = walk(hop3)`；
   紧接着 `__schedule(dialog_click)`（at_ms=now+500）→ `pending = dialog_click`，**walk 丢失**。
3. 日志側：19:59:38 后 92 秒**无任何日志**。若 walk 正常执行，会先打
   `走路: (x,y) → (x,y) ...`（对照 19:59:18 的同款日志）；没有 = 从未执行。
4. 若走"跨图推进"兜底（`__tick`，修复后 3244-3259 行），pop 条件是
   `robot_object.m_mapid == dijkstra_route[0]["target_map"]`；此时 m_mapid=11（主动同步已改），
   而 route[0] 是 11→12 的下一跳（target_map=12）→ **不匹配，兜底不接管**。

### Q2 `dijkstra_final` 是否为 None？

**是，且必然为 None —— 但本次静默与它无关。**

- 这条链路是 daily_ghost 的 `__goto_xy`（daily_ghost.py:1145-1176），第 1170 行**显式**
  `quest.dijkstra_final = None`（抓鬼去刷鬼图只需"到达目标图"，不需要最终点击 NPC）。
- 但 1028 当时 **route 非空**（还剩 11→13 的 2 跳）：证据是 20:01:10 能打印
  `抓鬼 NAV 跨图 120s 仍无进展`——该日志的前置条件（daily_ghost.py:3060）是
  `g.state == "NAV" and quest.dijkstra_route` 为真；且重推时重新规划"经 2 个跳转点"，
  正是剩余行程。
- 因此 `__start_next_hop` 走的是 **hop 分支（应正常排 walk）**，不是 `final==None` 的静默
  return 分支。`final==None` 只是该路径的正常状态，不是本次根因。

### Q3 为什么 daily_ghost 的 NAV 兜底没有及时救它？卡多久、怎么恢复？

**兜底有效，但最慢要等满 120s 绝对上限；且 120s 从"跨图开始时刻"起算，不是"卡住时刻"。**

- 12s 看门狗在 `NAV + route 非空` 时被**显式忽略**（daily_ghost.py:3060-3071，只保留 120s
  绝对上限；这是 09-02 为慢跨图留时间的设计，不是缺陷）。
- 120s 判定用 `g.state_since_ms`，它只被 `__goto_xy` 刷新（1171 行）= **19:59:10**；
  120s 后 **20:01:10** 到期。跨图已用掉 28s，所以号只"卡"了 92s（而非 120s）。
- **1028 已自愈**：19:59:38 静默 → 20:01:10 强制重推（静默 92s）→ 20:01:11 走路 →
  20:01:31 到图 13 → 20:01:41 抓鬼战斗开始。**不需要人工干预。**
- 严重性：19:20—20:20 一小时 **86 个号触发 286 次**（平均每号 3.3 次，最多 6 次）；
  45% 的中转过图（500/1100 次）会白停 60~130s。13115 成为"每跳必停"的吞吐瓶颈，
  号在落点上堆积（= 现场"4 个号挤同一格"）。

### Q4 为什么"过图成功"后还发了一次"点击对话选项 #0"？

**这不是多余动作，是必须发的真实点击**（`C2S_CLICK_DIALOG`，服务端据此把角色传送到图 11）。
"主动同步"只是**本地乐观推进**（假设点击会成功），点击本身由随后排入的 dialog_click
动作发出（`__do_action` 的 dialog_click 分支，修复后 3041-3055 行）。

但它的副作用就是根因：`__schedule` 单槽覆盖，把刚排入的 walk 冲掉了。
修复方向因此是**保留点击、错开推进时机**，而不是删掉点击。

## 3. 根因与修复

### 3.1 根因（一句话）

`__handle_dialog` 主动同步分支内，`__start_next_hop` 排入的"下一跳 walk"被紧随其后的
`__schedule(dialog_click)` 以单槽赋值覆盖丢弃，跨图链路静默停住，直到 daily_ghost 120s
兜底重推才恢复（每次白停 86~102s）。

### 3.2 修复（4 处，quest_engine.py）

**① 主动同步不再直接排下一跳；把推进挂在点击动作上（`then_next_hop_ms`）**

```python
# __handle_dialog（原 731-762 区域）
if best != None:
    _adv = 0	# 过图点击执行完后是否继续下一跳(2026-09-21 修复)
    if target and target in option_list[best][0]:
        quest.dijkstra_jumper = None
        try:
            if quest.dijkstra_route:
                ...
                quest.dialog_open = False
                quest.dialog = None
                # 原: __start_next_hop(robot_object, quest, 800)  ← 会被下一行 schedule 覆盖
                _adv = 800
        except Exception:
            _adv = 0
    __schedule(quest, {
        "type": "dialog_click",
        "at_ms": __now_ms() + __human_delay(500),
        "data": {"option_index": best, "then_next_hop_ms": _adv},
    })
```

**② `__do_action` 的 dialog_click 分支：动作执行完(pending 已清空)再推进**

```python
if t == "dialog_click":
    ...
    ret = robot_object.send_message(protocol3.C2S_CLICK_DIALOG, [0, d["option_index"]])
    if ret == error.NET_CLOSED:
        robot_mgr.g_mgr.drop_robot(robot_object)
        return error.ROBOT_DELETED
    # 2026-09-21 修复(跨图中转点堆积)
    _adv = int(d.get("then_next_hop_ms", 0) or 0)
    if _adv > 0:
        __start_next_hop(robot_object, quest, _adv)
    return 0
```

→ 点击照发（500ms 节奏不变），点击后 pending 清空，再排 walk（800ms）——**两个动作不再抢同一个槽**。

**③ `__start_next_hop` 的 `final == None` 分支不再静默 return**（加固，防同类"停住无信号"）

```python
if final == None:
    _plan = getattr(quest, "dijkstra_plan", None)
    if not _plan:
        # daily_ghost 模式(__goto_xy 显式 final=None): 到达目标图即完成, 交回上层
        diag.log("NEXT_HOP_DONE route=0 final=None 交回上层(daily_ghost)")
        return
    # quest 链模式: 属异常 → 用 plan 记的原目标重规划(复用 __teleport_click)
    #   同一时间窗限 NAV_REPLAN_MAX=3 次 + 递增退避(1500ms×N), 用尽报错交回上层
    ...
    __teleport_click(robot_object, quest, _plan.get("npc_id"), _plan.get("npc_index"),
        int(_plan.get("click_type", 0) or 0),
        int(_plan.get("delay_ms", 500) or 500) + NAV_REPLAN_BACKOFF_MS * _n,
        no_npc_jumper=bool(_plan.get("no_npc_jumper")))
    return
```

**④ 常量与 plan 补字段**

```python
NAV_REPLAN_MAX = 3
NAV_REPLAN_WINDOW_MS = 60 * 1000
NAV_REPLAN_BACKOFF_MS = 1500
# __goto_pos 的 dijkstra_plan 增加 "pos": pos（重规划兜底用）
```

**行为边界**：正常路径（有 hop / 有 final）行为完全不变；不引入无限重规划
（时间窗 + 上限 + 用尽报错）；所有 quest 字段访问沿用 `getattr`/`.get` 兜底（热更 reload 兼容）。
