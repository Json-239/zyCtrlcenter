## 2. 代码路径推演（哪一行把状态推回去的）

循环的五环，全部可在代码中定位（行号为**修改前**线上版本）：

```
① READY 分支（L2477-2488）
   for ti, t in quest.tasks.items():
       if is_ghost_task(ti):
           if ti == GHOST_SUBMIT_TASK:          # 2019511 是 int 键 → 恒命中
               __set_state(g, "SUBMIT", now_ms)
               __goto(robot_object, g, BROKER_NPC_ID, …)   # → 去钟馗
           else: …WAIT_GHOST…
           return 0

② SUBMIT 分支（L2799-2855）
   _has_deliver = True（2019511 在 quest.tasks 里）
   g.rounds >= 2 不满足 → 不计数、不 return → 落到底部通用看门狗等 20 秒超时

③ 底部看门狗（L2888-2953）
   if __timeout(g):        # SUBMIT=20000ms（L430-438）
       g.rounds += 1       # L2905 —— 只有状态连续保持 20 秒才会走到
       …

④ 点击钟馗 → 服务端推 S2C_SHOW_DIALOG（"已有任务菜单"变体 B，含"放弃捉鬼"）
   on_show_dialog L1522 起：
       has_abandon=True and npc_id==BROKER_NPC_ID
       _local_has = any(is_ghost_task(ti) for ti in quest.tasks)  # L1534-1538 → True
       → 不买令（或买令失败已跳过）、不走"放弃/恢复缓存"
       → L1608-1617【把状态推回去的那一段】：
             g.abandon_tries = 0
             quest.dialog_open = False; quest.dialog = None; …
             __log(…"钟馗弹已有任务菜单(放弃捉鬼), 关闭对话回 READY 去完成已有任务")
             __set_state(g, "READY", __now_ms())      # ← L1616：状态被打回 READY
             return True

⑤ 下一帧回到 ①，`quest.tasks` 里 2019511 仍在，dict 键序仍在首位 →
   又进 SUBMIT → 又去钟馗 → …（周期 2~3 秒，因为人就在钟馗旁边）
```

**闭环成立的关键**：本地任务表 `quest.tasks` 中，"服务端不认的交付任务 2019511"排在"可继续推进的打鬼任务"之前（16:00–16:11 键序 `['2019511','2019503']`，17:01 后 `['2019511','2019503','2019506']`，2019511 始终第一）。READY 的遍历按 dict 插入序取第一个可处理项，于是每次都优先交付 2019511；而服务端对交付的响应是"已有任务菜单"（不给交付对话），于是每一步都原地踏步。

### 2.1 为什么既有的四道上限全部失效

| 既有机制 | 为什么不触发 |
|---|---|
| `SUBMIT_FAIL_LIMIT=3`（L2839-2855） | 计数条件 `g.rounds>=2`，而 `g.rounds` 只在看门狗 20 秒超时时 +1（L2905）。每轮 2~3 秒就被 L1616 `__set_state(g,"READY")` 重置 `state_since_ms`（`__set_state` 在状态变化时重写计时）→ 20 秒永远攒不满。全天只在"跨图走路能连续 20 秒"的 15:47:06 / 17:02:17 各攒到 1 次（`SUBMIT 交付第 1 次无进展`），永远到不了 3 |
| `BROKER_NODLG_LIMIT=8`（L466-476） | 统计的是"点钟馗**无任何对话**"，本例每次点击都有菜单返回，计数被 `on_show_dialog` L1381 清零 |
| `ABANDON_FAIL_LIMIT=2` | 只在"本地无记录"路径（L1552 块）；本例 `_local_has=True`，走 L1609 时还顺手把 `abandon_tries` 清零 |
| 对话 30 秒超时兜底（L2430-2456） | 对话每次都被 L1610-1614 主动关掉，永远等不到 30 秒 |

补充：`on_add_task`（L1299）/`on_finish_task`（L1316）里的 `g.submit_fail = 0` 也解释了为什么 `submit_fail` 即使在缓慢累计也总被清掉（16:59 收到了新打鬼任务 2019506）。

### 2.2 结论（根因）

**本地任务表存在"服务端不认的交付任务 2019511"且键序始终排在打鬼任务之前，READY 反复把流程导向 SUBMIT；服务端回以"已有任务菜单"，`on_show_dialog` 的 L1616 把状态打回 READY，形成 2~3 秒死循环；而所有"无进展"类计数都依赖不会被这种高频打回刷新的计时器，因而全部失效。**

本次修复正是按用户验收口径，为这一环（L1608-1617）补上"连续 N 次无进展 → 中控重登"的独立计数通道。

def __task_fingerprint(quest, g):
    # 抓鬼任务键集合(排序) + 当前任务 + 完成数; 任一变化 = 有实际推进
    _keys = tuple(sorted(str(ti) for ti in (quest.tasks or {}) if is_ghost_task(ti)))
    return (_keys, str(getattr(g, "task_index", 0)), int(getattr(g, "done_count", 0) or 0))

### 3.4 `on_show_dialog` 的"关对话回 READY"分支（原 L1608-1617）

原逻辑（保留语义）+ 新增连续检测与重登出口：

```python
# 本地确实有任务: 关闭对话回 READY 去完成已有任务
g.abandon_tries = 0
_fp = __task_fingerprint(quest, g)
if _fp == getattr(g, "broker_menu_fp", None):
    g.broker_menu_streak = int(getattr(g, "broker_menu_streak", 0)) + 1
else:
    g.broker_menu_fp = _fp
    g.broker_menu_streak = 1
__log(robot_object, "warn",
    "钟馗弹已有任务菜单(放弃捉鬼), 关闭对话回 READY 去完成已有任务(连续 %d/%d 次无进展; tasks=%s task_index=%s done=%s _local_has=%s)" % (
        g.broker_menu_streak, BROKER_MENU_STREAK_LIMIT,
        [str(ti) for ti in (quest.tasks or {})], g.task_index, g.done_count, _local_has))
if g.broker_menu_streak >= BROKER_MENU_STREAK_LIMIT:
    quest.dialog_open = False; quest.dialog = None; quest.pending = None
    quest.walk_target = None; quest.dijkstra_route = []
    g.broker_menu_streak = 0; g.broker_menu_fp = None
    __need_relogin(robot_object, g,
        "钟馗已有任务菜单连续 %d 次无进展(本地与服务端任务状态不一致)" % BROKER_MENU_STREAK_LIMIT)
    return True
quest.dialog_open = False; quest.dialog = None; …   # 原有关对话逻辑
__set_state(g, "READY", __now_ms())
return True
```

- 未达阈值时**完整保留**"关对话回 READY 去完成已有任务"原语义（正常路径不误伤）。
- 达阈值时复用现有重登通道 `__need_relogin` → `GHOST_DIALOG_STUCK` 事件 → 中控下线重登 + 补发（中控侧有 15 分钟冷却 + 当日 5 次上限）。
- warn 级诊断日志每次弹菜单都打印：连续计数、`quest.tasks` 全部键、`task_index`、`done`、`_local_has`。

## 5. 残留风险

1. **误杀窗口**（可接受）：弹菜单后若进入"等刷鬼 30 秒超时 → 回钟馗"这类**真实无进展**路径，连续 3 轮（约 90 秒+）也会达阈值触发重登。此时重登本身就是设计好的恢复手段（中控 15 分钟冷却），代价有限。
2. **重登后任务表若原样重现**（2019511 与打鬼任务仍并存），可能再次累计触发重登；重登会重建 Robot 对象、任务表由服务端 TASK_LOAD/TASK_ADD 重建，若服务端确实仍推该组合，说明"交付任务在身但钟馗不给交付对话"是服务端侧交互问题，需另开工单联合排查（中控冷却可防风暴）。
3. **深层根因未除**：服务端为何在交付任务在身时弹"已有任务菜单"而非交付对话（`task_limited` 显示 `2019511/f=6/r=0` 的历史交付记录）未在本次解决，本次为客户端侧兜底自愈。
4. **未部署**：两份文件已同步一致，但**未热更/未重启**，修复暂未生效；需按既定部署流程另行操作。
