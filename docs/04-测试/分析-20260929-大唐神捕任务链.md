### 2.2 三层诊断

**第 1 层：running=0 —— 心跳 daily 判据是"state != STOPPED"**

- 计算处：`internal/api/autotask.go:905-944`（`autotaskOnlineCount`）：`DailyOf(key)` 条目存在且 `State != "STOPPED"` 且未满才计数。
- 事实：5256/5274 在 10:30:20/10:01:10 因包满停止后，**`m_share_daily.enabled` 仍为 true**（`share_daily.py:3922 __request_stop` 只改 `state=STOPPED`，**不清 enabled**——全文件 enabled 赋值点仅 1057/1895/1930/1986/2005），且 tick 不再执行（`share_daily.py:2260-2261` STOPPED 早退）。
- 于是心跳 daily = `{share_key, done, limit, state:"STOPPED"}` 一直上报 → running 判据"含 STOPPED"→ 不计。
- **口径矛盾**：同一份心跳，`/api/daily/overview` 把"有条目且未满"标成 `state:"running"`（`sharedaily.go:438-446 shareDailyStateEnum`），而 `/api/autotask` 的 running 判 STOPPED——**两个面板值互相打架**，用户看到的"账实不符"一半来自这里。

**第 2 层：candidates=0 —— 三类号全被排除**

`autotaskCandidatesCfg`（`autotask.go:643-808`）+ `shareDailyCandidateOf`（`sharedaily.go:379-425`）逐类排查：

| 号类型 | 数量（今日） | 拦截点 | 结果 |
|---|---|---|---|
| 抓鬼满额 → "转野外游荡" | **曾满额 156 个**（日志去重：今日任何时刻出现过 `抓鬼满额(50/50)/转野外游荡`；**≠ 当前都在游荡**——含已离线/被回收的号）。当前口径：在线+等级≥40+满额 = **33 个**（11:45 快照），其中 `walk.enabled=true` **31 个**（94% 被游荡占用）；游荡池实时 `running=124 / target=100` | `autotask.go:708` `isTasking(r)`→`waterline.Busy`→`Walking()=true` → "在跑就不打扰" `continue` | ❌ 不可选 |
| 意图=ghost 且抓鬼未满 | ~75 个 | `sharedaily.go:402-407`：`k != shenbu && !assigned`，`ghostFull=false` → 让路 | ❌ 不可选 |
| 台账续跑（5256/5274） | 2 个 | 停止后**全局 state 冻结在 CLICK/NAV**（share_daily tick 早退 ≠ 全局面板 state 更新）→ `isTasking=true` → `continue` | ❌ 不可选 |

（满额号三口径对照与 fenghuo-analysis §9-5 交叉核对：156=今日曾满额 / 33=当前在线达标满额 / 31=其中在游荡 / 124=游荡池 running；结论同向——满额号绝大多数在游荡且被 isTasking 挡住候选。）

- 三个口径叠加后 `len(candidates)==0` → Runner 每 300s 一轮全部"没号可拉"。
- **设计冲突实锤**：候选侧专门为"抓鬼满额"开闸（`sharedaily.go:403-406`：`k==ghost && ghostFull` 放行），但**满额号在机器人端随即被转成游荡**（`daily_ghost` 满额分支：`抓鬼满额(50/50) → 转野外游荡(不下线)`），Busy 一票否决，开闸形同虚设——**"抓鬼满额→神捕"的让渡从未发生**。
- 注：机器人端 `share_daily_start` 本来就会**主动停游荡**（`share_daily.py:1983-1989` 停 `m_collect_walk`），即"给游荡号派神捕"在机器人端是安全的——卡住它的纯粹是中控候选闸。

**第 3 层：usable=0 = candidates 长度**（`autotask.go:868-873`，分享日常族 used=candidates）→ 由第 2 层直接得出。

## 六、修复建议（按优先级）

> 均为"根因链 + 最小修法方向"；本报告不改码。

### P0-1 部署修正：启动脚本补 `CTRL_SHARE_DAILY=1`
- 根因：`config.go:315 ShareDailyEnabled = envBool("CTRL_SHARE_DAILY", false)`；`_start_detached.bat`/`_restart_warm_20260928.bat` **只设 CTRL_FENGHUO=1**；全仓库 bat/sh 无 `CTRL_SHARE_DAILY`（grep 0 命中）。中控"心跳判 shenbu"从未生效（09-28/29 日志 0 条"大唐神捕今日未满"）→ 神捕意图只依赖"续跑·台账"，跨日即断（0 点 5256 被切 ghost 的直接原因之一）。
- 最小修法：两个启动脚本各加一行 `set CTRL_SHARE_DAILY=1`；重启一次中控验证 `/api/intents` 出现 reason 含"大唐神捕今日未满"的条目。

### P0-2 候选闸：日常族放行"游荡中"的满额号（治"没号可拉"）
- 根因：满额号"转野外游荡"（当前在线达标 33 个中 31 个在游荡；游荡池 `running=124 > target=100`，富余 ~24 个）→ `waterline.Busy`（Walking）→ `autotask.go:708` 跳过；而机器人端 `share_daily_start` 本来就会停游荡，不存在抢断风险（与抓鬼不同）。
- 最小修法 A：`autotaskCandidatesCfg` 中对 `isDaily`（shenbu/fenghuo）改用"排除 Walking 的 Busy"变体（或 `if hasLive && isTasking(r) && !(isDaily && ghostFullFor(r)) { continue }`）；先小流量验证 2~3 个满额号。
- 最小修法 B（fenghuo-analysis 交叉核对补充）：游荡池已有"回收给任务池"机制（`[ROAMPOOL] 回收 → ghost_start`），但**只服务抓鬼**——把 shenbu/fenghuo 纳入 roampool 回收目标，即可复用既有的"回收→派活"通路（比改候选闸影响面更小）；且当前游荡池富余 24 个，**有现成号源、不必等抓鬼慢下来**。

### P0-3 停止状态机：`__request_stop` 清 `enabled`（治"冻态死号"）
- 根因：`share_daily.py:3922-3936` 停止不清 `g.enabled` → ① 心跳 daily 永带 STOPPED 条目（running 口径混乱）；② `random_walk.py:1872` 守卫继续拦游荡；③ 恢复引擎按"在跑"不补发 → 号卡死。
- 最小修法：`__request_stop` 末尾加 `g.enabled = False`（人工停止路径 `dispatch_cmd share_daily_stop` 已有此语义，可对齐）；若担心"恢复当前任务"依赖 enabled，则改为**停止时把心跳条目置 None 并复位全局 state 为 IDLE**（二者择一，需评估"重启恢复"链路）。
- 顺带：`__cmd_start` 幂等分支（`share_daily.py:1937-1955`）把 `STATE_STOPPED` 归入"可重启"是对的——现状已含。

### P1-1 接取空菜单：识别 + 长退避 + 降噪
- 根因：`share_daily.py:1670-1677` 空菜单只"不点"，靠 2271-2269 的 30s 对话看门狗清态重试 → 每次重接 ~10 分钟、245 次日志。
- 最小修法：空菜单视为"服务端未就绪（冷却/掉任务 buff）"→ 复用 `accept_cd_start_ms` 冷却等待通道（60s 起退避、上限 900s 已有），并聚合日志（首次+每 60s 一条）。

### P1-2 点击任务怪无响应：加熔断与换招
- 根因：`__click_kill` 1.2s 节流无限重试；636 次点击 13597 实例几乎全落空；KILL 超时后仅跨图绕圈回来再点。
- 最小修法：同一目标连续 N 次（如 6 次/20s）点击无"对话/战斗"反馈 → 换个站位（更近/换边）或短暂等待（明雷 60s 重生口径）；累计 M 次 → 放弃该目标并上报。
- 附注：KILL 超时后的"跨图绕圈"（图12⇄24⇄609⇄11）应优先"就地等待/换点"。

### P1-3 包裹已满：前置预检与处置
- 根因：`on_notice` 528/549/839 包满通知 → 直接 `ACCEPT_REFUSED` 停止（`share_daily.py:1868-1871`）；今日 3 个神捕/烽火号因此停摆（5256/5274/5264）。
- 最小修法：接取前预检背包余量（或接取前触发一次整理/丢弃）；停止时上报"需要清包"事件，中控侧可视 + 提供一键清包动作（复用既有 tidy 能力）。

### P2-1 面板口径统一
- `/api/daily/overview` 对 STOPPED 条目显示 `running` vs `/api/autotask` running 不计 STOPPED——同一份心跳两个答案。建议统一为"条目在且非 STOPPED = running；STOPPED = stopped（或 done）"。

### P2-2 观测埋点
- 神捕完成数入 `/api/daily/overview`（done 已有）；建议在 autotask shenbu 的 rounds 里记录"每轮候选=0 的原因直方图"，避免"没号可拉"黑盒。
