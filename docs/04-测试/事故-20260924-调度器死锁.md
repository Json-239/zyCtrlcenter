## 0. 结论（一句话）

**`autotask.Runner` 在持有内部锁 `r.mu` 时回调 `Deps.Candidates`，而 shenbu（大唐神捕）候选判定里又调用了 `a.AutoTask.States()` —— 同一个 goroutine 对不可重入的 `sync.Mutex` 二次加锁，tick 协程永久卡死且 `r.mu` 永不释放**；此后所有需要读 Runner 的路径（AUTOTASK 轮询 / RESTORE 恢复引擎 / `GET /api/autotask` / `POST /api/autotask/stop` / 游荡池缺口计算）全部无限等待。这是**单 goroutine 自锁重入**（不是 ABBA 双锁互等），CPU 不高、没有忙等，与现场观测完全一致。

## 2. 根因（代码路径与锁图）

### 2.1 死锁链（HEAD `f8d8f85`，行号=当前部署代码）

```
goroutine：autotask.Runner.Run 的 5s 定时器（唯一的 tick 协程）
  └─ tickKind(shenbu)                                   internal/services/autotask/autotask.go:317  r.mu.Lock()  ← ①持锁
       ├─ r.d.OnlineCount(kind)  → api.autotaskOnlineCount        （只读状态库，安全，不涉事）
       └─ r.d.Candidates(kind)  → api.autotaskCandidates          （autotask.go:365，**仍在锁内回调**）
            └─ case KindShenbu:
                 ├─ a.shareDailyMinLevel()                    internal/api/autotask.go:683
                 │    └─ a.AutoTask.States()                  internal/api/sharedaily.go:151
                 │         └─ Runner.States() → r.mu.Lock()   internal/services/autotask/autotask.go:282  ← ②同 goroutine 再锁 → 永久阻塞
                 └─ a.shareDailyMoneyShort(r)                 internal/api/autotask.go:689
                      └─ a.shareDailyBalanceGate() → States() internal/api/sharedaily.go:167（同类第二处，行 683 先触发）
```

Go 的 `sync.Mutex` 不可重入：②永远等不到①释放，而①所在的 goroutine 就是②的调用者 → **自锁重入，无任何外力可解**（只有进程重启）。

### 2.2 为什么 RESTORE 一起停摆

`restorer.Run` 每 5s：`TickForce → r.d.Skip(kind, account)`（`internal/services/restorer/restorer.go:251-252`）→ `api.GhostSkipFunc`（`internal/api/autotask.go:151`）→ 对所有 ghost/shenbu 意图走 `poolAllowsDispatch`（`internal/api/autotask.go:189/168`）→ `a.AutoTask.States()`（`internal/api/autotask.go:493`）→ **阻塞在 `r.mu`**（被 §2.1 的死锁协程持有）→ 恢复引擎整条循环停摆，日志归零。

### 2.3 为什么其它路径正常（反证同一把锁）

下列路径都不碰 Runner 锁，所以全部健康：`/api/status`、`/api/daily/overview`、`/api/chains`、`/api/accounts`、WATERLINE 补号（含 `robot_manage add`）、REGHOST 熔断、EVENT/INTENT 心跳链路。
而 `GET /api/autotask`（`handleAutoTaskGet` → `autotaskCandidates(kind)` 对 shenbu 调 `shareDailyMinLevel()` 或随后 `States()`，`internal/api/autotask.go:1001/1010`）、`POST /api/autotask/stop`（`Runner.Stop` 直接取 `r.mu`）与 `POST /api/autotask/run` 则永久挂起 —— 与现场现象逐条吻合。

### 2.4 引入与触发条件

- 缺陷由 **`3c7e493`（2026-09-23，"P0 收尾——Config 补 min_level/balance_gate"）引入**：往 `shareDailyMinLevel()` / `shareDailyBalanceGate()` 里加了 `a.AutoTask.States()` 读取。
- "Runner 持锁回调 Candidates" 自**初始提交**就存在（`aef3a0d`），此前没有任何回调实现回读 Runner，所以没暴露；**本次是 shenbu 策略第一次被真正启用（10:18:52）→ 第一次跑到该分支 → 立即死锁**。
- 触发条件（全部满足即必死）：`kind=shenbu` 已启用 + `TargetOnline>0 且未达标` + 池内存在至少一个能走到 shenbu 分支过滤链的账号（生产几百个号）。
- ⚠️ 重要连带：`LoadAutoTask` 会在重启时按 `data/autotask.json` **自动重新启用上次启用的策略**。所以"只重启不清障"是**无效**的：若 shenbu 仍 `enabled=true`，重启后 ≤5s 必再次死锁。现场 10:28:55 先改 `enabled=false`、10:29:19 再重启，顺序正确 —— 这也是恢复的唯一可行次序。

## 4. 修复方案（已实施，最小改动）

设计原则：**持锁回调不得回读 Runner**；把 shenbu 判据需要的配置改为**随回调入参传入**。

| 文件 | 改动 |
| --- | --- |
| `internal/services/autotask/autotask.go` | `Deps.Candidates` 增加 `cfg Config` 入参；`Deps` 注释写明"Candidates/OnlineCount 持锁调用、禁止回读 Runner"的契约；`tickKind` 改为 `r.d.Candidates(kind, cfg)` |
| `internal/api/autotask.go` | `AutoTaskDeps` 回调改走新入口 `autotaskCandidatesCfg(kind, cfg)`；原 `autotaskCandidates(kind)` 保留为**无锁入口**（面板/池统计用，自行取 cfg）；shenbu 分支改用 `cfg.MinLevel` / `cfg.BalanceGate`；`GhostSkipFunc` 显式传 `a.shareDailyBalanceGate()` |
| `internal/api/sharedaily.go` | `shareDailyMinLevel(cfg)`、`shareDailyMoneyShort(r, gate)` 改为**传参**，函数内不再回读 Runner；`shareDailyBalanceGate()` 标注"仅限无锁场景" |
| `test/autotask/autotask_test.go` | 假依赖适配新签名；新增 `TestCandidatesReceiveLiveConfig` 钉住"配置随回调传入"契约 |
| `test/api/autotask_deadlock_test.go`（新增） | 死锁回归：启用 shenbu 后 Tick / `GET /api/autotask` / `GhostSkipFunc` 三者均须限时返回（修复前 Tick 超时失败） |

行为不变性：无锁场景（面板/手动补发闸）口径与改前逐字一致（`States()`→取 `st.Config` 的值域相同）；持锁场景由"回读 Runner"变为"读同一份入参 cfg"，语义相同且更一致（与 tick 的快照同源）。

## 6. 防复发建议

1. **（P1，结构性）** 把 `Candidates`/`OnlineCount` 的调用移出 `r.mu`：新增"决策串行锁"（tickMu）保证并发 Tick 仍串行，`r.mu` 只做状态表短临界区 —— 从结构上消灭"持锁回调"这一类缺陷，而不是靠注释约束。
2. **（P0，门禁）** 新增策略 kind / 新增回调逻辑时，必须在"**启用态**下驱动一轮 Tick"的单测里过一遍（现有测试多为"仅启动、不 Tick"，正好漏掉本缺陷）；本次回归用例可作为模板。
3. 部署纪律：shenbu 再次启用前必须换修复版 exe；把"策略启用"与"进程版本"绑成检查项（部署单加一条：启用 shenbu 前确认 exe ≥ 修复提交）。
4. 排障口径沉淀：以后遇到"某子系统集体静默 + 面板读接口挂起 + CPU 不高"，先查"谁在持锁回调里打了圈"（`go test` 超时用例或 `curl` 探针即可定位）。

## 7. 遗留疑点（不确定项，如实列出）

1. 同类隐患只剩"契约"护栏：`Deps.OnlineCount` 与 `Deps.Tick` 也属回调，本次已逐一核对在线路径无 Runner 回读，但**未做结构性隔离**（见建议 1），未来改动仍有复发可能。
2. `GET /api/autotask`/`POST /api/autotask/stop` 的挂起为现场 curl 观测（中控不记访问日志），日志侧只能证明"死锁窗口内两子系统静默"，不能给出请求级时间戳。
3. 死锁窗口内 `/api/autotask/run`、`/api/intents/restore`（手动补发，走 `poolAllowsDispatch`）应同样挂起，现场未逐一点验（推断一致，未经实测）。
