# 分析-20260922 水位保持器 / 游荡池 / 自动任务（含恢复引擎）三套编排的交互冲突

> **性质**：只读分析，未改动任何生产代码（仅新增本文档）。
> **证据口径**：Go/Python 源码行号 + `logs/ctrlcenter_20260922.log` + `data/bot_logs/*/runs_20260922.log` + 只读 API（`127.0.0.1:28082`）现场采样（2026-09-22 21:5x~22:0x）。

## 0. 结论速览

| # | 冲突 | 严重度 | 生产是否已表现 | 一句话 |
|---|------|--------|----------------|--------|
| C1 | 游荡池「立刻回收」不校验**回收对象能否填缺口**，且缺口长期为正时**每轮持续回收** | **P0** | **是**（同 3 个号各被回收 20/21 次；回收↔机器人自动游荡 ~2 分钟往返） | 回收把号变成空闲，但号根本进不了任务池 → 白回收 + 抖动 |

## 2. 冲突清单

### C1【P0】游荡池"立刻回收"不看回收对象能否填缺口 → 无效回收 + `回收 ↔ 自动游荡` 往返抖动

**现象**
- 任务池缺口长期为正的窗口里，游荡池每轮都回收，且**反复回收同样的号**；
- 被回收的号随后又被派回游荡（90s 后），形成 ~2 分钟的往返；
- 缺口并不因回收下降（回收的号对任务池不合格）。

**代码证据**
- `internal/services/roampool/roampool.go:626-646`：`if deficit > 0 && cfg.ReclaimOnDeficit { n := minInt(deficit, cfg.MaxStep, running); picked := PickReclaim(robots, n); doStop(...) ; return true }` —— **只看缺口>0，没有任何"回收后能否被任务池选中"的校验**，也没有"上一轮回收是否真的把缺口填上"的记账。
- `internal/services/roampool/roampool.go:409-442`：`PickReclaim` 的唯一过滤是 `Roaming(r)`（`roampool.go:352-362` = `walk.enabled`），不查 `GhostDoneToday` / 等级门槛 / `StuckCount` / `ErrRepeat`。
- 对照：任务池的候选判据在 `internal/api/autotask.go:172-280`（`GhostDoneToday` 235、`ghostGate` 250、卡死 209-212）。
- 缺口口径：`internal/api/roampool.go:60-72`（读 `autotask.States()` 的 `Deficit = TargetOnline - cur`）。
- 机器人端把号送回游荡：`deploy/.../script/auto_roam.py:61-105`（**空闲 90s** → `random_walk.dispatch_cmd`，`robot_auto_roam_idle_sec = 90` 见 `script/config.py:459-463`）。

**最坏后果**
1. 游荡产出被逐步清空：每个持续为正的缺口窗口，每轮吃掉 `max_step` 个游荡号，而这些号不会留在任务池 → 号在"游荡 30s / 空闲 90s"之间空转，游荡（打野/暗雷）等于零产出；
2. 每次回收都中断一次跨图/在图内的路程（用户已知的"路程损耗"），本场景里是**纯损耗**；
3. 中控日志被"回收 N 个"刷屏，掩盖真实缺口原因。

**生产证据（本日）**
- `logs/ctrlcenter_20260922.log`：`回收 N 个游荡号给任务池` 共 73 条，其中 **robot0001108 被回收 21 次、robot0001127 20 次、robot0001176 20 次**（其余号最多 2 次）；缺口在 `21:09:22→21:24:22` 维持 `26/26/26/27…27`，同一秒仍在回收同样几个号。
- `data/bot_logs/robot0001127@xy3.com/runs_20260922.log`：`集合走停止 ts=1790083702 → 集合走启动 ts=1790083792（+90s）→ 集合走停止 ts=1790083822（+30s）→ 启动 +90s …`，全天 `集合走启动` 21 次 / `集合走停止` 20 次，**周期 = 90s 空闲 + 30s 游荡**（90s 与 `robot_auto_roam_idle_sec` 精确吻合；中控 `random_walk` 只负责"停止"，启动全部来自机器人端 auto_roam）。
- 这 3 个号当天已被判满额：`robot0001127` 有 `抓鬼满额(50/50)`（`runs_20260922.log` ts=1790084972），`robot0001108` 有 `启动时计数已满 50/50(服务端/中控权威)`（ts=1790084560）→ 它们**永远不可能**出现在抓鬼候选里（`api/autotask.go:235`），回收纯属无效。

**现有缓解**：`ReclaimOnDeficit` 可关（但那就等于放弃"任务优先"口径）；`max_step=5` 限幅（只限速，不限方向）。

**建议**
1. **回收前置资格校验**（最小改动）：回收只挑"回收后能进任务池"的号——至少排除 `St.GhostDoneToday(acc)`；`roampool.Deps` 增加 `Eligible func(kind, account) bool`（壳层直接用 `GhostSkipFunc` + 等级门槛），不合格的号不回收。
2. **回收记账**：回收成功后把号加入"已让位"集合（TTL 5~10 分钟），下一轮缺口仍在且这些号未被任务池拉起时**不再重复回收**（并记一条 warn："回收无效：号不合格/任务池未取用"）。
3. **停住机器人端 auto_roam 的"抢派"**：给机器人端一条"中控说了算"的开关——当号处于"任务池缺口为正 + 本号不合格"时，auto_roam 应维持一个更长的冷却（或由中控下发 `minutes` 限时游荡 + 不回收时段），避免回收后 90s 又被拉回游荡。

### C2【P1】恢复引擎补发缺 `GhostDoneToday` 门槛 → 向"今日满额"号补发 `ghost_start`

**现象**：满额号被判满 → 停抓鬼 → 转游荡；同秒/数秒后中控又给它补发 `ghost_start`，机器人再判一次满 → 再转游荡。

**代码证据**
- `internal/api/autotask.go:131-146` `GhostSkipFunc`：只查 ① `ghostGateFor`（等级）② `stuckCountToday >= 3`，**没有 `St.GhostDoneToday(account)`**。
- `internal/services/restorer/restorer.go:225-231`（Skip 调用）、`restorer.go:273-284`（每次补发都算一次 attempt）。
- 同类判据在任务池里是有的：`internal/api/autotask.go:235-237`。
- 机器人端后果：`deploy/.../script/daily_ghost.py:1339-1359`（服务端/中控权威计数已满 → `__emit_ghost_done` → `daily_ghost.py:610-645`：停抓鬼 + **立刻转野外游荡**）。

**最坏后果**：满额号在中控与机器人之间被反复"补发→判满→转游荡"；每次消耗 restorer 的 3 次 attempt（300s 冷却后熔断 1800s），并把该号的抓鬼会话反复置 READY，干扰"满额后安静游荡"。数量级不大（单号每天 1~3 次），但属于明确的判据缺口。

**生产证据**
- `logs/ctrlcenter_20260922.log:16256` `21:42:33 [ROAMPOOL] 回收 2 个…：robot0001108, robot0001176`
- `logs/ctrlcenter_20260922.log:16282` `21:42:40 [RESTORE] [robot0001078, robot0001108, robot0001167, robot0001176, robot0001185, robot0005089, robot0005302, robot0005328] 补发 ghost_start（…当前 IDLE）`
- `data/bot_logs/robot0001108@xy3.com/runs_20260922.log` `ts=1790084560(=21:42:40)`：`{"type":"ghost_done","reason":"启动时计数已满 50/50(服务端/中控权威)"}` → **同一秒的因果关系**。

**现有缓解**：`MarkGhostDoneToday` 会写入 `ghostUnavail`（`internal/state/state.go:159-178`），但**只有 autotask 读它**。

**建议**：`GhostSkipFunc` 增加一条：`if a.St != nil && a.St.GhostDoneToday(account) { return true, "今日抓鬼已满（只离线/游荡，勿补发）" }`（与 `api/autotask.go:235` 同口径）。

### C3【P1】恢复引擎不读任务池保持数/开关 → 池"被顶穿"、挤占游荡名额

**现象**：新手池 `target=0` 且 `enabled=false`，但仍有 16 个号在跑新手链；抓鬼池 `running=102/104 > target=100`。恢复引擎完全按 `intent`（等级判据）补发，不看池的保持数/开关（`internal/api/autotask.go:131-146` 的 Skip 也没有池状态）。

**代码证据**
- `internal/services/restorer/restorer.go:167-185`（判据只看机器人状态）+ `restorer.go:220-231`（意图→命令）。
- 任务池的保持数闸在 `internal/services/autotask/autotask.go:335-340`（`cur >= TargetOnline` 达标不补）与 `:372-379`（按差额限幅）；**restorer 没有对应逻辑**。
- 意图判定只看等级：`internal/services/intent/intent.go:72-90`（<31 → newbie），与"池是否需要"无关。

**最坏后果**：只要 `intent=newbie` 的号在线，恢复引擎就会持续补发 `start_chain`（现场 21:41 重启后 25 次）→ 这批号既不做抓鬼（等级不够）也不游荡（任务链在跑），**白占在线名额**；抓鬼池亦然——autotask 已达标不补，restorer 仍能继续补，实测 `running` 越过 target（102/104），把游荡池的目标名额吃光（roampool `last_action` 明确："差 15 个，但没有空闲号可派（在游荡 85 / 目标 100，空闲 0）"）。

**生产证据**：现场 API（见 1.3）；`logs/ctrlcenter_20260922.log` 21:41 之后 `补发 start_chain` 25 次、`补发 ghost_start` 36 次、而 `autotask 已下发抓鬼任务` 仅 11 次（重启后至今）。

**现有缓解**：无（只能手动停策略——但停策略不影响 restorer，反而是"停不干净"的坑）。

**建议**：给 restorer 的 `Skip` 闸补池信息：`newbie` 意图当 newbie 池 `!enabled || TargetOnline<=0`（或 running ≥ target）→ 不补；`ghost` 意图当 ghost 池 `running >= TargetOnline` 且该号无活跃会话说 → 不补（保留"会话丢失兜底"用 `GhostActive` 判定，避免误伤真正的掉线恢复）。**口径要写进文档**：restorer 的定位应从"按意图补发"收窄为"任务池的补偿器"。

### C4【P1】同一号被两个模块重复下发 `ghost_start`（机器人端**不是幂等**）

**现象**：一个号在同一分钟里收到两次甚至三次 `ghost_start`。

**代码证据**
- `internal/services/restorer/restorer.go:181-184`（IDLE/ONLINE 即补发；`Run` 每 5s 一轮，`restorer.go:304-327`）；
- `internal/services/autotask/autotask.go:396-404`（挑中离线号 → 先 `robot_manage add` → **8s 后**再 `Launch`）→ 两条链路互不知情。

### C5【P2】`isTasking` 漏 `GhostActive`/`Fight` → 在跑的号被当空闲候选

**代码证据**：`internal/api/autotask.go:302-316`（`isTasking` 只查 `Walking` + 状态字串；**没有** `r.Fight || r.GhostActive()`），对比 `internal/services/waterline/waterline.go:426-437`（两个都有）。调用点 `internal/api/autotask.go:215`。

**现场量化**（两次点采样，22:0x）：198 个在线号中 **39~43 个**满足 `GhostActive=true` 且状态 ∉ {NAV,CLICK,DIALOG,FIGHT,SHOP,ALLOC,WAIT_NEXT,WAIT_TASK(index≠0)}——状态值为 `WAIT_GHOST`（25~38）、`READY`（5~9）、`SUBMIT`（0~5）。即 `autotaskCandidates(ghost)`（现场 241 个候选）里混着这 39~43 个"正在跑"的号。

**最坏后果**：当 `cur < target` 时，`n = min(batch, target-cur, len(cands))` 从 241 个候选里**随机**挑，可能重复挑中"已在跑"的号 → 一次无效的 `ghost_start`（叠加 C4 的重置副作用）。数量级：每次挑中概率 ≈ 39~43/241 ≈ 16~18%（挑 3 个时约 40%+ 至少撞一个），但因为 `cur` 已把它们算进去，实际浪费的是"本可以拉起真空闲号"的名额。（前提：这些号在账号池里有记录——现场绝大多数在，`api/autotask.go:186-201` 的遍历只覆盖池内条目。）**双保险缺一**：`autotaskOnlineCount`（`api/autotask.go:362-389`）已修正为按活跃会话说，候选侧却没收紧。

**建议**：`isTasking` 直接改为调用 `waterline.Busy(r)`（或补 `if r.Fight || r.GhostActive() { return true }`），删掉这份复制实现，避免第三套"忙"口径。

### C6【P2】`roampoolDeficit` 把新手池的负缺口与抓鬼池的正缺口相加 → 该回收时不回收

**代码证据**：`internal/api/roampool.go:60-72`：`sum += st.Deficit`（kind 取 `ghost` + `newbie`）。

**现场量化**：`ghost deficit=-2`、`newbie deficit=-16` → `Deficit=-18`；`newbie` 池 `target=0` 却 `running=16`（C3 造成）。若哪天 `ghost` 缺 10 个（`running=90`），合计仍是 `-6` → **游荡池不会回收**（还可能在 ② 分支继续往游荡派号）。两个池的"缺人"语义完全不同（新手池根本不该有人），相加没有物理意义。

**建议**：只统计**启用中**的池（`enabled && TargetOnline>0`），或对每个池分别判决（`ghost` 缺口 → 回收；`newbie` 缺口 → 不管）。同时把 `deficit` 在 status 里拆成明细，便于面板判断。

### C7【P2】水位器 / 游荡池 争"空闲号"，且机器人端 `auto_roam` 与中控抢"派游荡权"

**现象 / 代码证据**
- 水位器要断的就是"空闲号"：`PickOffline` 的 `preferIdle`（`waterline.go:360-399`，默认 true）；
- 游荡池要派的正是"空闲号"：`PickIdle`（`roampool.go:445-459`）；

**建议**：面板/文档明确"游荡派发以中控为准"；给机器人端 `auto_roam` 增加"中控在管时退让"的开关（例如中控可在心跳里下发 `roam_policy=managed`，或机器人端读一个 `robot_auto_roam_idle_sec` 大幅调大如 600s），从源头消除 C1 的驱动源。

## 4. 本次修复后的新风险评估（461 个号回到候选池）

**结论：不会再出现"候选池为空"，但会出现"没有冗余 → 三池拉锯 + 游荡池被挤空"的新常态。**

1. **数量上刚好、没有冗余**：`waterline target=200`，池目标 `ghost 100 + newbie 0 + roam 100 = 200`。461 个号回到候选池只解决"能不能补到 200"，**不解决"200 的名额怎么分"**。实测已经出现：`ghost running=102`（超编）+ `newbie running=16`（池关闭仍在跑）→ `roam 只有 85，且"空闲 0"，永远差 15`。
2. **拉锯的形式**（推演 + 已知证据）：
   - 抓鬼池缺人（例如 stuck/不可用累计 31 个、`ghost_unavailable_today=31`）→ roampool 回收游荡号；
   - 被回收的号里必然有一部分"今日满额/未毕业/卡死≥3"→ 任务池**永远不会取用**（`api/autotask.go:209-212,235-237,244-252`）→ 90s 后 auto_roam 又把它拉回游荡 → 再回收（C1 实测）；
   - 如果 restorer 也在补（C3），抓鬼 `running` 会越过 target → `roampoolDeficit` 变负 → 游荡池转入"补位"但"空闲 0" → 游荡数量被锁死在 `200 - ghost实际 - newbie实际`。
3. **放大因素**：`ghost_unavailable_today` 只增不减（跨日才清），每天越晚"不可抓鬼号"越多，游荡池可用的"合格抓鬼号"越少，回收/补位判决越容易失真；`newbie` 池 target=0 但 restorer 造出的 16 个"任务占用号"是纯固定损耗。
4. **建议的余量策略**（三选一，需用户拍板）：
   - **A. 给游荡池留余量**：`waterline target = 200`，`ghost target` 按"可用合格号上限"动态取（如 `min(100, 候选里非满额号数)`），roam = 200 − ghost_实际 − newbie_实际，并允许 roam target 自动跟随（面板显示"余量池"而不是固定 100）；
   - **B. 加互斥/优先级**：明确"任务池 > 游荡池 > 水位器压号（压号只压空闲且非任务池候选）"，并用 C1/C3/C6 的改动落实；
   - **C. 给 retuser 加"必须比池更保守"约束**（restorer 只在池有缺口时补），把所有"补号权"收回到池/水位器两家。
