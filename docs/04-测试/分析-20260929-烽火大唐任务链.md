## 1. 为什么"几乎没在跑"（供给链断裂，重点）

### 1.1 烽火号从哪来：意图分配链路（代码事实）

- 判据入口 `decideIntent`：`internal/services/event/event.go:371-410`
  - 触发点：机器人上线 / hello / **心跳(status)**（:360、:668）。
  - 基础判据 `DecideDailyStates`：`internal/services/intent/intent.go:163-196` ——
    **等级 ≥40 且心跳 `daily` 明确上报"该玩法未满"且开关启用** → fenghuo；两个玩法都满足时 **shenbu 优先**。
  - ⚠ 机器人端 `daily` 块**只在会话 enabled=true 时上报**（`client.py:713-725`）→ **没在跑 share_daily 的号，
    心跳里没有 fenghuo 信息（Known=false）→ 永远判不到 fenghuo**。
  - 台账兜底 `dailyAssignedIntent`：`event.go:412-443` —— 心跳丢失（重登/重启）时，按
    "今日已派且未见满额"的持久台账恢复玩法意图（顺序 shenbu → fenghuo）。
    **台账只在"下发成功 share_daily_start"时写入**（`internal/api/sharedaily.go:505-512`）。

> 结论：**意图是"自持"的**——要先跑起 share_daily（心跳/台账）才拿得到 fenghuo 意图；
> 而新号要跑 share_daily 必须先被"候选"挑中。这是一个自锁环，唯一的外部注入点是候选通道和手动「启动」。

## 4. 链路健康度：故障根因（新发现，按影响排序）

### 4.1 跳转点 destination 30 热循环（5207/5275；今天 76% 的错误量）

- 现象（5207，1100:03-11:10 持续）：`到达跳转点(2629,3614), 发 C2S_DIJKSTRA_DESTINATION 30` →
  `跨图跳转被拒绝(destination 30), 重走跳转点重试(第 N 次)`（**N 从 1059 一路涨到数千，每秒 1 次**）→
  `拉黑 10 分钟, 换其它跳转点重新规划` **但同秒又重发同一跳点**（拉黑未生效）→ `任务出错 TASK_STUCK` 每条重试都上报。
- 另一形态（5275）：`换路重规划(destination 30, 免费优先): 回滚后图不匹配(本跳 30 属地图 21, 当前图 25)`
  → **乐观过图回滚残留导致"本跳不属于当前图"**（A 型乐观过图的 share_daily 版本；参考 daily_ghost 的 R-1 修复，
  `docs/04-测试/分析-20260928-抓鬼停摆…`/R-1 条目）。R-1 的"同点回滚≥2 → 硬黑名单 → 无路停链"只做在 daily_ghost，
  **share_daily.py 的导航重试没有这套守卫**。
- 代价：5207 error 2804 条 + 5275 error 2525 条 = 全站 error 6982 条的 **76%**（TASK_STUCK 全场 5363 条几乎全来自这两号）；
  日志被刷爆（20 分钟/万行量级），且两号全天 done=0 和 2。

### 4.2 背包满：最高频故障（6/9 号）

- `SHOP_FAILED`：`采购失败: item=xxx (NPC 1300x, 购买被拒: 背包空格不足)`（5162/5208/1175/5235/1080）；
- `ACCEPT_REFUSED`：`接取任务失败: 包裹已满，请清理包裹`（5264）；
- 代码里已有 `BAG_FULL` 停止分支（`share_daily.py:3741-3743`），但只有"停止"没有"清理"——
  号一旦背包满就反复卡死，且**没有清包/丢弃流程接管**（bag_ops 已有丢弃能力，未见接入烽火链路）。

### 4.3 HANDIN_STUCK：交付连拒 13 次后停止，且中控不当"卡死"处理

- 触发点 `share_daily.py:3749-3750`（尝试 13 次 → `__request_stop(g,"HANDIN_STUCK")`）。
- 中控 `onError`（`event.go:776-825`）+ `isStuckCode`（:871-877）白名单 = `{GHOST_DIALOG_STUCK, TASK_STUCK, STUCK_*}`——
  **`SHARE_DAILY_HANDIN_STUCK` 不在内** → 不触发 reghost 重登、不记当日 StuckCount，只 `MarkTaskError`（ErrRepeat=1）。
  该号随后**没有任何自动恢复路径**（实测 5054 空转 8 小时）。
- 5054 的样本细节：任务 2002103 要"军需品 220602"，bot 判定"背包已满足，等服务端标可交"→"库存已够但服务端未标可交,
  去 catcher 催一次"→点击后 `任务对话无可点选项` 循环 → 13 次 → 停止。**需要按"需求物品判定口径"单独复核**
  （可能拿错物品/数量口径不符/服务端要求打不同的催交付 NPC）。

### 4.4 停止后不"收工"：死会话挡住游荡（20 号、5636 条刷屏）

- `__request_stop` **只置 state=STOPPED，不清 `enabled`**（`share_daily.py:3922-3940`）→ 心跳仍带该玩法条目
  （state=STOPPED，非满额）；`random_walk` 的"集合走"据此拒绝启动游荡（`random_walk.py:1867-1878`）。
- 现场：20 个号共 5636 条 `集合走: 分享日常进行中(share_daily_宫廷10), 不启动游荡(等日常结束/中控重派)`——
  其中 3004/3006/1058/1166/1185/5102/5150/1028 等 8 个号各 ~398 条（≈每 90 秒一条、持续一天）：
  **这些号在抓鬼，但全天无法被游荡回收**（本来满额后该转游荡）。
- 5054 的 8 小时空转与此叠加：session 死、游荡被挡、抓鬼不派（意图还是 fenghuo，抓鬼候选让路）、
  恢复引擎又没补发（见 §6 待复核）→ 三重静默。

### 4.5 中控恢复链的"静默"特性（可观测性缺口）

- 恢复引擎跳过是**静默**的：Skip 命中只写 `Status.LastMsg`（`restorer.go:252-257`），不落 ctrl 日志；
  `needsRestore=false` 直接 continue（`restorer.go:189-207`、:271-276）。现场看"什么都没发生"。
- 5054 02:12→10:04 无任何 RESTORE 记录（同期 5162/1175 有 RESTORE，说明引擎在工作）：
  排除项 = Skip（池配额/池未启用/满额，`autotask.go:207-289`）或 `needsRestore`（状态不在 IDLE/""/ONLINE/WAIT_TASK0）。
  **未决**：这两条都可能，且都无日志，需补日志后复核（§8）。

## 5. 与神捕的候选竞争 / "系统性饿死"分析

- **不是"神捕优先"饿死烽火**：`decideIntent` 里 shenbu 优先只在"两个玩法心跳都明确未满"时生效；
  今天两个池 **candidates 都为 0、running 接近 0**（shenbu 5256 done=6/10、5274=0/10，均 raw STOPPED）——
  神捕自己也在饿死。共同瓶颈在 §1 的候选通道。
- **真正的饿死机制**（三层，均有数据）：
  1. **意图自锁**：fenghuo 意图只能靠"已在跑"（心跳）或台账（曾派过）自持，**新号永远判不到 fenghuo**（intent.go:163-196 + client.py:713-725）；
  2. **候选让路**：幽灵意图号（229 个）不抓满不让路给烽火（sharedaily.go:402-407）；唯一放行的"抓鬼已满"号（30 个）
     **全部被游荡池占用**（walk.enabled → isTasking 剔除，autotask.go:708-710）——游荡与烽火在同一批号上竞争，游荡全胜；
  3. **running 虚高**：daily 口径"raw≠STOPPED 即算在跑"（autotask.go:923-934），熔断/热循环号照算 →
     `deficit=2` 长期挂账但从不真正补号。
- 09-29 09:58 重启放大了问题：周末班组（3004/3006/1058/1166/5150/5102/1185）的机器人进程重启后
  **share_daily 会话清空（daily=None）→ 心跳再无 fenghuo 信息 → 判回 ghost**（现 7 号 reason 均为"等级 ≥31 → 抓鬼"），
  而它们已不在今日台账里 → **烽火存量池从 8 号缩到 5 号（其中 3 个当天会死/已死）**。

## 6. 修复建议（按优先级；"根因链 + 最小修法方向"）

**P0-1 热循环止血（5207/5275，影响面最大：76% 错误量）**
- 根因链：乐观过图回滚残留 → 传送目标与当前图不符（destination 30 被拒）→ 重试无守卫（每秒 1 次、拉黑失效、计数器跨日累计）。
- 最小修法：把 daily_ghost 的 R-1 守卫移植进 share_daily 的跳转重试：
  同点被拒 ≥2 → 硬黑名单 → 换路；连续 N 轮无路 → **停链一次并静默退避**（不要 1Hz 重试 + 每跳一条 error）。
  先对 5207/5275 清熔断并人工重派验证。

**P0-2 背包满治理（6/9 号的第一死因）**
- 根因链：背包空格不足 → 采购被拒（SHOP_FAILED）/接取被拒（ACCEPT_REFUSED）→ 停止；无清包接管。
- 最小修法：a) 派发前预检心跳 `bag` 空格（中控已有该字段）→ 满则先下发背包整理/丢弃或换号；
  b) 采购前本地清理一次（丢弃低价值物/回收），复用 bag_ops 现有能力；c) `BAG_FULL` 停止分支加"清理后自动重试一轮"。

**P0-3 停止后的"僵尸会话"（20 号被挡游荡）**
- 根因链：`__request_stop` 不清 enabled → 心跳仍带 daily → random_walk 拒绝游荡 + 让路判定继续生效。
- 最小修法：`__request_stop` 里 `g.enabled=False`（或 random_walk 判据改为 `enabled and state != STOPPED`）；
  中控侧 `dailyRunningOf` 同步收紧为"raw≠STOPPED"。

**P0-4 让 HANDIN_STUCK 进"卡死类"恢复链**
- 根因链：`SHARE_DAILY_HANDIN_STUCK` 不在 `isStuckCode` 白名单 → 无 reghost/无重派 → 8 小时空转。
- 最小修法：`isStuckCode` 收录 `SHARE_DAILY_HANDIN_STUCK`（走 reghost 重登→重派）；或至少纳入 ErrRepeat 的
  "当日不再派"（防 churn）。5054 的 2002103 交付口径另开单复核（§4.3）。

**P0-5 恢复引擎可观测（排障前提）**
- 根因链：Skip/needsRestore 跳过全静默 → "8 小时为什么没救"无法从日志定位。
- 最小修法：跳过时按账号节流打日志（每号 5-10 分钟一条：`[RESTORE-SKIP] acc kind 原因`）。

**P1-1 打通烽火号源（结构性）**
- 根因链：意图自锁 + 让路 + 游荡抢占 → 候选恒 0。
